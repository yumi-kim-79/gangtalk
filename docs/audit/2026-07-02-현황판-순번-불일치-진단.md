# 관리자 순번 vs 현황판 표시 순번 불일치 — 진단

날짜: 2026-07-02
증상: 관리자 페이지에서 매긴 업소 순번과 사용자 현황판(`gangtox.com`)에 실제 표시되는 순번이 다르게 보임
관련 PR: PR #124/#125/#126 (노출 필드 분리) 는 정상. 이건 별개 **정렬 이슈**
범위: 진단 전용. 코드 / 룰 / PR / 배포 변경 0건.

---

## 0. TL;DR

- **관리자 순번과 현황판 정렬은 같은 필드 (`config/marketing.homeOrder`) 참조** — 필드 자체는 일치
- **불일치 원인 후보 4 개**:
  - **후보 C (가장 유력)**: 관리자가 Tab 1 에서 드래그만 하고 **"저장" 버튼 안 누름** → 로컬만 바뀌고 Firestore 반영 안 됨 → MainPage 는 옛 순서 유지
  - **후보 D (시각 착시)**: Tab 1 은 **승인된 모든 가게** 표시 (`orderedApproved`, dashboard 여부 무관). MainPage 는 **dashboard=true 인 subset** 만. 관리자가 "1, 2, 3, 4, 5" 로 봤는데 현황판에는 "1, 3, 5" 로 뜸 → 상대 순서는 일치하지만 사용자는 "다르다"고 인식
  - **후보 B (신규 승인 폴백)**: `homeOrder` 에 없는 신규 승인 가게는 `Infinity → 원본 순서 (updatedAt desc)` 폴백. Tab 1 과 MainPage 폴백 로직 동일이라 여기선 불일치 없음
  - **후보 F (별 필드 혼동)**: 관리자가 Top5 페이지 (`config/marketing.topRanks`) 에서 매긴 순번을 현황판 순번으로 오해 — 완전 별개 필드
- **가장 유력한 원인 확정 방법**: Firebase Console → `config/marketing.homeOrder` 배열이 관리자 화면상 순서와 같은지 즉시 확인

## 1. 관리자 순번 저장 방식 (`StoresManagePage.vue` Tab 1)

### 1-1. 필드 = `config/marketing.homeOrder` (배열)
- 타입: `string[]` (stores.id 문자열 배열)
- 위치: `config/marketing` 도큐먼트의 `homeOrder` 필드
- 저장 함수: `saveExposeAndOrder` (`:660-661`)
  ```js
  await setDoc(doc(fbDb, 'config', 'marketing'), {
    homeOrder: homeOrder.value.map(String),
    homeOrderSavedAt: serverTimestamp(),
  }, { merge: true })
  ```

### 1-2. Tab 1 표시 순서 = `orderedApproved` computed (`:450-459`)
```js
const orderedApproved = computed(() => {
  const arr = approvedStores.value                            // 승인된 모든 가게
  if (!homeOrder.value.length) return arr                     // homeOrder 없으면 원본
  const pos = new Map(homeOrder.value.map((id,idx)=>[String(id), idx]))
  return arr.slice().sort((a,b)=>{
    const ai = pos.has(String(a.id)) ? pos.get(String(a.id)) : Infinity
    const bi = pos.has(String(b.id)) ? pos.get(String(b.id)) : Infinity
    return ai - bi
  })
})
```

**★ 핵심**:
- 대상: `approvedStores` = `stores.filter(isApproved)` = **승인된 모든 가게 (dashboard 여부 무관)**
- 정렬: `homeOrder` 인덱스 순
- **폴백**: homeOrder 에 없는 항목 → `Infinity` → 원본 배열 순서 (updatedAt desc)

### 1-3. 드래그 (`reorderApproved` + SortableJS)
- SortableJS `onEnd` (`:530-537`) → `reorderApproved(oldIndex, newIndex)`
- `reorderApproved` (`:508-518`):
  ```js
  const displayIds = orderedApproved.value.map(s => String(s.id))
  const [moved] = displayIds.splice(fromIdx, 1)
  displayIds.splice(toIdx, 0, moved)
  const others = homeOrder.value.filter(id => !approvedIdSet.has(String(id)))
  homeOrder.value = [...displayIds, ...others]     // ★ 로컬만 갱신 (저장은 별도)
  ```
- **드래그만으로는 Firestore 반영 안 됨** — `saveExposeAndOrder` 를 별도 호출해야 저장

### 1-4. 저장 트리거 = "저장" 버튼
- Tab 1 헤더 우측 "저장" 버튼 (line ~37, `@click="saveExposeAndOrder"`)
- 클릭 시:
  1. `exposureEdits` (가게찾기 토글) 반영
  2. `dashboardEdits` (현황판 토글) 반영
  3. **`config/marketing.homeOrder = homeOrder.value.map(String)`** 저장

### 1-5. 새로고침 시 로컬 로스
- `homeOrderLoadedOnce` (`:399, :414-417`) 가드:
  - 첫 onSnapshot 만 로컬 시드
  - 이후 외부 변경 무시 (로컬 편집 보호)
- **저장 안 하고 새로고침** → `homeOrderLoadedOnce` 리셋 → 서버 값으로 되돌아감
- 관리자가 드래그 → 저장 잊고 새로고침 → 순서 사라짐

## 2. 사용자 현황판 정렬 (`MainPage.vue`)

### 2-1. 필드 = 동일한 `config/marketing.homeOrder`
- `subHomeOrder` (`:1786-1796`):
  ```js
  const ref = doc(db, 'config', 'marketing')
  unsubOrder = watchWithLabel('config/marketing.homeOrder', ref, (snap)=>{
    const data = snap.exists() ? (snap.data() || {}) : {}
    homeOrder.value = Array.isArray(data.homeOrder) ? data.homeOrder.map(String) : []
  })
  ```
- **관리자 Tab 1 이 저장한 그 필드 그대로 참조** ✓

### 2-2. 정렬 대상 = `baseFiltered` (`:1893-1913`)
```js
const okExpose   = exposedHere(s)      // exposure.dashboard === true (PR #125)
const okApproved = isApproved(s)
const okPeriod   = isActiveAd(s)
const okT/okM/okQ/okNear
return okExpose && okApproved && okPeriod && okT && okM && okQ && okNear
```

**★ 관리자 Tab 1 (`approvedStores`) 대비 좁은 subset**:
- `exposedHere` 필터 추가 → **`exposure.dashboard === true` 인 가게만**
- `isActiveAd` 필터 추가 → 광고 기간 통과만
- 카테고리/매크로/검색/근처 필터

### 2-3. `filtered` computed 정렬 (`:1917-1937`)
```js
const filtered = computed(()=>{
  const base = baseFiltered()
  if (near.value.enabled){ /* 거리순 (dead code — near.enabled 항상 false) */ }
  if (!homeOrder.value.length) return base
  const pos = new Map(homeOrder.value.map((id,idx)=>[String(id), idx]))
  return base.slice().sort((a,b)=>{
    const ai = pos.has(String(a.id)) ? pos.get(String(a.id)) : Infinity
    const bi = pos.has(String(b.id)) ? pos.get(String(b.id)) : Infinity
    if (ai !== bi) return ai - bi
    return 0
  })
})
```

**★ Tab 1 과 100% 동일 로직**:
- `homeOrder` 인덱스 순 정렬
- 없는 항목 → Infinity 폴백
- 폴백 시 `return 0` → 원본 순서 유지

### 2-4. 렌더: `filtered.slice(0, 20)` (`:91`)
```html
<article v-for="s in filtered.slice(0, 20)" ... >
```
- 상위 **20개만** 표시

## 3. 필드/로직 일치 검증 매트릭스

| 항목 | 관리자 Tab 1 (`orderedApproved`) | 사용자 MainPage (`filtered`) |
|---|---|---|

→ **필드/알고리즘 100% 동일**. 차이는 **정렬 대상 범위** 와 **표시 개수**.

## 4. 불일치 원인 후보 분석

### 후보 A: 필드/알고리즘 불일치 [× 배제]
- 검증 §3 → 100% 동일
- 배제

### 후보 B: 신규 승인 가게 폴백 순서 [× 배제]
- Tab 1 과 MainPage 모두 `homeOrder` 에 없으면 `Infinity → return 0 → 원본 (approvedStores/baseFiltered) 순서`
- 원본은 stores 쿼리 `orderBy('updatedAt', 'desc')` (`MainPage.vue:1196`) 순서
- Tab 1: `approvedStores.slice().sort(...)` 는 원본 배열 참조 유지
- MainPage: `baseFiltered().slice().sort(...)` 도 원본 유지
- **양쪽 동일 폴백** → 배제

### 후보 C: 관리자가 드래그만 하고 "저장" 안 함 [★ 매우 유력]
- Tab 1 `reorderApproved` 는 **로컬 `homeOrder.value` 만 갱신** (`:517`)
- Firestore 저장은 **"저장" 버튼 클릭 필수**
- 관리자가 저장 잊고 새로고침 or 다른 탭 이동 → 로컬 잃음 → 서버는 옛 순서 유지
- **MainPage 는 저장된 값 참조** → 관리자 화면상 순서 ≠ MainPage 순서
- **확정 방법**:
  1. Firebase Console → `config/marketing.homeOrder` 배열 확인
  2. Tab 1 화면상 순서와 배열 순서 비교
  3. 다르면 → 후보 C 확정 → 관리자에게 "저장 눌러 주세요" 안내

### 후보 D: Tab 1 (승인 전체) vs MainPage (dashboard subset) 시각 착시 [★ 유력]
- Tab 1 `approvedStores` = 승인된 모든 가게 (dashboard=false 포함)
- MainPage `baseFiltered` = **dashboard=true 만**
- 예시:
  ```
  Tab 1 (관리자 화면):
  1위  A (dashboard=T)
  2위  B (dashboard=F)  ← 관리자만 보임
  3위  C (dashboard=T)
  4위  D (dashboard=F)  ← 관리자만 보임
  5위  E (dashboard=T)

  MainPage (사용자 현황판):
  1위  A
  2위  C  (관리자 화면에선 3위였음)
  3위  E  (관리자 화면에선 5위였음)
  ```
- **상대 순서는 유지** (A → C → E 순)
- 관리자가 "3위" 라고 매긴 게 사용자 눈엔 "2위" 로 보임 → 사용자 인식으로는 "순번이 다름"
- **실제 데이터는 정합** — dashboard=false 인 B/D 를 사용자에게 안 보여주는 게 사용자 목표
- 해결: Tab 1 에 "현황판에서는 몇 위" 힌트 표시 (UX 개선) 또는 dashboard=true 만 필터링해 순번 표시

### 후보 E: 20개 슬라이스 [× 부분적, 20위 이상만 영향]
- MainPage `filtered.slice(0, 20)` — 상위 20개만
- Tab 1 는 slice 없음 (전체 리스트)
- 21번째 이하 관리자 순번은 현황판에 안 뜸
- 상위 20개 안에서는 무관 → 불일치의 주 원인 아님

### 후보 F: 다른 순서 필드 혼동 [보조 가능성]
- **`config/marketing.topRanks`** (StoreFinder Top5 순위) — 완전 별개
- **`config/marketing.partnerOrder`** (PartnersPage 순위) — 별개
- **`config/marketing.homeOrder`** (본 진단 대상) — 현황판 순서
- **관리자가 Top5 페이지에서 매긴 순번을 현황판 순번으로 오해했다면** 완전 다름
- 확인: Tab 1 (현황판 순서) 로 매긴 게 맞는지, Top5 페이지 (`/admin/top5`) 에서 매긴 건 아닌지

### 후보 G: `homeOrder` 배열이 stale (구버전 저장) [보조]
- 어떤 관리자가 예전에 순서 저장 → 그 후 신규 가게 승인 여러 개 → 신규 가게는 배열에 없음 → 뒤로 (updatedAt desc 순)
- 관리자가 최근 Tab 1 진입 → 화면상 [예전 순서 + 신규 updatedAt desc] 자연스러워 보임
- 저장 안 하면 → Firestore 는 옛 배열만 유지
- 새 관리자 진입 or 다른 브라우저에서 볼 때 순서 다를 수 있음 (로컬 seed 없어)
- 결국 **저장 안 함** 문제 (후보 C 파생)

## 7. 참고 — Tab 1 vs MainPage 정렬 흐름 요약

```

  approvedStores (승인 전체)
    ↓ orderedApproved computed (homeOrder 순 sort)
    ↓ 화면 표시 (드래그 UI)
    ↓ [드래그] → reorderApproved → homeOrder.value 로컬 갱신

    ↓ 화면 표시
  config/marketing.homeOrder (subHomeOrder onSnapshot 실시간 구독)
```

## 8. 결론

- **관리자와 사용자가 같은 필드 (`config/marketing.homeOrder`) + 같은 알고리즘 사용** → 필드 자체는 불일치 아님
- **차이는 (1) 대상 범위** (Tab 1 = 승인 전체 / MainPage = dashboard subset), **(2) 표시 개수** (Tab 1 전체 / MainPage 20개)
- **가장 유력한 원인 = 후보 C (관리자가 드래그만 하고 "저장" 안 함)** — 로컬만 바뀌고 Firestore 미반영
- **두 번째 유력 = 후보 D (dashboard subset 착시)** — 데이터는 정합이지만 사용자 인식이 "다르다"
- **확정 방법**: Firebase Console → `config/marketing.homeOrder` 배열 확인 (Tab 1 화면 순서와 비교)
- **변경 0**: 본 문서는 진단만. 코드/룰/PR/배포 없음
