**날짜**: 2026-06-18

**전제**: 진단 전용. 코드/룰 수정·PR·배포 없음.

## 1. 로그인 후 역할 분기 흐름도

### 1-1. 진입 URL 별 처리

| URL | 컴포넌트 | 후 처리 |
|---|---|---|
| `/` | (router 가드만) | `role==='platform'` → `/admin/dashboard` <br/> `role==='biz'` → `/biz/dashboard` <br/> 그 외 → `/biz/login?next=/admin/dashboard` |
| `/biz/login` | `BizLoginPage` (`src/pages/admin/BizLoginPage.vue`) | **업체+관리자 공용 진입점** |

### 1-2. BizLoginPage 의 분기 (`BizLoginPage.vue:103-135`)

```js
async function onLogin() {

  const role = await resolveRole(cred.user)

}
```

- 그 외 → `null`
- **`getDoc` 실패 시** `console.warn` → `null` 반환

### 1-4. router 가드 (`src/router/admin.js:145-192`)

```js
router.beforeEach(async (to) => {
  if (to.name === 'adminLogin' || to.name === 'bizLogin') return true
  await authReady()                          // 첫 onAuthStateChanged 1회 대기
  const user = getAuth().currentUser
  if (user && cachedRoleUid && cachedRoleUid !== user.uid) invalidateRoleCache()
  if (!user) invalidateRoleCache()
  const role = user ? await getUserRole(user) : null

  if (to.name === 'root') { /* role 따라 분기 */ }
  if (needsAdmin) {
    if (!user)                 return { name:'bizLogin', query:{next:to.fullPath} }
    if (role !== 'platform') {
      if (role === 'biz')      return { name:'bizDashboard' }
      await auth.signOut(); invalidateRoleCache()
      return { name:'bizLogin', query:{next:to.fullPath} }
    }
  }
  if (needsBiz) {
    if (!user)                 return { name:'bizLogin', query:{next:to.fullPath} }
    if (role !== 'platform' && role !== 'biz') {
      await auth.signOut(); invalidateRoleCache()
      return { name:'bizLogin', query:{next:to.fullPath} }
    }
  }
})
```

`getUserRole(user)` (`:112-137`):
- `cachedRoleUid === user.uid && cachedRole !== null` → 캐시 hit (단, **null 캐시는 미스 → 매번 재조회**)
- `email === 'gangtalk815@gmail.com'` → `'platform'`
- `users/{uid}.type === 'company' && accountKind === 'storeOwner'` → `'biz'`
- `getDoc` 실패 시 `console.warn` → `null`

## 2. "관리자로 로그인하라" 메시지 — 정확한 출처

### 2-1. 코드 grep 으로 확인된 후보 메시지

| 메시지 | 위치 | 조건 |
|---|---|---|
| **"관리자 계정이 아닙니다."** | `AdminLoginPage.vue:92` | `/login` 에서 업체 이메일로 로그인 시 |
| **"업체 계정이 아닙니다. 관리자에게 문의해 주세요."** | `BizLoginPage.vue:121` | `/biz/login` 에서 로그인은 됐지만 `resolveRole` 가 `null` 반환 시 |

→ **사용자가 본 "관리자 화면으로 로그인하라"** 는 둘 중 하나의 변형 또는 의역으로 추정. **가장 유력한 시나리오 2가지**:

### 2-2. 시나리오 A — 업체가 잘못된 URL `/login` 으로 진입

- 옛 북마크 / 옛 안내 메일 / SNS 링크 등으로 `/login` (AdminLogin) 직접 진입
- 업체 이메일로 로그인 → **"관리자 계정이 아닙니다."** 노출 + 강제 로그아웃
- 사용자 입장에서 "관리자 화면이라네, 다른 URL 로 가야 하나?" → "관리자 화면으로 로그인하라" 로 의역 가능
- **사실은 정상 동작이지만 진입점이 잘못된 케이스**

### 2-3. 시나리오 B — `resolveRole` 의 `users/{uid}` 조회 실패

- BizLoginPage 의 `resolveRole(cred.user)` 가 `getDoc(users/{uid})` 호출 (`:78`)
- **권한 에러 / 네트워크 에러 / 토큰 만료 race** 등으로 `getDoc` 가 예외 → catch → `null` 반환
- → **"업체 계정이 아닙니다. 관리자에게 문의해 주세요."**
- 사용자 입장에서 "관리자에게 문의하라" → "관리자 화면으로 로그인하라" 로 의역 가능

**룰 재확인** (`firestore.rules:67-70`):
```
match /users/{uid} {
  allow read: if isOwner(uid) || isAdmin();
  ...
}
```
- `isOwner(uid)` = `signedIn() && request.auth.uid == uid` → **자기 자신 doc 은 read 가능**
- 룰 자체는 정상. 따라서 **시나리오 B 발생 시 원인은 룰이 아니라 "토큰 만료 / signedIn() 일시 false / 네트워크 race"**

### 2-4. 시나리오 C — `users/{uid}` 문서 자체가 없거나 필드 누락

- `createBizAccount` Cloud Function (`functions/index.js`) 가 `users/{uid}` 에 `type:'company', accountKind:'storeOwner'` 를 set 함 — 정상 생성 시 문제 없음
- **단**: 관리자가 Firebase Auth Console 에서 수동으로 사용자만 만들고 `users/{uid}` 를 만들지 않았다면 → `snap.exists() === false` → `resolveRole === null` → "업체 계정이 아닙니다."
- 또는 `type`/`accountKind` 값이 다른 케이스 (예: 옛 데이터 `type:'business'`) → 동일하게 `null`

## 3. "시간 지나면 막힘" — 원인 추정 (파일:라인)

### 3-1. 핵심 의심 1 — Firebase Auth 토큰 갱신 race

- Firebase Auth 의 ID 토큰은 **1시간** 만료. SDK 가 백그라운드에서 자동 갱신
- **자동 갱신 실패** 시 (네트워크 끊김, 리프레시 토큰 만료) `auth.currentUser` 는 유지되지만 후속 Firestore 호출이 권한 에러
- 영향:
  - `router/admin.js:122 getDoc(users/{uid})` 실패 → `role=null` → 가드가 `bizLogin` 으로 강제
  - `AdminLayout.vue:97 getDoc(users/{uid})` 실패 → `role=null` → 사이드바 메뉴 빈 상태 (`menus.value = []`)
  - `BizDashboardPage` 의 `stores where ownerId==uid` 구독도 동일 실패 가능

### 3-2. 핵심 의심 2 — `authReady()` 의 1회성 promise

`router/admin.js:92-103`:
```js
let authReadyPromise = null
function authReady() {
  if (authReadyPromise) return authReadyPromise
  authReadyPromise = new Promise(resolve => {
    const unsub = onAuthStateChanged(getAuth(), () => { unsub(); resolve(getAuth().currentUser) })
  })
  return authReadyPromise
}
```
- 모듈 스코프 promise — 한 번 resolve 되면 영구 메모이즈
- **이후 router navigation 시 `await authReady()` 는 즉시 통과 → `auth.currentUser` 를 그 시점 값으로 읽음**
- 토큰 갱신/네트워크 race 로 `auth.currentUser` 가 **일시적으로 null** 인 시점에 navigation 발생 시:
  - `:157 if (!user) invalidateRoleCache()` → 캐시 무효화
  - `:159 role = null`
  - `:172 if (!user) return { name:'bizLogin', query:{next:to.fullPath} }` → **강제 로그인 페이지**
- 사용자 입장: 멀쩡히 로그인됐었는데 갑자기 로그인 화면으로 튕김 → "막힘"

### 3-3. 핵심 의심 3 — `resolveRole` 4곳 중복 + 결과 불일치

| 위치 | 캐시 | 함수명 |
|---|---|---|
| `router/admin.js:112` | `cachedRole` 모듈 스코프 (uid 별) | `getUserRole` |
| `BizLoginPage.vue:73` | 없음 | `resolveRole` |
| `AdminLayout.vue:92` | 없음 | `resolveRole` |
| `AdminLoginPage.vue` | (email 직접 비교) | — |

- 같은 사용자에 대해 4번 각각 `getDoc(users/{uid})` — 한 곳이라도 실패하면 다른 곳과 결과 불일치
- 특히 **AdminLayout 의 onAuthStateChanged 콜백** (`:107-110`):
  ```js
  unsubAuth = onAuthStateChanged(auth, async (u) => {
    currentEmail.value = u?.email || ''
    role.value = await resolveRole(u)
  })
  ```
  - `u === null` 발화 시 → `role.value = null` → 사이드바 메뉴 사라짐
  - SDK 가 토큰 갱신 중 일시 null 발화 가능 (드물지만 발생)
  - 사용자가 그 시점에 메뉴 클릭하려 하면 "메뉴 없음 / 막힘" 으로 인지

### 3-4. 핵심 의심 4 — `cachedRole` 의 stale 가능성

`router/admin.js:109-137`:
- `cachedRole = 'biz'` 로 한 번 캐시되면 동일 uid 면 영구 hit
- **`users/{uid}` 문서가 외부에서 삭제되거나 `accountKind` 가 변경돼도 캐시는 갱신 안 됨**
- 캐시 무효화 트리거:
  - uid 변경 (`:154`)
  - user=null (`:157`)
  - `invalidateRoleCache()` 수동 호출 (`AdminLayout.vue:138` 로그아웃 시)
- → 일반 운영에서는 무해. 단 관리자가 업체 권한을 박탈했는데 업체 세션이 살아있으면 클라이언트는 여전히 biz 로 인식 (서버 룰이 막아주긴 함)

### 3-5. 핵심 의심 5 — `IS_ADMIN_BUILD` 의 AppCheck 미초기화

CLAUDE.md 작업 로그 (2026-06-16 admin CORS+AppCheck 수정) 참조:
- admin 빌드는 `src/firebase.js` 에서 AppCheck 초기화 스킵
- 단 firestore.rules 에 `request.auth` 만 사용하므로 영향 없음
- → **현 시점에서는 영향 없음**. 단 향후 룰에 `request.app` 검증이 추가되면 영구 거부 가능

## 6. 결론

### 6-1. 역할 분기 흐름 — 정상 동작
- 코드/룰 모두 정상 (`PLATFORM_EMAIL` 비교 → `users/{uid}` doc 조회 순)
- `/biz/login` 이 업체+관리자 공용 진입점, `/login` 은 관리자 전용
- 가드가 `requiresAdmin` / `requiresBiz` 로 적절히 분기

### 6-2. "관리자로 로그인하라" 메시지의 가장 유력한 출처
1. **시나리오 A** — 업체가 `/login` (AdminLogin) URL 로 직접 진입 → **"관리자 계정이 아닙니다."** 메시지
2. **시나리오 B** — `BizLoginPage.resolveRole` 의 `getDoc(users/{uid})` 가 권한/네트워크 race 로 실패 → **"업체 계정이 아닙니다."** 메시지

### 6-3. "시간 지나면 막힘" 의 가장 유력한 원인
1. **`router/admin.js:92-103 authReady()` 가 모듈 스코프 1회 promise** — 토큰 갱신 race 시 `auth.currentUser` 일시 null → 강제 `bizLogin` redirect
2. **`AdminLayout.vue:107-110 onAuthStateChanged` 가 user=null 발화** → `role.value = null` → 사이드바 메뉴 사라짐
3. **`router/admin.js:122 getDoc(users/{uid})` 가 토큰 만료/네트워크 race 로 실패** → `cachedRole=null` → 매번 재조회 시도하지만 동일 실패 → 사용자 체감 "막힘"

### 6-4. 사용자 운영 확인 액션 (코드 변경 없이)
- (A) 업체 사용자에게 **`https://gangtalk815.com/biz/login` URL 만 안내** (옛 `/login` 링크 폐기)
- (B) `users/{uid}` 문서가 모든 업체 계정에 대해 정상 생성됐는지 Firebase Console 에서 확인 (`type='company'`, `accountKind='storeOwner'`)
- (C) 사용자가 "막힘" 발생 시 브라우저 콘솔에 다음 출력 확인:
  ```

  ```
  → 어떤 단계에서 실패하는지 (권한 / 네트워크 / 토큰 만료) 식별
- (D) 토큰 만료 race 라면 **새로고침 (F5) 으로 해결됨** — 사용자에게 우선 안내
