## 1. Cloud Function 입출력 확정

### 1-1. `createBizAccount` (`functions/index.js:2447-2535`)

**입력**:
```js
{
  email: string,        // 필수, 정규식 검증
  password: string,     // 필수, 6자 이상
  storeName: string,    // 필수
  storeId?: string,     // 선택 — 있으면 stores 연결까지
}
```

**처리 (3단계, sequential)**:
1. `admin.auth().createUser({ email, password, displayName: storeName })` → Auth user 생성
2. `users/{uid}.set({ type:'company', accountKind:'storeOwner', profile, company, createdBy:'admin', ... })` → Firestore users doc
3. **storeId 가 있으면** `stores/{storeId}.set({ ownerId: uid, ownerEmail, updatedAt }, { merge:true })` → 연결

**반환**: `{ ok: true, uid, email }`

**에러 처리 매트릭스**:
| 단계 | 실패 시 | 영향 | 복구 |
|---|---|---|---|
| 1 (Auth) | `email-already-exists` → throw `already-exists` | 변경 0 | 다른 이메일 또는 기존 계정 연결 |
| 1 (Auth) | `invalid-password` → throw `invalid-argument` | 변경 0 | 비번 재입력 |
| 1 (Auth) | 기타 → throw `internal` | 변경 0 | 재시도 |
| 2 (Firestore users) | throw `internal` | ⚠️ **Auth user 잔존 (고아)** | UI 안내 + Firebase Console 수동 삭제 또는 deleteBizAccount 호출 |
| 3 (stores 연결) | `console.warn` 만, throw 없음 (`:529`) | Auth+users 정상, stores 미연결 | linkStoreToBiz 단독 재호출 |

### 1-2. `linkStoreToBiz` (`functions/index.js:2572-2598`)

**입력**:
```js
{
  storeId: string,        // 필수
  bizUid?: string,        // bizUid 또는 bizEmail 중 하나 이상
  bizEmail?: string,
}
```

**처리**: `stores/{storeId}.set({ ownerId: bizUid?, ownerEmail: bizEmail?, updatedAt }, { merge:true })`

**반환**: `{ ok: true }`

**에러 처리**:
- `storeId` 없으면 `invalid-argument`
- `bizUid`/`bizEmail` 둘 다 없으면 `invalid-argument`
- Firestore write 실패 → `internal`

## 2. 안전한 조합 흐름

### 2-1. 경우 1 — 신규 업체 계정 생성 + 업소 등록 (옵션 A, 권장)

```
[클라이언트]                                    [서버]

1. storeId = doc(collection(fbDb, 'stores')).id  (auto-id 미리 발급)
   └─ 네트워크 0

2. setDoc(stores/{storeId}, {
     ...form,                                   // 폼 입력 (StoreFormFields)
     ownerId: ADMIN_UID,                        // ★ admin uid (rules:111 통과)
     ownerEmail: ADMIN_EMAIL,
     applyStatus: 'pending',                    // 또는 'approved' (즉시 노출 체크)
     approved: false,                           // 또는 true
     'exposure.gangtalk': false,                // 또는 true
     createdAt: serverTimestamp(),
     updatedAt: serverTimestamp(),
   })
   └─ Firestore write 1                        ─→ stores/{storeId} 생성 (admin 소유)

3. fnCreateBiz({ email, password, storeName, storeId })  ─→ Cloud Function 호출
                                                              ├─ Auth user 생성
                                                              ├─ users/{uid} 생성
                                                              └─ stores/{storeId}.ownerId/ownerEmail 갱신 (admin → 업체)

4. alert("업체 계정 생성 완료\n이메일: {email}\n임시 비번: {password}\n업체에 전달하세요.")
```

**장점**:
- 2회 네트워크 호출 (write + Cloud Function)
- `createBizAccount` 내부 단계 3 (stores 연결) 이 자동 처리 — linkStoreToBiz 별도 호출 불필요
- 코드 변경 적음

**부분 실패 시나리오**:
- 단계 2 실패 → 변경 0. UI 에 "업소 생성 실패" 안내
- 단계 3 실패 (email-already-exists) → stores 가 admin uid 로 잔존. UI 안내: "이메일 중복 — 다른 이메일 사용 또는 기존 업체 계정 연결로 전환"
- 단계 3 Auth 성공 + Firestore users 실패 → **고아 Auth + stores 가 admin 잔존**. UI: "Auth 계정만 생성됨. 관리자가 Firebase Console 정리 또는 deleteBizAccount 호출"
- 단계 3 의 stores 연결 부분 실패 (console.warn) → Auth+users 정상, stores 가 admin 잔존. UI: "업소 연결 실패. BizAccountsPage 에서 수동 연결"

### 2-2. 경우 1 — 옵션 B (3-step, 비권장)

```
1. storeId 발급
2. setDoc(stores, { ownerId: ADMIN_UID, ... })
3. fnCreateBiz({ email, password, storeName })       // storeId 안 넘김
4. fnLinkStore({ storeId, bizUid, bizEmail })        // 명시적 양도
```

**비교**:
- 3회 네트워크 호출 → 옵션 A 보다 0.3~0.5초 느림
- 단계 분리로 디버깅 용이
- 단계 4 실패 시 stores 가 admin 잔존 — 옵션 A 와 동일 결과
- **권장 안 함** — 옵션 A 가 단순 + 빠름

### 2-3. 경우 2 — 기존 업체 연결

```
1. storeId 발급
2. setDoc(stores/{storeId}, {
     ...form,
     ownerId: ADMIN_UID,
     ownerEmail: ADMIN_EMAIL,
     applyStatus, approved, exposure,
     createdAt, updatedAt
   })
3. fnLinkStore({
     storeId,
     bizUid: selectedBiz.value.uid,
     bizEmail: selectedBiz.value.email,
   })
4. alert("업소 등록 완료. {업체명} 에 연결되었습니다.")
```

**부분 실패**:
- 단계 2 실패 → 변경 0
- 단계 3 실패 → stores 가 admin uid 로 잔존. UI: "연결 실패 — BizAccountsPage 에서 수동 연결"

### 2-4. 경우 3 — 미연결 (나중 연결)

```
1. storeId 발급
2. setDoc(stores/{storeId}, { ownerId: ADMIN_UID, ... })
3. alert("업소 등록 완료. 나중에 BizAccountsPage 에서 업체에 연결할 수 있습니다.")
```

**잔존 상태**:
- `ownerId = admin uid` → BizMyStorePage 에서 admin 로그인 시 보이지만 admin 은 `/admin/*` 만 사용
- 사용자 화면: applyStatus='pending' 면 미노출, 'approved' 면 노출
- UI 권장: 카드에 "미연결" 뱃지 표시 (StoresManagePage Tab 1)

## 5. 기존 BizAccountsPage 와의 관계

### 5-1. 충돌 여부 — 없음

| 항목 | BizAccountsPage 의 "새 업체 계정 생성" | 본 진단의 StoresManagePage 모달 |
|---|---|---|
| Cloud Function | `fnCreateBiz({ email, password, storeName })` | `fnCreateBiz({ email, password, storeName, storeId })` |
| storeId | 안 넘김 | **넘김 (미리 발급한 새 store ID)** |
| 결과 | Auth + users 만 | + stores 연결까지 |
| 진입점 | BizAccountsPage 카드 헤더 "+ 새 업체 계정" | StoresManagePage 의 "+ 새 업소 등록" 모달 안 |
| 사용 시점 | 계정만 먼저 만들고 나중에 업소/연결 | 업소 + 계정 동시 |

→ **공존 가능** — 같은 함수, 입력만 다름. 충돌 없음

### 5-2. 흐름 비교

**기존 흐름 (BizAccountsPage)**:
- (1) 관리자가 새 업체 계정 생성 (storeId 없이)
- (2) 업체가 BizMyStorePage 에서 자가등록 → 본인 uid 의 stores 생성
- (3) 또는 관리자가 BizAccountsPage 의 "업소 연결" 모달로 기존 stores 연결

**신규 흐름 (StoresManagePage 모달, 본 진단)**:
- (1) 관리자가 한 번에 업소 + 계정 + 연결
- 빠른 셋업 — 신규 업체 입점 시 사용

→ 두 진입점 모두 유지. 사용자 시나리오에 따라 선택

### 5-3. BizAccountsPage 의 "업소 연결" 버튼 — 유지

본 PR 의 모달과 별개:
- BizAccountsPage 의 "업소 연결" 모달은 **기존 업체에 기존 stores 연결** (link)
- 본 PR 모달의 (b) 옵션은 **신규 stores 를 기존 업체에 연결** (create + link)
- 동작은 같은 `linkStoreToBiz` 함수, 진입점/맥락만 다름

→ 둘 다 유지 (운영 유연성)

## 7. 주의점

### 7-1. 비밀번호 보안

- 임시 비번 표시 화면은 **클립보드 복사 후 즉시 닫기** 안내
- 화면 닫으면 다시 못 봄 — Firebase Auth 는 비번 read 불가
- 분실 시: BizAccountsPage 의 "비번 재설정" (resetBizPassword)

### 7-2. 이메일 중복 처리

- `email-already-exists` 발생 시:
  - 옵션 1: 사용자에게 다른 이메일 입력 권유
  - 옵션 2: "기존 업체 계정 연결" 라디오로 자동 전환 + 그 이메일의 업체 자동 선택
  - 옵션 3: stores 자동 롤백 (방금 만든 stores 삭제) — 안전하지만 데이터 손실
- 권장: 옵션 1 (UX 단순) + stores 잔존 시 안내 ("업소는 생성됐습니다. 다른 이메일로 다시 시도하세요.")

### 7-3. stores create 룰 우회 없음

- `firestore.rules:111-112 stores/{id}.create: ownerId == auth.uid`
- 관리자도 본인 uid 로만 create. 다른 업체 uid 로 바로 create 불가
- → 본 진단의 옵션 A 가 admin uid 로 일단 create → linkStoreToBiz 로 양도
- **룰 변경 없이도 작동**

### 7-4. 즉시 노출 체크박스

- default = OFF (안전)
- ON 시 `applyStatus='approved', approved=true, exposure.gangtalk=true`
- 사용자 화면 즉시 노출 — 관리자 의도 명시 필요

### 7-5. 트랜잭션성 부재

- stores create (Firestore rules) + createBizAccount (Cloud Function) 은 **개별 트랜잭션**
- 부분 실패 시 UI 가 명확히 안내
- 더 강한 트랜잭션 보장 원하면 단일 Cloud Function 으로 통합 (옵션 D, 별도 PR)

### 7-6. users dropdown 권한

- `users where type='company'` collection-level query → admin 만 가능
- `firestore.rules:67-70 users/{uid}.allow read: if isOwner(uid) || isAdmin()`
- 출시전 점검 H-2 의 `admins/{uid}` 부트스트랩 완료 후 작동
- 부트스트랩 없으면 "권한 부족" 에러 (BizAccountsPage 와 같은 증상)

### 7-7. 옛 BizAccountsPage 흐름 유지

- BizAccountsPage 의 "새 업체 계정 생성" / "업소 연결" 모달 모두 유지
- 신규 흐름은 **추가 진입점**

### 7-8. ChatBiz 및 rooms_biz 연동

- 신규 등록 store 도 ChatBiz 진입 가능 (storeId 그대로)
- `rooms_biz/{storeId}` doc 신규 생성됨 (ChatBiz.ensureRoom)
- BizMetrics / PR #109 saveAllMetrics 도 정상 동작
