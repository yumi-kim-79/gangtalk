## 2. 업소-업체 연결 기존 메커니즘 — 완비

### 2-1. Cloud Function `linkStoreToBiz` (`functions/index.js:2572-2598`)

```js
exports.linkStoreToBiz = onCall({ cors: ADMIN_CORS }, async (req) => {
  assertCallerIsAdmin(req);                                        // ← 관리자만

  const storeId = safeStr(req?.data?.storeId);
  const bizUid = safeStr(req?.data?.bizUid);
  const bizEmail = safeStr(req?.data?.bizEmail).toLowerCase();

  if (!storeId) throw new HttpsError("invalid-argument", "storeId 가 필요합니다.");
  if (!bizUid && !bizEmail) {
    throw new HttpsError("invalid-argument", "bizUid 또는 bizEmail 중 하나는 필요합니다.");
  }

  const patch = { updatedAt: serverTimestamp() };
  if (bizUid) patch.ownerId = bizUid;
  if (bizEmail) patch.ownerEmail = bizEmail;

  await db.collection("stores").doc(storeId).set(patch, { merge: true });
  return { ok: true };
});
```

**입력**: `{ storeId, bizUid, bizEmail }`
**동작**: `stores/{storeId}` 의 ownerId / ownerEmail 만 set (merge)
**호출 권한**: 관리자만 (`assertCallerIsAdmin`)
**룰 우회**: Admin SDK 라 firestore.rules 우회 — admin uid 가 자기 게 아닌 stores 도 update 가능

→ **관리자가 신규 등록 후 업체에게 양도하는 데 그대로 사용 가능**.

## 3. firestore.rules 제약 분석

### 3-1. stores `allow create` (`:111-112`)

```
allow create: if signedIn()
           && request.resource.data.ownerId == request.auth.uid;
```

**의미**:
- 인증된 사용자가 본인 uid 로만 ownerId 세팅 가능
- 관리자도 본인 uid 로만 create 가능 (다른 업체 uid 로 바로 create 불가)
- **isAdmin 분기 없음** — 관리자 별도 우대 없음

**제약**: 관리자가 처음부터 `ownerId: bizUid` 로 setDoc 하면 **룰 차단**.

### 3-2. stores `allow update` (`:120-132`)

```
allow update: if signedIn() && (
  isAdmin()
  || ( 본인 owner 분기, ownerId/ownerEmail 변경 금지 )
  || changesAreOnly(['rating', 'ratingSum', 'ratingCount', 'updatedAt'])
);
```

**의미**:
- `isAdmin()` 통과 시 모든 필드 변경 가능 (ownerId 포함)
- 즉 admin 이 클라이언트에서 직접 `updateDoc(stores, { ownerId: bizUid })` 도 가능

### 3-3. 2가지 접근 방식

#### 접근 A — 룰 변경 없이 (권장)

Phase 1: 관리자가 자기 uid 로 create
```js
await setDoc(doc(fbDb, 'stores', newId), {
  ...payload,
  ownerId: ADMIN_UID,        // ← 관리자 본인 uid (룰 통과)
  ownerEmail: ADMIN_EMAIL,
  applyStatus: 'pending',    // 또는 'approved'
})
```

Phase 2 (업체 선택 시): 즉시 linkStoreToBiz 호출
```js
await fnLinkStore({
  storeId: newId,
  bizUid: selectedBizUid,
  bizEmail: selectedBizEmail,
})
```

**장점**: 룰 변경 0. 검증된 함수 재활용
**단점**: 2회 write (네트워크 조금 느림. 0.5초 정도)

#### 접근 B — 룰 수정 (대안)

stores `create` 룰에 isAdmin 분기 추가:
```
allow create: if (signedIn() && request.resource.data.ownerId == request.auth.uid)
           || isAdmin();
```

→ 관리자가 처음부터 다른 업체 uid 로 create 가능. 1회 write.

**장점**: 더 빠름
**단점**: 룰 변경 + 배포 필요. 출시 직전 비권장

→ **접근 A 권장** (룰 변경 0).

## 5. 자가등록과의 공존 검증

### 5-1. 같은 stores 컬렉션 — 데이터 분리 없음

자가등록 / 관리자 등록 모두 `stores/{auto-id}` 에 같은 형식 payload 저장. doc 구조 동일.

### 5-2. ownerId 시나리오별 BizMyStorePage 동작

| ownerId 상태 | BizMyStorePage 에서 보이는 사용자 |
|---|---|
| `admin_uid` (관리자 등록 후 미연결) | 관리자 로그인 시 보임 (하지만 관리자는 BizMyStorePage 안 봄 — `/admin/*` 가 우선) |
| `biz_uid_A` (linkStoreToBiz 후) | 업체 A 로그인 시 BizMyStorePage 에 본인 가게로 표시. 수정 가능 |
| `biz_uid_B` 로 변경 (재연결) | 업체 B 가 보임, 업체 A 는 안 보임. 양도 자연스러움 |

### 5-3. 룰 통과 검증 — 업체가 등록 후 자기 store 수정 가능?

stores update 룰 (`:120-132`):
```
allow update: if signedIn() && (
  isAdmin()
  || ( resource.data.ownerId == request.auth.uid
       && request.resource.data.ownerId == resource.data.ownerId
       && (... ownerEmail 변경 금지) )
  || changesAreOnly(['rating', ...])
);
```

- `linkStoreToBiz` 후 `ownerId = biz_uid_A`
- 업체 A 가 BizMyStorePage 에서 update 시 → `resource.data.ownerId == auth.uid` 통과 ✓
- 단 ownerId/ownerEmail 변경 금지 분기는 그대로 유지 (양도 차단)

→ ✅ **자가등록과 동일하게 작동**. 회귀 0.

### 5-4. MainPage 노출 흐름

`MainPage.isApproved` 가 `approved===true || applyStatus==='approved'` 체크 + `exposure.gangtalk` 필터.
- **즉시 승인 + 노출**: 관리자 모달의 체크박스로 한 번에 처리
- **승인 대기**: Tab 3 의 기존 `approveStore` (`:610`) 로 처리 → 변경 0

## 7. 주의점

### 7-1. ownerId 잔존 케이스 (admin 등록 후 미연결)

- 관리자가 store 등록 + 업체 미연결 → `ownerId = admin uid` 잔존
- 의미: 그 store 는 admin 이 "소유"한 것. BizAccountsPage 에서 나중에 연결 가능
- BizMyStorePage `where ownerId==uid` 쿼리: admin 로그인 시 보임 (단 admin 은 `/admin/*` 만 봄 — 큰 문제 없음)
- 권장: UI 에 "미연결" 뱃지 표시 — 관리자가 한눈에 식별

### 7-2. 즉시 승인 + 노출의 의미

- 자가등록은 항상 `applyStatus:'pending', approved:false` — 사용자 화면 자동 미노출
- 관리자 등록은 **즉시 노출 체크 가능** — 빠른 운영 (예: Top5 에 넣을 store)
- 단 체크박스 default 는 선택 (안전한 default = 미체크 → pending → 별도 승인 클릭)

### 7-3. 카테고리 / 지역 (출근업소 키)

BizMyStorePage 의 옵션 그대로:
- 카테고리 9개: `hopper / point5 / ten / tenpro / onep / nrb / kara / bar / etc`
- 지역 4개: `강남 / 비강남 / 경기 / 인천`

partners (제휴처) 의 카테고리 (`ps/skin/beauty/nail/...`) 와 다름 — 혼용 금지.

### 7-4. PR #109 의 saveAllMetrics 가드 영향

- 그 후 Tab 2 "수동 지표 업데이트" 에 노출됨 (exposedStores 에 포함)
