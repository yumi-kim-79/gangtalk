# userSeq 카운터가 안 오르는 진짜 원인 진단

**날짜**: 2026-06-18
**범위**: 모든 신규 가입자가 추천코드 `prefix+'00001'` (seq=1) 을 받는 회귀
**전제**: 진단 전용. 코드/룰/함수 수정·PR·배포 없음.
**결론**: **카운터/룰/트랜잭션 자체는 정상**. 진짜 원인은 **`store/user.js me.init` 의 `else` 분기 (`:377-410`)** — `createUserWithEmailAndPassword` 직후 `onAuthStateChanged` 가 발화하면서 me.init 콜백이 `_fbSignupUser` 의 `runTransaction` **보다 먼저 실행**됨. me.init 의 else 분기는 `seq = 1` 하드코딩으로 users doc 을 자동 생성 → `_fbSignupUser` 트랜잭션 도달 시 `uSnap.exists()===true, myJoinSeq=1` → `already` 분기 → **counters 분기 영원히 도달 안 함**. 결과: `meta/counters.userSeq` 는 영원히 생성 안 되거나 0/1 에 머무름. 모든 신규 가입자가 `seq=1` → `prefix+'00001'` 받음.

---

## 1. 진짜 원인 (파일:라인)

### 1-1. `_fbSignupUser` 의 트랜잭션 — 정상 코드 (`store/user.js:453-530`)

```js
async _fbSignupUser({ email, password, nickname, refCode }) {
  ...
  const cred = await createUserWithEmailAndPassword(auth, email, password)  // ① auth 생성
  const uid  = cred.user.uid
  const userRef = doc(db, 'users', uid)
  const countersRef = doc(db, 'meta', 'counters')

  let seq = 0
  let myCode = ''

  await runTransaction(db, async (tx) => {                                  // ② 트랜잭션
    const cSnap = await tx.get(countersRef)
    const uSnap = await tx.get(userRef)

    const already = uSnap.exists() && Number(uSnap.get('myJoinSeq')) > 0
    if (already) {                                                          // ③ 여기로 빠짐
      seq = Number(uSnap.get('myJoinSeq')) || 1
      myCode = makeMyCodeV2(email, seq)
      return                                                                // ← counters 안 건드림
    }

    const base = cSnap.exists() ? Number(cSnap.get('userSeq')) || 0 : 0
    seq = base + 1
    if (!cSnap.exists()) {
      tx.set(countersRef, { userSeq: 1, updatedAt: serverTimestamp() })
    } else {
      tx.update(countersRef, { userSeq: seq, updatedAt: serverTimestamp() })  // ← 도달 안 함
    }
    ...
  })
}
```

→ `already` 분기로 빠지면 **counters 건드림 안 함**. `_fbSignupUser` 의 트랜잭션 자체는 정상이지만 `else` 의미 분기에 도달하지 못함.

### 1-2. **`me.init` 의 else 분기 — 진짜 범인** (`store/user.js:377-410`)

```js
} else {
  // (예외) 문서가 없을 때 최소 생성 — 이 경우도 V2 포맷 사용
  const seq = 1                                  // ← 하드코딩 1
  const myCode = makeMyCodeV2(u.email || '', seq)
  const nickname = u.displayName || ''
  ...
  data = {
    type: 'user',
    profile: { email: u.email || '', nickname, ... },
    points: 0,
    referral: { myCode, codeVersion: 2, refBy: null, refApplied: false },
    myJoinSeq: seq,             // ← 1
    myRefCode: myCode,          // ← 'prefix00001'
    myRefCreatedAt: serverTimestamp(),
    createdAt: Date.now(),
  }
  await setDoc(userRef, { ...data, createdAt: serverTimestamp(), updatedAt: serverTimestamp() })
}
```

- 주석에 "예외" 라고 표기됐지만 **매 신규 가입 시 발동**
- `seq=1` 하드코딩 → counters 무관하게 `myCode='prefix00001'`
- `setDoc` 로 users doc 즉시 생성 → `_fbSignupUser` 트랜잭션이 본 시점에 이미 존재

### 1-3. race 시점별 흐름 재구성

| t | 이벤트 | users/{uid} | meta/counters |
|---|---|---|---|
| 0 | AuthPage 가입 클릭 → `me.signupUser` → `me._fbSignupUser` | 없음 | 없음 |

| 2 | **Firebase Auth SDK 가 `onAuthStateChanged` 발화** | 없음 | 없음 |
| 3 | **me.init 콜백 시작** (`store/user.js:250`) | 없음 | 없음 |
| 4 | me.init: `await getDoc(userRef)` → `snap.exists()===false` | 없음 | 없음 |
| 5 | me.init else 분기 (`:377`): `seq=1` 하드코딩, `myCode='prefix00001'` | 없음 | 없음 |

→ 모든 신규 가입자가 `myJoinSeq=1, myRefCode='prefix00001'`. `meta/counters` 는 생성조차 안 됨.

## 2. firestore.rules — **정상**

`firestore.rules:334-349`:
```
match /meta/counters {
  allow read: if signedIn();
  allow create: if signedIn()
    && !exists(/databases/$(database)/documents/meta/counters)
    && (userSeq == 0 || userSeq == 1)
    && keys.hasOnly(['userSeq', 'updatedAt']);
  allow update: if signedIn()
    && request.resource.data.userSeq == resource.data.userSeq + 1
    && diff.changedKeys().hasOnly(['userSeq', 'updatedAt']);
}
```

- read: signedIn → 가입 직후 `auth.currentUser` 있으므로 OK
- create: doc 없을 때 + userSeq 0/1 → `_fbSignupUser` 의 `tx.set({ userSeq: 1, updatedAt: ... })` 통과
- update: 정확히 +1 + 키 hasOnly → `tx.update({ userSeq: seq, updatedAt: ... })` 통과

룰 자체는 정상. 단 §1 의 race 로 트랜잭션이 이 분기에 도달 못 함.

`users/{uid}` 룰:
```
match /users/{uid} {
  allow read: if isOwner(uid) || isAdmin();
  allow create, update, delete: if isOwner(uid) || isAdmin();
}
```
me.init 의 setDoc 도 정상 통과 (자기 자신 doc).

## 3. me.init else 분기가 매번 발동하는 이유

`createUserWithEmailAndPassword` 의 SDK 동작:
- Auth user 생성 즉시 SDK 가 내부 state 변경
- 등록된 `onAuthStateChanged` 콜백 발화 (microtask 큐)
- `await createUserWithEmailAndPassword` 의 resolve 와 거의 동시 (microtask 순서에 따라 다름)

`_fbSignupUser` 의 흐름:
```js
const cred = await createUserWithEmailAndPassword(...)  // ← 여기서 await 끝나는 그 시점에
                                                       //    onAuthStateChanged 콜백이 큐에 들어감
const uid = cred.user.uid
const userRef = doc(db, 'users', uid)
const countersRef = doc(db, 'meta', 'counters')
...
await runTransaction(db, async (tx) => {                // ← await 시작 — 이 사이에 me.init 콜백 실행
  ...
})
```

`await runTransaction` 시작 = JS 이벤트 루프 양보. 그 사이에 `onAuthStateChanged` 콜백이 실행 → me.init 의 `await getDoc(userRef)` → 새 user 라 `snap.exists()===false` → else 분기 → setDoc.

setDoc 완료 후에야 `_fbSignupUser` 의 runTransaction 진입 → already 분기.

이게 race 의 정확한 메커니즘. **SDK 동작에 의한 거의 결정론적 race** — 우연이 아니라 거의 매번 발동.

## 5. 고칠 방향

### 5-1. **단순 수정 — `me.init` 의 else 분기 제거** (가장 깔끔)

`store/user.js:377-410` 의 else 블록 제거. me.init 가 users doc 없으면 자동 생성하지 않고 그냥 `_ready = true` 만 set + return.

```diff
  if (snap.exists()) {
    ... 기존 처리 ...
- } else {
-   // (예외) 문서가 없을 때 최소 생성 — 이 경우도 V2 포맷 사용
-   const seq = 1
-   const myCode = makeMyCodeV2(u.email || '', seq)
-   ...
-   await setDoc(userRef, { ...data, ... })
+ } else {
+   // 새 가입자 — _fbSignupUser 의 runTransaction 이 곧 doc 생성.
+   // 여기서 자동 생성하면 그 트랜잭션이 already 분기로 빠져 counters 가 안 오름.
+   _ready.value = true
+   return
  }
```

**효과**:
- `_fbSignupUser` 의 트랜잭션이 정상 진입 → `cSnap.exists()===false` 또는 `userSeq` 읽기 → seq=base+1 → counters 정상 갱신
- 첫 가입자 seq=1, 두 번째 seq=2 ...
- 정확히 다른 myRefCode 발급

### 5-2. 보조 — `_fbSignupUser` 가 me.init 보다 먼저 실행되도록 보장 (어려움)

JS 이벤트 루프 / SDK 콜백 순서에 의존하지 않게 하려면:
- `_fbSignupUser` 안에서 `onAuthStateChanged` 콜백이 끝나기를 기다린 뒤 트랜잭션 실행
- 구현 복잡, 5-1 로 충분

### 5-3. 보강 — me.init else 분기를 자동 생성 대신 counters 트랜잭션으로

5-1 의 else 분기 제거 대신, else 분기 안에 정확한 counters 트랜잭션 추가:

```js
} else {
  await runTransaction(db, async (tx) => {
    const cSnap = await tx.get(countersRef)
    const base = cSnap.exists() ? Number(cSnap.get('userSeq')) || 0 : 0
    const seq = base + 1
    if (!cSnap.exists()) tx.set(countersRef, { userSeq: 1, updatedAt: ... })
    else tx.update(countersRef, { userSeq: seq, updatedAt: ... })

    const myCode = makeMyCodeV2(u.email || '', seq)
    tx.set(userRef, { type:'user', profile:{...}, referral:{myCode,...}, myJoinSeq: seq, myRefCode: myCode, ... })
  })
}
```

단 `_fbSignupUser` 도 같은 일을 하므로 **race 가 또 일어남** (둘 다 트랜잭션) → Firestore 트랜잭션이 retry 로 처리하지만 복잡. **5-1 권장**.

## 6. 기존 중복 코드 받은 계정 재발급

§4-2 으로 다수 사용자가 `myJoinSeq=1, myRefCode='prefix+00001'` 가진 게 확인되면 마이그레이션 Cloud Function 필요:

```js
exports.migrateReferralSeq = onCall(async (req) => {
  if (req.auth?.token?.email !== 'gangtalk815@gmail.com') throw new HttpsError(...)

  const usersSnap = await db.collection('users').orderBy('createdAt', 'asc').get()
  let counter = 0
  for (const doc of usersSnap.docs) {
    counter++
    const d = doc.data()
    const email = d.profile?.email || ''
    const seq = counter
    const newCode = makeMyCodeV2(email, seq)   // 클라이언트와 같은 알고리즘

    if (d.myJoinSeq === seq && d.myRefCode === newCode) continue

    await doc.ref.update({
      myJoinSeq: seq,
      myRefCode: newCode,
      'referral.myCode': newCode,
      updatedAt: FieldValue.serverTimestamp(),
    })
  }

  await db.doc('meta/counters').set({ userSeq: counter, updatedAt: FieldValue.serverTimestamp() }, { merge: true })
  return { migrated: counter }
})
```

- `createdAt` 순으로 정렬 → 진짜 가입 순서 복원
- 각 사용자 `myJoinSeq` + `myRefCode` 일관성 보장
- `meta/counters.userSeq` 도 마지막 seq 로 갱신

호출은 1회 (관리자만).
