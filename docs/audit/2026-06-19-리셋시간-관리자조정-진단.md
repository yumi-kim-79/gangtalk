## 1. 현재 리셋 구조 — 정확한 위치

### 1-1. `functions/index.js:2386-2405`

```js
exports.dailyReset0700 = onSchedule(
  { schedule: "0 7 * * *", timeZone: "Asia/Seoul", region: "asia-northeast3" },
  async () => {
    const col = db.collection("rooms_biz");
    const qs = await col.get();
    const bw = db.bulkWriter();
    const today = new Date().toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" });
    for (const doc of qs.docs) {
      bw.set(doc.ref, {
        needRooms: 0,
        needPeople: 0,
        matched: 0,
        lastResetDate: today,
        updatedAt: admin.firestore.FieldValue.serverTimestamp()
      }, { merge: true });
    }
    await bw.close();
    return null;
  }
);
```

### 1-2. 사양

| 항목 | 값 |
|---|---|
| 함수명 | `dailyReset0700` |
| cron | `"0 7 * * *"` (매일 분=0, 시=7) — **코드에 하드코딩** |
| timeZone | `Asia/Seoul` |
| region | `asia-northeast3` |
| 트리거 | Cloud Scheduler (Firebase 자동 생성: job name `firebase-schedule-dailyReset0700-asia-northeast3`) |
| 작업 | `rooms_biz` 전체 doc → `needRooms=0, needPeople=0, matched=0, lastResetDate=today` (merge:true) |
| `today` 형식 | `toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" })` 예: `"2026.6.22"` |

### 1-3. cron 변경의 코드 의존성

- Firebase Functions 가 배포 시점에 `onSchedule.schedule` 값을 Cloud Scheduler 의 job spec 으로 등록
- 코드의 `schedule` 값 변경 → 다음 deploy 시 Cloud Scheduler job 갱신
- 즉 **코드 변경 + 재배포 사이클** 필요. 관리자가 런타임에 cron 자체를 못 바꿈

## 3. 방법 B — 함수 자주 실행 + 설정 분기 (권장)

### 3-1. 동작

1. cron 을 매시 정각 (`"0 * * * *"`) 으로 변경 — 24번/일 호출
2. 함수 진입 시 `config/settings` doc 읽기 → `resetHour` 추출
3. 현재 KST hour 가 `resetHour` 와 같고, 오늘 아직 리셋 안 한 경우만 실제 리셋 실행
4. 리셋 후 `config/settings.lastResetDate = today` cursor 업데이트
5. 관리자가 admin UI 에서 `resetHour` 만 변경 — 다음 정시 tick 부터 적용

### 3-2. 구현 추정 코드 (참고용)

```js
exports.dailyResetHourly = onSchedule(
  { schedule: "0 * * * *", timeZone: "Asia/Seoul", region: "asia-northeast3" },
  async () => {
    // 1. 설정 읽기
    const settingsRef = db.collection("config").doc("settings");
    const snap = await settingsRef.get();
    const settings = snap.exists ? (snap.data() || {}) : {};
    const resetHour = Number(settings.resetHour ?? 7);

    // 2. 현재 KST hour 비교
    const now = new Date();
    const kstHourStr = now.toLocaleString("en-US", {
      timeZone: "Asia/Seoul", hour: "2-digit", hour12: false
    });
    const currentHour = Number(kstHourStr) || 0;
    if (currentHour !== resetHour) return null;            // 다음 tick 까지 대기

    // 3. 같은 날 중복 방지
    const today = now.toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" });
    if (settings.lastResetDate === today) return null;     // 이미 오늘 리셋함

    // 4. 리셋 실행 (기존 로직 그대로)
    const col = db.collection("rooms_biz");
    const qs = await col.get();
    const bw = db.bulkWriter();
    for (const doc of qs.docs) {
      bw.set(doc.ref, {
        needRooms: 0, needPeople: 0, matched: 0,
        lastResetDate: today,
        updatedAt: admin.firestore.FieldValue.serverTimestamp()
      }, { merge: true });
    }
    await bw.close();

    // 5. cursor 업데이트
    await settingsRef.set({
      lastResetDate: today,
      lastResetAt: admin.firestore.FieldValue.serverTimestamp(),
      lastResetHour: resetHour,
    }, { merge: true });

    return null;
  }
);
```

### 3-3. 장점
- ✅ 관리자 페이지에서 시간 변경 가능 — 즉시 다음 정시부터 적용
- ✅ **중복 리셋 방지** — `config/settings.lastResetDate` cursor 로 같은 날 한 번만 보장
- ✅ 안전 + 단순 — 기존 리셋 로직 그대로 보존
- ✅ 시간대 일관성 — Asia/Seoul 시간 기준
- ✅ 룰 변경 0 — `config/settings` 가 `config/{docId}` 룰 (`firestore.rules:33-36`) 통과

### 3-4. 단점 + 완화책

| 단점 | 완화책 |
|---|---|
| 함수 호출 빈도 증가 (1번/일 → 24번/일) | 호출당 비용 거의 0 (read 1번 + 23번 조기 종료). Firebase 100만 호출/월 무료 → 무시 가능 |
| 분 단위 정밀 제어 불가 (시 단위만) | 충분 — 운영 정책상 시 단위로 결정 |
| 시간 변경 시 같은 날 이미 리셋되면 그날 미적용 | cursor 가 의도된 동작. 다음날부터 새 시간 적용. + 보완: "지금 즉시 리셋" 버튼 (§5-3) |
| 첫 배포 시 cursor 없어서 첫 tick 에 리셋 가능 | 정상 — `settings.lastResetDate === undefined` 면 today 와 다르므로 첫 실행 시 리셋 트리거. 의도된 동작 |

### 3-5. 결론
**가장 권장** — 관리자 친화적 + 안전 + 비용 무시 + 회귀 위험 낮음.

## 7. 주의점 + 엣지 케이스

### 7-1. 중복 리셋 방지

- `config/settings.lastResetDate === today` 비교로 차단
- 함수가 동시에 두 번 실행돼도 두 번째는 즉시 return
- 단 race condition (두 함수가 동시에 진입해서 둘 다 cursor 갱신 전) — 매우 드문 케이스. Firestore transaction 사용해서 100% 차단 가능하나 과잉 (현재 매시 1회라 충돌 거의 없음)

### 7-2. 시간대 일관성

- cron: `timeZone: "Asia/Seoul"`
- JavaScript 비교: `toLocaleString(..., { timeZone: "Asia/Seoul" })`
- `today` 형식: `toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" })`
- → 모두 Asia/Seoul 일관

### 7-3. 시간 변경 후 적용 시점

| 변경 시각 | 변경 값 | 다음 적용 |
|---|---|---|
| 06:30 → 7시 → 8시 | 07:00 이미 리셋 → cursor today set → 다음날 08:00 |
| 08:30 → 7시 → 14시 | 오늘 07:00 리셋 후 → 08:00~13:00 함수는 hour 비교 실패 → 14:00 함수 진입 → cursor 가 today 면 차단 / 아니면 실행 |
| 06:00 (전날 07:00 리셋) → 14시 | 함수가 07:00 호출 시 hour=7 ≠ resetHour=14 → 차단. 14:00 호출 시 hour=14 → cursor (어제) ≠ today → 실행. 정상 |

→ **변경 직후 같은 날 적용 보장 안 됨**. "지금 즉시 리셋" 버튼으로 보완

### 7-4. `resetHour` 범위 검증

- 클라이언트: input min=0, max=23 + JS 보정
- 함수: `Number(settings.resetHour ?? 7)` + 안전망 (`if (!Number.isInteger(resetHour) || resetHour < 0 || resetHour > 23) resetHour = 7`)

### 7-5. 함수명 변경 시 옛 cron job 삭제

- `dailyReset0700` → `dailyResetHourly` 로 함수명 변경 시 Firebase 가 새 job 생성
- 옛 job (`firebase-schedule-dailyReset0700`) 자동 삭제 안 됨
- 수동 삭제 필수: `firebase functions:delete dailyReset0700`
- 또는 함수명 유지 + 내부 로직만 변경 (cron 만 다르게)

### 7-6. 주말/공휴일 처리 (옵션, 후속)

- `weekendSkip` 필드 추가 → 함수가 요일 체크
- 한국 공휴일은 캘린더 API 또는 별도 hardcoded list 필요
- 본 PR 범위 외 — 향후 검토

### 7-7. 함수 호출 비용 검증

- Cloud Functions 가격: 첫 200만 호출/월 무료 (Spark 100만)
- 매시 = 730 호출/월 → 무료 한도의 0.04%
- read 1번 (config/settings) + (조건 안 맞으면 즉시 return) = 23번 거의 무료
- 1번만 전체 rooms_biz read (`qs = await col.get()`) + bulkWriter — 평소 dailyReset0700 과 동일 비용
- **총 비용 무시 가능**
