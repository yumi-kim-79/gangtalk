## 0. 한 줄 결론

**PR #70 의 `_hasInput` 가드가 막지 못하는 시나리오 2 개 발견.**
가장 가능성 높은 진짜 범인은 **여러 rooms_biz 문서가 같은 storeId 로 합쳐지면서 last-wins 로 빈 doc 가 admin 의 좋은 doc 를 덮어쓰는 케이스** (`subscribeRoomsBiz:1378-1430` 의 `Promise.all` + `Object.fromEntries`).

차순위 범인은 **`needRooms: 0` 으로 명시 저장된 레거시 doc 가 `_hasInput=true` 를 통과**해 `byRb.rooms=0` 으로 그대로 사용되는 케이스 (PR #70 가드의 false-positive).

## 2. PR #70 의 `_hasInput` 가드 — 적용 범위 한계

### 현재 가드 위치 (`MainPage.vue:1156-1164`)
```js
const rbActive = !!byRb?._hasInput
const match = rbActive && Number.isFinite(byRb?.rooms)
  ? Number(byRb.rooms)
  : (Number.isFinite(legacyMatch) ? legacyMatch : 0)
const persons = rbActive && Number.isFinite(byRb?.people)
  ? Number(byRb.people)
  : (Number.isFinite(legacyPersons) ? legacyPersons : 0)
```

### `_hasInput` 생성 조건 (`:1421-1423`)
```js
const hasInput = !!pastedText
  || x.needRooms != null
  || x.needPeople != null
```

### ❌ 가드가 못 막는 케이스 A — `needRooms: 0` 으로 명시 저장된 레거시 doc
**시나리오**:
- ChatBiz `updateCounts` (`ChatBiz.vue:294-311`) 가 chat 파싱 결과를 그대로 `needRooms: 0, needPeople: 0` 으로 `safeUpdate` 호출 (실제로 0/0 이 채팅에서 나올 수 있음)
- 그 doc 가 user-side 에서 처리되면:
  - `x.needRooms = 0` → `0 != null` → **`hasInput = true`** ← 통과
  - `inputRooms = 0, inputPeople = 0`
  - `pastedText = ''` (또는 fetch 도 빈 결과)
  - Step A 스킵 → Step B trigger → `Math.max(0, 0) = 0`
  - `map[id] = { rooms: 0, people: 0, _hasInput: true }`
- `applyRoomsBiz`: `rbActive = true`, `Number.isFinite(0) = true` → **match = 0** (legacy 무시)

**현재 PR #70 가드는 "값이 명시적으로 0 인지" 와 "doc 가 비어있는지" 를 같은 _hasInput=true 로 다루므로** 이 케이스를 못 막음.

### ❌ 가드가 못 막는 케이스 B — 여러 rooms_biz doc 가 같은 storeId 로 합쳐짐 (last-wins)
**시나리오**:
- `subscribeRoomsBiz` 가 각 doc 마다 `storeId` 를 4 단계 resolution 으로 결정 (`:1340-1361`):
  1. `x.storeId` (data field)
  2. 이름 매칭 (`_storeIdByName[name]`)
  3. vendorKey 매칭 (`_storeIdByVendor[bizId]`)
  4. `bizId` (doc id 자체)
- **여러 doc 가 같은 storeId 로 결정될 수 있음**:
  - Doc A (`rooms_biz/elite_doc_id_xxx`) — admin saveAllMetrics 가 생성한 정상 doc (needRooms=3, needPeople=5)
  - Doc B (`rooms_biz/elite`) — 옛 vendorKey 기반 레거시 doc (비어있음 or 0/0)
  - 둘 다 storeId 'elite_doc_id_xxx' 로 resolve (B 는 vendorKey 매칭 via step 3)
- `entries.push({ id: storeId, x })` 가 둘 다 push → `Promise.all` 결과도 둘 다 포함
- `Object.fromEntries(results)` 가 **같은 key 면 마지막 값으로 덮어씀**
- Firestore snapshot 순서가 운에 따라 B 가 뒤에 오면 → B 의 0/0 이 A 의 3/5 를 덮음
- `map[elite_doc_id_xxx] = { rooms: 0, people: 0, _hasInput: ? }`

`_hasInput` 도 last-wins 로 따라옴. B 가 `needRooms: null` 이면 `_hasInput=false` → 다행히 legacy 폴백. 하지만 B 가 `needRooms: 0` 이면 `_hasInput=true` → 가드 통과 → match=0.

### 가드 OK 케이스
- doc 가 완전히 비어있음 (`needRooms` undefined, `needPeople` undefined, `pastedText` 없음) → `_hasInput=false` → legacy 폴백 ✓ (이게 PR #70 의 의도)

## 4. 관리자 저장 경로 vs 사용자 읽기 경로 — 필드 매핑

| Admin 저장 (`StoresManagePage:saveAllMetrics:467-480`) | 사용자 읽기 |
|---|---|
| `updateDoc(stores/{s.id}, { match: 3, persons: 5, totalRooms: 11, maxPersons: ?, statusMode, status, updatedAt })` | `stores` onSnapshot → `baseStores[i]` → `applyRoomsBiz` 의 `legacyMatch / legacyPersons / s.totalRooms` 로 사용 ✓ |
| `setDoc(rooms_biz/{s.id}, { needRooms: 3, needPeople: 5, need: 5, totalNeeded: 5, totalRooms: 11, updatedAt }, { merge: true })` | `subscribeRoomsBiz` 가 `x.needRooms` 읽음 → 처리 → `roomsBiz.value[s.id]` → `applyRoomsBiz` 의 `byRb` |

**저장 경로/필드 자체는 일치**. 단 user-side 가 "여러 rooms_biz doc 가 같은 store 를 가리킬 때" 의 충돌을 해소 못 함 → 케이스 B 발생.

또한 **admin save 가 한 store 의 가짜 vendorKey 기반 rooms_biz 를 정리/삭제하지 않음** → 레거시 doc 잔존 → 사용자 측에서 같이 처리됨.

## 5. 추가 사각지대 — `totalRooms` 가 0 으로 바뀌는 경로

PR #70 가드는 match/persons 만 보호. `totalRooms` 는 `applyRoomsBiz:1168-1170` 에서:
```js
const totalRooms = Number(
  byAg?.totalRooms ?? s?.totalRooms ?? s?.total ?? s?.rooms ?? 0
)
```
- byAg (vendors) → 권한 deny → undefined
- s.totalRooms = stores doc 의 totalRooms

만약 admin 이 totalRooms=11 을 저장하면 `s.totalRooms=11` → 표시 OK.
만약 admin 이 totalRooms 를 0 으로 저장했거나 안 보낸 store 라면 → 0.

**totalRooms 가 0 으로 바뀌는 경로는 stores doc 자체에 totalRooms=0 또는 미저장된 경우뿐.** PR #70 가드와 무관.

## 7. PR #70 이 놓친 부분 — 구체적 파일/라인

### `MainPage.vue:1421-1423` — `_hasInput` 정의가 너무 관대
```js
const hasInput = !!pastedText
  || x.needRooms != null
  || x.needPeople != null
```
- `x.needRooms = 0` 도 `_hasInput=true` 처리
- 의도: "데이터 없음 vs 진짜 0" 구분
- 결과: "진짜 0" 과 "쓰레기 0" (레거시 ChatBiz 의 0 write) 을 구분 못함

### `MainPage.vue:1378-1430` — 중복 storeId 충돌 해소 없음
```js
const results = await Promise.all(entries.map(async ({ id, x }) => { ... return [id, {...}] }))
const map = Object.fromEntries(results)
```
- 같은 id 가 entries 에 여러 번 들어오면 last-wins
- "더 의미 있는 데이터 우선" 규칙 없음

### `MainPage.vue:1156-1164` — 가드 자체는 OK 이지만 위 두 가지가 입력을 더럽힘
가드가 정확히 동작하려면 `byRb._hasInput=true` 일 때는 byRb 가 의미 있는 값을 들고 있어야 함. 위 두 케이스는 byRb 가 의미 없는 0 을 들고 오는데 `_hasInput=true` 인 상태로 들어옴.
