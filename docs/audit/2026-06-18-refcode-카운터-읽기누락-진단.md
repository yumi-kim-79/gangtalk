# 추천코드가 카운터 값을 안 읽고 seq=1 을 쓰는 정확한 지점 진단

**날짜**: 2026-06-18
**범위**: 모든 신규 가입자가 `prefix+'00001'` 받는 회귀. `referral_counters/Y.next = 12`, `meta/counters.userSeq = 38` 인데도 새 가입자가 `y00001`
**전제**: 진단 전용. 코드/룰/함수 수정·PR·배포 없음.
**결론**: **`referral_counters/{letter}` 컬렉션은 운영 코드에서 더 이상 읽지 않음 — dead 컬렉션**. 12 값은 옛 `functions/authFunctions.js` (Sprint 0 PR 에서 삭제됨) 의 흔적. **운영 시스템의 진짜 카운터는 `meta/counters.userSeq` (=38) 이지만 신규 가입 시 코드 생성에 사용 안 됨**. 진짜 원인은 이전 진단 (`docs/audit/2026-06-18-userseq-카운터-진단.md`) 의 결론과 동일 — **`me.init else 분기 (store/user.js:377-410)` 가 `_fbSignupUser` 의 트랜잭션보다 먼저 실행돼 `seq=1` 하드코딩으로 users doc 자동 생성**. 카운터를 안 읽는 게 아니라 **카운터 분기 자체에 도달하지 못함**.

## 1. 카운터를 읽는 코드 vs 안 읽는 코드 — 전수 검증

### 1-1. 운영 코드에 `referral_counters` 사용 없음


- `src/store/user.js` — `referral_counters` 참조 없음. **`meta/counters.userSeq` 만 사용**
- `functions/index.js` — 동일. `referral_counters` 참조 없음

### 1-2. `referral_counters` 의 출처

- **Sprint 0 PR (`feature/sprint0-sms-secret-hardening`) 에서 삭제된 `functions/authFunctions.js`** 의 옛 `reserveReferralCode` 가 이 컬렉션을 썼음
- git 히스토리:
  ```js
  // 옛 functions/authFunctions.js:83-104 (Sprint 0 에서 파일 삭제됨)
  exports.reserveReferralCode = onCall(async (req) => {
    const countersRef = db.collection("meta").doc("referral_counters");
    const snap = await countersRef.get();
    const counter = snap.exists ? snap.data()[prefix] || 0 : 0;
    const next = counter + 1;
    const code = `${prefix}${String(next).padStart(5, "0")}`;
    await countersRef.set({ [prefix]: next }, { merge: true });
    await db.collection("referral_codes").doc(code).set({ reserved: true, ... });
    return { code };
  });
  ```
- 이 함수가 옛날에 작동했을 때 Y 시작 가입자 12명에게 발급됨 → `meta/referral_counters` 의 `Y` 필드 = 12
- 함수 삭제 후 **호출 코드 (`AuthPage.vue:520 httpsCallable('reserveReferralCode')`) 는 남았지만 함수 미배포 → catch 폴백 → AuthPage 의 `myReferralCode` 변수는 dead variable**

### 1-3. 사용자 보고의 "카운터 정상 증가 중" 인식

- `meta/referral_counters.Y = 12` 가 Firestore 콘솔에 살아있음 → 그러나 **현재 코드에서 안 씀**. dead 컬렉션
- "정상 증가 중" 은 잘못된 인식 — Sprint 0 이후 한 번도 증가 안 함. 누가 수동 편집했거나 옛 잔재값

### 1-4. 운영의 진짜 카운터 = `meta/counters.userSeq` (=38)

- `_fbSignupUser` 의 `runTransaction` 이 갱신하는 컬렉션
- 정상 동작하면 가입자 1명당 +1 증가
- userSeq=38 = 옛날 (me.init else 분기 도입 전) 38명의 가입자가 트랜잭션 분기에 정상 도달했을 때 누적
- 현재는 race 로 트랜잭션 분기 도달 안 함 (§3)

## 2. 추천코드 생성 경로 — 3개

| 경로 | 위치 | 카운터 | 결과 |
|---|---|---|---|
| (a) `_fbSignupUser` 의 정상 트랜잭션 | `store/user.js:472-490` | `meta/counters.userSeq` 읽고 +1 | `makeMyCodeV2(email, seq)` — `'prefix' + 5자리 zero-pad` |
| (b) `me.init` 의 else 분기 | `store/user.js:377-410` | **없음 — `seq=1` 하드코딩** | `makeMyCodeV2(email, 1)` — `'prefix00001'` |
| (c) 서버측 `ensureMyReferralCode` → `generateUniqueReferralCode` | `functions/index.js:508-518` | 없음 — **랜덤 8글자** | 예: `AB3K7QXR` |

### 2-1. `makeMyCodeV2` 동작 (`store/user.js:54-61`)
```js
function makeMyCodeV2(email = '', seq = 1) {
  const local = emailLocalPart(email)
  const prefix = (local[0] || 'x').toLowerCase()
  const n = Math.max(1, Number(seq) || 1)
  const numStr = String(n)
  const padded = numStr.length >= 5 ? numStr : numStr.padStart(5, '0')
  return `${prefix}${padded}`
}
```
- `email='yusung090909@naver.com'`, `seq=1` → `'y00001'`
- `seq=38` → `'y00038'`
- **결정론적**. 입력 (email, seq) 이 같으면 같은 코드

### 2-2. 클라이언트 (a, b) vs 서버 (c) 의 충돌 / 덮어쓰기

- 클라이언트 (a) 또는 (b) 가 `users/{uid}.myRefCode` 를 먼저 set
- 서버 (c) 의 `ensureMyReferralCode` 는 `if (existing) return existing` — **이미 있으면 그대로 유지**, 덮어쓰지 않음
- → 클라이언트 (b) 의 `'y00001'` 이 set 된 상태에서 `applyReferralNow` 호출되면 `ensureMyReferralCode` 가 'y00001' 그대로 인식 → 변화 없음

### 2-3. 대소문자 (Y vs y) — 무관

- 운영 코드의 `makeMyCodeV2:56` 는 `prefix.toLowerCase()` — 항상 소문자 'y'
- 대소문자 불일치로 다른 문서를 읽거나 못 읽는 케이스 없음
- `referral_counters.Y` (대문자) 는 dead 컬렉션이라 운영 무관

## 3. 진짜 원인 — race 메커니즘 재확인

이전 진단 (`docs/audit/2026-06-18-userseq-카운터-진단.md`) 의 §1-3 표 그대로:

| t | 이벤트 | users/{uid} | meta/counters |
|---|---|---|---|
| 1 | `await createUserWithEmailAndPassword` 완료 | 없음 | userSeq=38 |
| 2 | Firebase Auth SDK `onAuthStateChanged` 발화 (microtask 큐) | 없음 | 38 |
| 3 | `_fbSignupUser` 가 다음 `await runTransaction(...)` 시작 (microtask 양보) | 없음 | 38 |
| 4 | **me.init 의 onAuthStateChanged 콜백 먼저 실행** | 없음 | 38 |
| 5 | me.init: `await getDoc(userRef)` → `snap.exists()===false` → else 분기 | 없음 | 38 |
| 6 | me.init: `setDoc({ ..., myJoinSeq:1, myRefCode:'y00001' })` | **존재 (seq=1)** | 38 |
| 7 | `_fbSignupUser` 의 runTransaction 안의 첫 read 실행 | 존재 | 38 |
| 8 | `tx.get(userRef)` → `uSnap.exists()===true, myJoinSeq=1` | 존재 | 38 |
| 9 | `already === true` → return seq=1 → **counters 분기 안 들어감** | 존재 | **38 (변화 없음)** |
| 10 | 트랜잭션 commit (effective no-op) | 존재 | 38 |

→ **`_fbSignupUser` 의 트랜잭션이 카운터를 안 *읽는* 게 아니라, `already` 분기에서 일찍 return 해 카운터 갱신 코드에 *도달 못 함***. 사용자 표현 "카운터 값을 안 읽음" 은 의미상 같음.

### 3-1. 카운터 분기 도달 조건
- `uSnap.exists() === false` (users doc 없음)
- OR `Number(uSnap.get('myJoinSeq')) === 0`

둘 다 me.init else 분기가 이미 set 한 후라 false. 도달 불가.

### 3-2. 폴백 위치 — seq=1 하드코딩 (파일:라인)
- **진짜 폴백 = `store/user.js:379` `const seq = 1`**
- `_fbSignupUser` 의 트랜잭션 catch 폴백은 **없음**. throw 시 가입 자체 실패
- "트랜잭션 실패 시 seq=1 폴백" 같은 코드 없음 — me.init 의 else 분기 자체가 seq=1

## 4. 올바른 흐름 — 클라이언트 vs Cloud Function

### 4-1. 옵션 A: **me.init else 분기 제거** (가장 단순, 권장)

```diff
  if (snap.exists()) {
    ... 기존 처리 ...
- } else {
-   // (예외) 문서가 없을 때 최소 생성 — 이 경우도 V2 포맷 사용
-   const seq = 1
-   const myCode = makeMyCodeV2(u.email || '', seq)
-   ...
-   await setDoc(userRef, { ...data, ... })
+ } else {
+   // 새 가입자 — _fbSignupUser 의 runTransaction 이 직후 doc 생성.
+   // 여기서 자동 생성하면 그 트랜잭션이 already 분기로 빠져 counters 못 오름.
+   _ready.value = true
+   return
  }
```

**효과**:
- `_fbSignupUser` 의 트랜잭션 진입 시 `uSnap.exists()===false` → counters 분기로
- `cSnap.exists()===true, userSeq=38` → base=38, seq=39 → `tx.update({ userSeq: 39 })`
- `tx.set(userRef, { ..., myJoinSeq:39, myRefCode:'y00039' })`
- **새 가입자가 정확히 seq=39 받음**

**`_fbSignupUser` 와 me.init 의 충돌 차단**:
- 정상 가입 흐름: AuthPage → `me.signupUser` → `me._fbSignupUser` → 트랜잭션
- 비정상 진입 (예: Auth user 만 있고 users doc 없는 케이스, 데이터 손상 등) 은 거의 없음
- 만약 발생하면 `_ready=true` 만 set 하고 me.auth = LS_AUTH 캐시 그대로. 사용자가 다시 가입 시도하면 트랜잭션이 처리

### 4-2. 옵션 B: 트랜잭션을 Cloud Function 으로 이전 (CLAUDE.md Sprint 2 #11)

- 보안: 클라이언트가 직접 카운터 +1 하는 것보다 서버에서 처리하는 게 안전
- 단 옵션 A 보다 큰 변경. 본 PR 범위 아닐 수 있음
- 옵션 A 적용 후 별도 후속 작업으로

### 4-3. 옵션 C: me.init else 분기에 counters 트랜잭션 추가 (비추천)

- me.init + `_fbSignupUser` 두 곳에서 트랜잭션 → Firestore 트랜잭션 retry 메커니즘이 처리하지만 코드 복잡도 증가
- 옵션 A 의 단순성 이상 가치 없음

## 5. 기존 중복코드 (y00001 등) 재발급 방법

### 5-1. 영향 범위 확인
사용자 보고: `referral_counters/Y.next = 12` (dead 컬렉션) 이지만 실제 운영의 중복 코드는 **me.init else 분기 도입 이후의 가입자**. `meta/counters.userSeq=38` 이지만 그 후 추가 가입자가 모두 seq=1.

### 5-2. Cloud Function 마이그레이션 (관리자 1회 호출)

```js
exports.migrateReferralSeq = onCall(async (req) => {
  if (req.auth?.token?.email !== 'gangtalk815@gmail.com') {
    throw new HttpsError('permission-denied', 'admin only')
  }

  const usersSnap = await db.collection('users')
    .orderBy('createdAt', 'asc')
    .get()

  let counter = 0
  const batch = db.batch()
  let writes = 0

  for (const doc of usersSnap.docs) {
    counter++
    const d = doc.data()
    if (d.type !== 'user') continue   // 회원만 (company 는 별도)

    const email = d.profile?.email || ''
    const seq = counter
    const local = (email.split('@')[0] || '').toLowerCase()
    const prefix = (local[0] || 'x')
    const newCode = `${prefix}${String(seq).padStart(5, '0')}`

    if (d.myJoinSeq === seq && d.myRefCode === newCode) continue

    batch.update(doc.ref, {
      myJoinSeq: seq,
      myRefCode: newCode,
      'referral.myCode': newCode,
      updatedAt: FieldValue.serverTimestamp(),
    })
    writes++

    // batch 500 limit
    if (writes >= 450) {
      await batch.commit()
      writes = 0
    }
  }

  if (writes > 0) await batch.commit()

  // counters 도 마지막 seq 로 동기화
  await db.doc('meta/counters').set({
    userSeq: counter,
    updatedAt: FieldValue.serverTimestamp(),
  }, { merge: true })

  return { migrated: counter }
})
```

- `createdAt` 순으로 정렬해 진짜 가입 순서 복원
- 각 user 의 `myJoinSeq` + `myRefCode` 일관성 보장
- `meta/counters.userSeq` 갱신 (next 가입자가 정상 seq+1 받도록)
- 1회 호출, 그 후 함수 삭제 가능

### 5-3. `referral_counters` dead 컬렉션 정리 (선택)
- Firebase Console 에서 수동 삭제 또는 별도 마이그레이션 함수
- 운영 무관이라 우선순위 낮음

### 5-4. 사용자 통보
- 추천코드가 변경되는 사용자에게 알림 (옵션) — 본인이 코드 외워 사용한 경우 영향
- 추천코드 자동 적용 (`applyReferralNow`) 는 이미 적용된 경우 변경된 코드와 무관 — `referral.refBy` 는 그대로

## 6. 결론

### 6-1. 사용자 보고의 정정
- "글자별 카운터(`referral_counters`) 정상 증가 중" — **틀린 인식**. 운영 코드에서 안 씀. 12 는 옛 흔적
- "코드 생성이 카운터 값을 안 읽음" — 의미상 맞음. 진짜 메커니즘은 **`_fbSignupUser` 의 트랜잭션이 카운터 분기 도달 못 함**
- "읽는 곳과 쓰는 곳이 어긋남" — 정확히는 **me.init else 분기 (`seq=1`)** 가 `_fbSignupUser` 의 카운터 분기 작동을 막음

### 6-2. 진짜 원인 (이전 진단과 일치)
- **`store/user.js:377-410` me.init else 분기**
- 새 가입자의 `onAuthStateChanged` 발화 시 `_fbSignupUser` 트랜잭션보다 먼저 실행
- `seq=1` 하드코딩 + `setDoc` 으로 users doc 생성
- `_fbSignupUser` 트랜잭션은 이미 존재 → `already` → counters 분기 미도달
