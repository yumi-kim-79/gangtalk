## 1. 자동 로그아웃

### 1-1. firebase.js 의 인증 부트스트랩 (`src/firebase.js:144-182`)

```js
const auth = getAuth(app)             // ① SDK 가 default(localStorage) 로 복원 시작

;(async () => {                       // ② persistence 설정 — 비동기, await 안 함
  try { await setPersistence(auth, indexedDBLocalPersistence) }
  catch { try { await setPersistence(auth, browserLocalPersistence) }
          catch { await setPersistence(auth, inMemoryPersistence) } }
})().catch(() => {})

async function ensureSignedIn() {     // ③
  if (auth.currentUser) return auth.currentUser
  const existing = await new Promise(resolve => {
    const unsub = onAuthStateChanged(auth, u => { unsub(); resolve(u || null) })
  })
  if (existing) return existing
  const cred = await signInAnonymously(auth)   // ④ 실계정 위에 익명 덮어쓰기 가능
  return cred.user ?? null
}

const firebaseReady = (async () => {
  try { await _appCheckReady } catch {}
  await ensureSignedIn()
})()
```

### 1-2. 자동 로그아웃의 진짜 원인 — `onAuthStateChanged` 첫 콜백 race

Firebase Auth SDK 의 알려진 동작:
- 페이지 로드 시 SDK 가 persistence 에서 user 복원 시작 (비동기)
- 복원 진행 중에 등록된 `onAuthStateChanged` 는 **두 번 발화 가능**:
  1. 첫 번째: `null` (복원 전)
  2. 두 번째: 복원된 user

`ensureSignedIn` (`firebase.js:164-177`) 의 동작:
- 첫 콜백이 발화하면 `unsub()` 호출 → 두 번째 콜백 못 받음
- 첫 콜백이 `null` 이면 `signInAnonymously` 호출 → **익명 user 가 currentUser 가 됨**
- SDK 가 뒤늦게 실계정 복원 시도 → 이미 익명으로 점유됨 → **실계정 잃음**

**결과**: 새로고침 시 실계정 → 익명 user 로 교체되는 race 가 가끔 발생.

### 1-3. store/user.js 의 보조 증폭 (`src/store/user.js:231-238`)

```js
onAuthStateChanged(auth, async (u) => {
  if (!u) {
    me.auth.value = { loggedIn: false }
    me.save()                          // ← localStorage LS_AUTH 를 loggedIn:false 로 즉시 덮어씀
    _uid.value = ''
    _listenUserDoc(FBOK, '')
    _ready.value = true
    return
  }
  ...
})
```

- SDK 의 일시 `null` 발화에 대해 **즉시** `LS_AUTH` 캐시를 `{ loggedIn: false }` 로 덮어씀
- 다음 새로고침 시 화면이 "비로그인" 상태로 시작 (캐시가 sticky)

### 1-4. 다른 의심 차단 — App Check / 라우터 가드

| 의심 | 확인 결과 | 영향 |
|---|---|---|
| App Check 토큰 만료 | `isTokenAutoRefreshEnabled: true` + `visibilitychange` 시 getToken | 자동 갱신, auth 끊지 않음 |
| App Check 실패 (Enterprise 키) | catch 블록에서 `console.warn` 만, 차단 안 함 (`firebase.js:121-130`) | 영향 없음 |
| 라우터 가드 강제 로그아웃 | `src/router/index.js` 의 beforeEach 는 `requiresAdmin` 만 처리. 회원 사이트는 가드에서 `signOut` 호출 안 함 | 영향 없음 |
| ChatOpen 의 `signInAnonymously` (`ChatOpen.vue:185`) | `if (!auth.currentUser)` 가드 — 실계정 있으면 호출 안 함 | 정상 |

→ **유일한 트리거는 §1-2 의 `ensureSignedIn` race 와 §1-3 의 LS_AUTH 즉시 덮어쓰기**

### 1-5. "시간이 지나면 로그아웃"? — 사용자 보고와의 일치

엄밀히 말해 **시간 경과로 자동 로그아웃 트리거되는 코드는 없음**. 그러나 사용자가 보고하는 "시간 지나면" 의 실제 시나리오 추정:
- 사용자가 한참 후 새 탭/새로고침 → §1-2 race 발생 → 익명으로 교체
- 또는 토큰 만료(1시간) 후 일시적 인증 끊김 → onAuthStateChanged 의 null 발화 → §1-3 가 LS_AUTH 덮어씀 → 다음 페이지 진입 시 "비로그인" 으로 시작

### 1-6. PR #72 / PR #74 와의 연관 — 없음

- **PR #72**: `src/composables/useAuthRole.js` + `src/router/admin.js` 만 영향. `lastKnownUser` 폴백은 admin 빌드 전용. 회원 빌드 (`src/firebase.js`, `src/router/index.js`) 는 손대지 않음
- **PR #74**: firestore.rules + storage.rules 만. auth 코드 무관

### 1-7. "한 번 로그인하면 유지" 만들 변경점 (별도 PR — 본 진단 외)

1. **`ensureSignedIn` 의 race 차단** (`firebase.js:164-177`):
   - 첫 콜백이 `null` 이면 즉시 `signInAnonymously` 하지 말고, 짧은 timeout (예: 1500ms) 동안 두 번째 콜백 기다림
   - 또는 `localStorage` 의 `firebase:authUser:*` 키 존재 여부를 사전 확인 후 익명 호출 결정
2. **`me.init` 의 null 콜백 처리** (`store/user.js:231-238`):
   - `u === null` 일 때 즉시 `LS_AUTH` 를 덮어쓰지 말고, 일정 시간 후에도 여전히 null 이면 그제야 비로그인 처리
   - 또는 `lastKnownUser` 패턴을 회원 사이트에도 도입 (admin 빌드의 `useAuthRole` 와 동일)
3. **익명 로그인 자체 폐지 검토**:
   - GangTalk 회원 사이트가 실제로 익명 로그인을 필요로 하는 기능이 있는지 재검토
   - `firestore.rules` 의 대부분 룰이 `signedIn()` 이지만 — public read 가 광범위 (stores/config/news/partners 등). 익명 로그인 없어도 표시는 가능
   - `ChatOpen.vue:185` 만 익명 필요 — 그 경로 진입 시에만 호출

## 2. 즐겨찾기 (찜)

### 2-1. 코드 경로 — **두 가지 방식 공존, 동기화 안 됨**

| 페이지 | 동작 | 저장처 |
|---|---|---|
| `MainPage.vue:911 toggleFav` | 하트 버튼 | **`localStorage` (`mp:favs`)** — Firestore 안 씀 |
| `PartnerDetail.vue:223 setDoc(favorites, ...)` | 하트 버튼 | **Firestore `favorites/{favDocId}`** |
| `FavoritesPage.vue:185` | 마이페이지 찜 목록 표시 | **Firestore** — ① `favorites where ownerId==uid` ② 권한 거절 시 폴백 `users/{uid}/favorites` |

### 2-2. 디바이스 간 동기화 안 됨

- MainPage 의 하트는 `localStorage` 만 저장 → 다른 기기 / 새 브라우저에서 사라짐
- FavoritesPage 는 Firestore 만 읽음 → MainPage 에서 찜한 것이 FavoritesPage 에 안 나타남

### 2-3. firestore.rules 의 favorites 룰 — **존재하지 않음 = default deny**

`firestore.rules` 전체에서 `favorites` 또는 `users/{uid}/favorites` 매치 룰이 **없음**.
Firestore 의 default 정책 = deny → 모든 read/write 거부.

따라서:
- **PartnerDetail 의 setDoc(`favorites/...`) → 항상 실패** (`PartnerDetail.vue:223`)
- **FavoritesPage 의 onSnapshot(`favorites where ownerId==uid`) → 권한 에러** → 폴백
- **폴백의 `users/{uid}/favorites` 도 룰 없음** → 권한 에러 → `err.value` set → 화면 "오류" 표시

(참고: `users/{uid}` 자체 doc 는 read 가능 (`firestore.rules:67-70`), 단 서브컬렉션 `favorites` 는 별도 룰 필요. wildcard `match /users/{uid}/{document=**}` 도 없음)

### 2-4. PR #74 의 영향 — **없음**

- PR #74 는 `stores`, `storage` 룰만 변경
- `favorites` 컬렉션 룰은 PR #74 이전부터 부재
- → favorites 미동작은 **기존부터의 룰 부재 + 코드/저장처 불일치** 문제. 최근 변경 무관

### 2-5. 정리

| 항목 | 상태 | 원인 |
|---|---|---|
| MainPage 의 하트 클릭 (localStorage) | ✓ 작동 (단 한 기기 한정) | 코드는 정상, 디바이스 간 동기화 없음 |
| MainPage 찜 → FavoritesPage 표시 | ✗ 안 됨 | 저장처 다름 (localStorage vs Firestore) |
| PartnerDetail 의 하트 클릭 | ✗ 안 됨 | 룰 부재 → default deny |
| FavoritesPage 의 목록 표시 | ✗ 안 됨 | 같은 이유 |
| 로그인 의존성 | 일부 | FavoritesPage 진입 시 `auth.currentUser` 필요 (`FavoritesPage.vue:180`). 자동 로그아웃 (§1) 영향으로 진입 자체가 막힐 수도 |

## 3. 별점 (Rating)

### 3-1. 코드 경로 (`src/pages/StoreDetail.vue:488-535`)

```js
const storeRef = doc(db,'stores', store.id)
const myRef    = doc(db,'stores', store.id, 'ratings', uid.value)

await runTransaction(db, async (tx) => {
  const [storeSnap, mySnap] = await Promise.all([tx.get(storeRef), tx.get(myRef)])
  ...
  if (s > 0) tx.set(myRef, { score: s, updatedAt: serverTimestamp() })
  else if (mySnap.exists()) tx.delete(myRef)

  tx.update(storeRef, {
    ratingSum: nextSum,
    ratingCount: nextCount,
    rating: nextAvg,
    updatedAt: serverTimestamp(),
  })
})
```

별점 매기기:
- 두 쓰기를 `runTransaction` 으로 동시 실행
  1. `stores/{id}/ratings/{uid}` 서브컬렉션 — 본인 별점 기록
  2. `stores/{id}` 상위 doc — 평균/카운트 갱신

### 3-2. firestore.rules 의 ratings 서브컬렉션 — **존재하지 않음 = default deny**

`firestore.rules` 에서 `stores/{id}/ratings/{uid}` 또는 `stores/{id}/{document=**}` 매치 룰 **없음**.
→ ratings 서브컬렉션 read/write **default deny**

### 3-3. stores update 의 룰 — PR #74 가 변경 (간접 영향)

별점 사용자가 stores 상위 doc 의 `ratingSum/ratingCount/rating` 을 update 하려면:
- **이전 룰**: 본인 ownerId 일치, 관리자, **또는 빈 ownerId 점유 룰 (③④)**
- **PR #74 이후 룰**: 본인 ownerId 일치 또는 관리자만. 빈 ownerId 점유 절 제거

별점 매기는 **일반 사용자는 가게 owner 가 아님** → 이전에도, 이후에도 거부.

다만:
- 이전에는 `ownerId` 가 없는 옛 stores doc 에 대해 **빈 ownerId 점유 룰 (③④)** 로 한정해 update 가 통과되는 의도치 않은 케이스가 있을 수 있었음 (보안 구멍)
- 이로 인해 일부 가게에서 별점이 작동했을 가능성 → PR #74 가 이 보안 구멍을 닫음 → 그 가게들에서도 작동 안 함

### 3-4. PR #74 의 영향 — **간접적, 부수효과**

PR #74 는 명시적으로 별점을 차단하려 한 것이 아니라:
- 별점 기능은 **처음부터 ratings 서브컬렉션 룰 부재 + stores update 룰 모두 통과 못 하는 구조**
- 이전에 작동했다면 빈 ownerId 점유 구멍을 우연히 활용 → 이 구멍을 닫으면서 작동 안 됨이 표면화

### 3-5. 별점이 정상 작동하려면 (별도 PR)

- `stores/{id}/ratings/{uid}` 서브컬렉션 룰 추가:
  ```
  match /stores/{storeId}/ratings/{uid} {
    allow read: if true;
    allow create, update, delete: if isOwner(uid);
  }
  ```
- `stores/{id}` update 룰: 일반 사용자가 별점 필드만 변경 가능하도록 확장:
  ```
  allow update: if signedIn() && (
    isAdmin()
    || (resource.data.ownerId == request.auth.uid && /* ... 기존 ... */)
    || changesAreOnly(['rating', 'ratingSum', 'ratingCount', 'updatedAt'])
  );
  ```
  (`changesAreOnly` 헬퍼는 `firestore.rules:26` 에 이미 정의됨)
- 그리고 트랜잭션 내에서 별점 사용자가 ratingSum/ratingCount 를 임의 조작 못하도록 검증 — 실제로는 트랜잭션이라 클라이언트가 새 값을 직접 결정. 룰에서 `request.resource.data.ratingCount == resource.data.ratingCount + 1 || == resource.data.ratingCount - 1` 같은 무결성 룰 필요. **추가 설계 필요**

## 4. 결론 — 사용자 보고 vs 코드 진실

### 4-1. 자동 로그아웃
- **진짜 원인**: `firebase.js:164-177 ensureSignedIn` 의 onAuthStateChanged race + `store/user.js:231-238 me.init` 의 null 콜백 즉시 LS_AUTH reset
- **트리거**: 새로고침 / 토큰 만료 / SDK 복원 race
- **PR #72/#74 와 관계 없음** (기존 디자인 문제)
- **해결 방향**: `ensureSignedIn` 의 첫 콜백이 null 일 때 timeout 후 한 번 더 확인, 또는 `localStorage` 의 firebase 캐시 키 존재 확인 후 익명 호출 결정

### 4-2. 즐겨찾기 (찜)
- **MainPage 하트**: localStorage 만 — 한 기기 한정. FavoritesPage 와 분리됨 (저장처 불일치 = 코드 설계 문제)
- **PartnerDetail 하트**: Firestore `favorites/...` write → 룰 부재 → 항상 실패
- **FavoritesPage 표시**: Firestore `favorites` 또는 `users/{uid}/favorites` 구독 → 둘 다 룰 부재 → 화면 "오류"
- **PR #74 와 관계 없음** (favorites 룰은 처음부터 부재)
- **해결 방향**: favorites 룰 추가 + MainPage 도 Firestore 사용으로 통일

### 4-3. 별점
- **코드는 존재** (StoreDetail.vue 의 runTransaction)
- **룰 부재 + PR #74 부수효과**:
  - `stores/{id}/ratings/{uid}` 서브컬렉션 룰 없음 → 처음부터 deny
  - PR #74 이전: 빈 ownerId 점유 구멍으로 일부 가게에서 우연히 작동했을 가능성
  - PR #74 이후: 빈 ownerId 구멍 닫혀 모든 가게에서 일관되게 deny
- **해결 방향**: ratings 서브컬렉션 룰 추가 + stores update 룰에 `changesAreOnly(['rating', 'ratingSum', 'ratingCount', 'updatedAt'])` 분기 추가
