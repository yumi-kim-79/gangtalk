## 목표 1 — 지표 불일치 분석

### 1-1. 현재 저장처 / 읽기처 1:1 대조

| 주체 | 페이지 / 함수 | stores 에 쓰는 필드 | rooms_biz 에 쓰는 필드 |
|---|---|---|---|
| 관리자 | `StoresManagePage.vue:447-496 saveAllMetrics` | `match, persons, totalRooms, maxPersons, statusMode, status, updatedAt` | `needRooms, needPeople, need, totalNeeded, totalRooms, updatedAt` (merge:true) |
| 업체 | `BizMetricsPage.vue:282-318 onSave` | `match, persons, totalRooms, statusMode, status, updatedAt` (⚠️ **maxPersons 빠짐**) | `needRooms, needPeople, need, totalNeeded, totalRooms, updatedAt` (merge:true) |
| 사용자 | `MainPage.vue:1138-1204 applyRoomsBiz` | (읽기 전용) `s.match ?? s.needRooms ?? 0` 등 legacy 폴백 | `byRb.rooms / byRb.people` (PR #71 의 `_hasInput` 양수 신호일 때만) |

→ 두 저장 경로 모두 **stores + rooms_biz 양쪽에 같은 값을 쓰도록** 구현돼 있음. 단일 트랜잭션은 아니라 **부분 실패** 시 둘이 어긋남.

### 1-2. PR #71 이후에도 남아 있는 불일치 케이스

#### 케이스 A — 한쪽 write 실패로 분리
- `saveAllMetrics` 가 `updateDoc(stores)` → `setDoc(rooms_biz, ..., {merge:true})` 순차 호출 (`StoresManagePage.vue:467-480`).
- **stores 성공 / rooms_biz 실패**: stores 는 새 값, rooms_biz 는 옛 값(또는 없음).
  - rooms_biz 가 양수 옛 값이면 → PR #71 tier=2 우선 → 옛 값 표시
  - rooms_biz doc 가 없으면 → byRb=null → legacy 폴백 → stores 새 값 표시 (이 경우는 정상)
- **stores 실패 / rooms_biz 성공**: rooms_biz 새 값, stores 옛 값.
  - rooms_biz 양수면 PR #71 tier=2 우선 → 새 값 표시 (정상)
  - rooms_biz 0/0 이면 `_hasInput=false` → legacy 폴백 → **stores 옛 값** 표시
- **현황**: 부분 실패 시 콘솔에 `metric save fail {storeId} {err}` 출력. `errors[]` 에 누적해 alert. 그러나 사용자는 자기 화면에서 옛값을 보고 있음

#### 케이스 B — rooms_biz 가 ChatBiz / 시트 업로드로 갱신 (관리자 saveAllMetrics 와 무관한 경로)
- `rooms_biz` 는 ChatBiz 초톡 메시지, 시트 업로드 파이프라인, `pastedText` 자동 파싱 등 **외부 경로로도 갱신** 됨
- 관리자가 수동지표로 양수 값을 저장한 뒤, **그 후 다른 경로가 rooms_biz 만 다른 값으로 덮어씀**
- PR #71 의 tier 머지는 동일 storeId 의 여러 doc 사이에서만 작동. **같은 doc 의 시간 차 덮어쓰기는 막지 못함**.
- 결과: stores.match=12 인데 rooms_biz.needRooms=3 같은 불일치 — 사용자 화면은 rooms_biz 의 3 표시

#### 케이스 C — 중복 storeId 매핑 (`subscribeRoomsBiz` 의 4단계 폴백)
`MainPage.vue:1330-1367`:
```js
let storeId = String(x.storeId || '')
if (!storeId || !_hasStoreId(storeId)) {
  const guessName = _normName(x.name || bizId)
  storeId = _storeIdByName.value.get(guessName) || ''
}
if (!storeId) {
  storeId = _storeIdByVendor.value.get(bizId.toLowerCase()) || ''
}
if (!storeId) storeId = bizId
```
- **동명 가게가 둘 이상** 일 때 `_storeIdByName` 매핑은 **마지막 등록 가게로 덮어씀** (`rebuildStoreIndexes` 가 `Map.set` 으로 build → 동명이면 last-wins)
- 그래서 두 가게의 rooms_biz 가 서로의 storeId 로 잘못 매핑됨
- PR #71 의 tier 머지는 같은 storeId 로 매핑된 후의 충돌은 잡지만, **매핑 자체가 잘못된 케이스는 못 잡음**

#### 케이스 D — rooms_biz 가 storeId 가 아닌 옛 id 로 저장 + 양수 값 보유
- 옛 rooms_biz doc id = `vendor_xxx` 또는 `biz_xxx` 등 임의 id
- `subscribeRoomsBiz` 가 이름/vendorKey 매칭 → 새 stores doc 와 동일 storeId 로 흡수
- 새 saveAllMetrics 가 `rooms_biz/{store.id}` 에 새 doc 생성
- 결과: 같은 storeId 에 매핑되는 doc 가 2개. 둘 다 양수면 PR #71 tier 동점 → updatedAt 최근 우선.
- **만약 옛 doc 가 ChatBiz 등으로 timestamp 자동 갱신되면 옛 doc 이 최근 → 옛 값 표시**

#### 케이스 E — stores.match 도 외부 경로로 변경됨
- 회원 사이트의 `StoreEditPage.vue` 가 stores 전체 필드 (match, persons, totalRooms 포함) 를 setDoc 으로 갱신
- 업체나 관리자가 가게 정보를 편집하면서 `match` 를 의도치 않게 0 으로 reset 하는 케이스
- 이 후 rooms_biz 는 양수 → rbActive=true → byRb.rooms 표시 (이건 정상)
- 단 reverse 경우: 업체가 가게 편집으로 match=10 set 후 → rooms_biz 는 그대로 옛 값 (3) → 사용자는 3 봄

### 1-3. 값이 다른 업체 식별 — 콘솔 스니펫

브라우저 콘솔 (gangtox.com/dashboard) 에서 실행:

```js
// =====================================================================
// 지표 불일치 식별 스니펫
// stores.match  ↔ rooms_biz.needRooms 가 다른 가게를 모두 찾아 표로 출력
// =====================================================================
const fs = firebase.firestore()
;(async () => {
  const [stSnap, rbSnap] = await Promise.all([
    fs.collection('stores').get(),
    fs.collection('rooms_biz').get(),
  ])

  // ── A. storeId → rooms_biz docs (subscribeRoomsBiz 의 4단계 폴백 시뮬레이션)
  const norm = (s) => String(s||'').trim().toLowerCase()
  const nameToId = new Map(), vkToId = new Map()
  const stById = new Map()
  stSnap.docs.forEach(d => {
    const x = d.data() || {}
    stById.set(d.id, x)
    if (x.name) nameToId.set(norm(x.name), d.id)         // 동명이면 last-wins
    if (x.vendorKey) vkToId.set(norm(x.vendorKey), d.id)
  })

  const tsOf = (t) => {
    if (!t) return 0
    if (t.toMillis) return t.toMillis()
    if (typeof t.seconds === 'number') return t.seconds * 1000
    return Number(t) || 0
  }

  // 같은 storeId 에 매핑되는 rooms_biz doc 들
  const groups = {}  // storeId → [ {rbDocId, x, ts, tier} ]
  rbSnap.docs.forEach(d => {
    const x = d.data() || {}
    const bizId = d.id
    let sid = String(x.storeId || '')
    if (!sid || !stById.has(sid)) {
      const gn = norm(x.name || bizId)
      if (nameToId.has(gn)) sid = nameToId.get(gn)
    }
    if (!sid || !stById.has(sid)) {
      if (vkToId.has(norm(bizId))) sid = vkToId.get(norm(bizId))
    }
    if (!sid) sid = bizId
    const pasted = String(x.lastPastedText || x.manualText || x.bannerText || '').trim()
    const r = Number(x.needRooms || 0), p = Number(x.needPeople || 0)
    const tier = pasted ? 3 : (r > 0 || p > 0 ? 2 : 1)
    ;(groups[sid] ||= []).push({
      rbDocId: bizId,
      storeName: stById.get(sid)?.name,
      needRooms: r,
      needPeople: p,
      pastedText: !!pasted,
      updatedAt: tsOf(x.updatedAt),
      tier,
    })
  })

  // ── B. 같은 storeId 에 2개 이상 매핑되는 케이스 (케이스 C / D)
  const dups = Object.entries(groups).filter(([, arr]) => arr.length > 1)
  if (dups.length) {
    console.log(`%c[중복 매핑] storeId 1개에 rooms_biz 여러 개 = ${dups.length}건`, 'color:#ff2e7e;font-weight:bold')
    dups.forEach(([sid, arr]) => {
      console.log(`  ${sid} (${arr[0]?.storeName}):`, arr)
    })
  } else {
    console.log('[중복 매핑] 없음 ✓')
  }

  // ── C. stores.match vs rooms_biz.needRooms 불일치 (케이스 A / B / E)
  const mismatches = []
  stSnap.docs.forEach(d => {
    const x = d.data() || {}
    const sid = d.id
    const matched = groups[sid] || []
    // tier 머지 흉내
    const picked = matched.length
      ? matched.slice().sort((a, b) => b.tier - a.tier || b.updatedAt - a.updatedAt)[0]
      : null
    const storesM = Number(x.match || 0)
    const storesP = Number(x.persons || 0)
    const rbM = Number(picked?.needRooms || 0)
    const rbP = Number(picked?.needPeople || 0)
    const rbActive = !!picked && (picked.pastedText || rbM > 0 || rbP > 0)
    const userShownM = rbActive ? rbM : storesM
    const userShownP = rbActive ? rbP : storesP
    if (userShownM !== storesM || userShownP !== storesP) {
      mismatches.push({
        storeId: sid,
        name: x.name,
        category: x.category,
        stores_match: storesM,
        stores_persons: storesP,
        rb_needRooms: rbM,
        rb_needPeople: rbP,
        rb_pastedText: picked?.pastedText,
        rb_updatedAt: picked?.updatedAt ? new Date(picked.updatedAt).toISOString() : null,
        userShown_match: userShownM,
        userShown_persons: userShownP,
      })
    }
  })
  if (mismatches.length) {
    console.log(`%c[불일치] stores ↔ rooms_biz 값 다름 = ${mismatches.length}건`, 'color:#ff2e7e;font-weight:bold')
    console.table(mismatches)
  } else {
    console.log('[불일치] 없음 ✓')
  }
})()
```

**해석 가이드**:
- `[중복 매핑]` 이 있으면 → **케이스 C 또는 D** 가 그 가게에서 발생 중
- `[불일치]` 가 있으면 → **케이스 A / B / E**. `rb_pastedText` 가 true 이면 외부 텍스트 파싱이 stores 와 다른 값을 만든 것 (케이스 B), false 이면 한 쪽 write 실패 또는 외부 갱신 (케이스 A / E)
- `userShown_*` 가 관리자가 의도한 값과 다르면 → 사용자 화면이 그 값을 보고 있음

### 1-4. 결론 (지표 불일치)

PR #71 은 **같은 storeId 로 매핑된 후의 중복 문서** 문제는 해결. 하지만 다음 3개는 여전히 가능:

1. **저장 부분 실패** (`saveAllMetrics` 의 stores / rooms_biz 순차 호출 중 한쪽 실패)
   - 해결 방향: 트랜잭션화 (`runTransaction`) 또는 batch write
2. **rooms_biz 의 외부 경로 갱신** (ChatBiz, pastedText 파싱 등)
   - 해결 방향: 외부 갱신이 stores 도 함께 갱신하도록 동기화하거나, applyRoomsBiz 에서 `manualSavedAt` (관리자/업체 명시 저장 시점) > 외부 자동 갱신 timestamp 인 경우만 byRb 우선
3. **동명 가게의 name 매칭 실패** (`subscribeRoomsBiz` 의 nameToId last-wins)
   - 해결 방향: rooms_biz 에 항상 `storeId` 필드 보장 (관리자/업체 저장 시 명시), name 매칭은 마지막 폴백

코드 수정은 본 진단 범위가 아니므로 후속 PR 로 분리.

### 2-3. firestore.rules stores 룰 분석 (`firestore.rules:73-86`)

```
match /stores/{id} {
  allow read: if true;
  allow create: if signedIn()
             && request.resource.data.ownerId == request.auth.uid;
  allow update, delete: if signedIn()
             && (
                  resource.data.ownerId == request.auth.uid       // ① 본인 가게
                  || isAdmin()                                     // ② 관리자
                  || (!('ownerId' in resource.data)
                       && request.resource.data.ownerId == request.auth.uid)   // ③ 빈 ownerId 점유
                  || (resource.data.ownerId == null
                       && request.resource.data.ownerId == request.auth.uid)   // ④ null ownerId 점유
                );
}
```

- **create**: `ownerId === auth.uid` 강제. **업체가 본인 uid 로 새 가게 생성 가능** ✓
- **update**:
  - ① 본인 ownerId → OK
  - ② 관리자 → OK
  - ③, ④ **빈 ownerId 점유 룰 — 보안 구멍 (보고서 1-3)**
    - 임의의 로그인 사용자가 `ownerId` 필드 없거나 null 인 stores doc 를 자기 것으로 점유 가능
    - CLAUDE.md Sprint 1 작업 #7 = "stores 빈 ownerId 점유 룰 제거 (firestore.rules:83-84 두 절 삭제)" → **아직 미수정**

### 2-4. "업체가 알아서 입력" 방향 전환 시 필요한 변경점

#### A. createBizAccount 변경 (선택)

- 옵션 2: createBizAccount 가 placeholder stores doc 도 함께 생성 (`approved=false, applyStatus='pending', ownerId=uid, name=storeName`) — 업체가 수정만 하면 되도록
- **추천: 옵션 2** — 계정 생성 시 빈 가게 doc 도 함께 만들면 BizMyStorePage 가 항상 "연결된 가게" 보유 상태로 시작. 업체는 update 만 하면 됨

#### B. BizMyStorePage 신규 생성 흐름 추가 (옵션 1 채택 시)

#### D. 대표이미지 업로드 — 기존 자산 재활용 가능
- `StoreEditPage.vue:413, 800-825` 에 완전한 패턴 존재:
  - `fileToJpegBlob(file, 1280, 0.85)` — 클라이언트 리사이즈 + JPEG 변환
  - Storage path: `stores/{storeId}/thumb-{ts}.jpg`
  - `uploadBytes` → `getDownloadURL` → versioned URL (`?v={ts}`)
  - `stores/{id}.{ thumb, thumbVer, updatedAt }` 업데이트
- **재활용 가능**. BizMyStorePage 에 `<input type="file">` 추가하고 동일 onPick 핸들러 작성
- BizMyStorePage 의 현재 입력은 **URL 문자열 only** (`form.thumb` 직접 입력) → 업체가 외부 호스팅 이미지 URL 을 붙여넣어야 하는 비현실적인 UX

#### E. Storage Rules 점검 필요
- `storage.rules` 파일이 프로젝트에 없음 (`firebase.json` 에 storage 섹션도 없음). Firebase Console 에서 직접 설정한 룰 사용 중일 가능성
- 기본 Firebase Storage 룰 = `allow read, write: if request.auth != null` (인증된 모든 사용자 read/write 가능)
- 그렇다면 업체 / 일반 사용자 누구나 `stores/{any}/thumb-*.jpg` 업로드 가능 → 보안 우려
- **점검 필요**: Firebase Console → Storage → Rules 확인 후 `stores/{storeId}/{file}` write 권한을 `request.auth.uid == get(/databases/.../stores/$(storeId)).data.ownerId` 또는 isAdmin 으로 제한

#### F. firestore.rules stores 룰 강화 (별도 PR)
- **빈 ownerId 점유 절 ③④ 제거** (CLAUDE.md Sprint 1 #7)
- update 룰: 업체가 자기 가게 수정 시 `ownerId/ownerEmail` 필드는 변경 불가 강제 (자기를 다른 사람으로 양도 못하게)
- create 룰: `approved` 필드 강제 false (업체가 자기 가게를 자체 승인하지 못하게)

### 2-5. 변경점 요약 — 우선순위별
