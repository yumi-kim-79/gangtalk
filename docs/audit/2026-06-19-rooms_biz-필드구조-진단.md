## 3. youandme 데이터 해석 — 진짜 원인 (추정 90%)

youandme 의 관찰 데이터:
- `needRooms: 0`, `needPeople: 0`, `matched: 0`
- `need: 6`, `totalNeeded: 18`, `estCurrent: 12`
- `lastPastedText: 실제 데이터`, `lastResetDate: "2026.6.21"`, `updatedAt: 오늘`

### 3-1. 가능 시나리오 (확률 순)

#### 시나리오 A — admin saveAllMetrics 의 빈 시드 일괄 저장 (가장 의심)
- **PR #109 이전** 시점에 관리자가 Tab 2 진입 → 빈 시드 그대로 "일괄 저장"
- `batch.set(rooms_biz, { needRooms:0, needPeople:0, manualSaved:true, ... }, { merge:true })` 발동
- **merge:true** 라 다른 필드 (`need / totalNeeded / lastPastedText / estCurrent / lastResetDate / matched`) 는 보존
- 직후 ChatBiz/Cloud Function 이 needRooms/needPeople 안 갱신하거나 가끔만 갱신 → 0 유지
- 결과: needRooms/needPeople=0 + 다른 필드는 양수/실데이터 보존

#### 시나리오 B — 시트 시스템 일시 중단 + admin 0 박음
- 과거 시트 시스템이 양수 갱신 (need/totalNeeded/estCurrent 채움)
- 시트 시스템 중단 또는 vendors 권한 거부 (현재 의도된 차단) → Cloud Function 호출 안 됨
- admin 이 0 저장 → needRooms/needPeople 만 0

#### 시나리오 C — ChatBiz 와 Cloud Function 의 write 키 불일치
- ChatBiz 가 `youandme` (소문자) doc 에 write
- Cloud Function 이 `vendorId` (대문자 가능) 로 다른 doc 에 write
- 같은 store 의 데이터가 두 doc 으로 분산 → 한 쪽 (youandme) 는 ChatBiz 의 옛 데이터 + admin 의 0 박음 잔존

### 3-2. 결정적 추가 정보 (사용자만 확인 가능)
- `manualSaved` 가 doc 에 있는가? `true` 면 시나리오 A 확정
- `manualSavedAt` 의 시각이 다른 13개 doc 과 같으면 시나리오 A 100%
- 대문자 doc 의 데이터를 보면 시나리오 C 확인 가능

## 4. 대소문자 중복 doc 원인 (추정)

### 4-1. ChatBiz 의 sanitize 분기 (`ChatBiz.vue:467-528`)

```js
function looksLikeAutoId(v) {
  const s = sanitize(v)                       // = toLowerCase
  return /^[a-z0-9]{20,}$/.test(s)           // ⚠️ 소문자만 매칭
}

async function resolveStoreKey() {
  if (!looksLikeAutoId(rawStoreId)) {
    finalStoreId.value = sanitize(rawStoreId) // ← 소문자화
    ...
  }
  // ... vendorKey 추출 시도 ...
  // 실패 시:
  finalStoreId.value = sanitize(rawStoreId)   // ← 소문자화
}
```

**핵심**: `looksLikeAutoId` 의 정규식이 **소문자만 매칭** (`/^[a-z0-9]{20,}$/`). 따라서:
- `6uZOAi...` (대문자 포함) → `looksLikeAutoId=false` → `:475` `sanitize` 적용 → **`6uzoai...` (소문자) doc 에 저장**
- `youandme` (이미 소문자) → `looksLikeAutoId=false` (20자 미만) → `sanitize` 적용 → **`youandme` doc 에 저장** (변화 없음)

### 4-2. useBizActions 의 sanitize (`useBizActions.js:38-42`)

```js
const picked = cand.find(v => !looksRandomId(v))
if (picked) return picked.replace(/\s+/g, '').toLowerCase()
```

→ 마찬가지로 ChatBiz 진입 시 항상 소문자화

### 4-3. Cloud Function 의 write — sanitize 안 함

`functions/index.js:1413`:
```js
const bizId = bizFromRoomId(roomId) || vendorId;
await db.collection("rooms_biz").doc(bizId).set(...)
```

- `vendorId` 가 외부 (시트/매크로) 에서 대문자로 들어오면 **그대로 대문자 doc 에 저장**
- `bizFromRoomId(roomId)` 도 roomId prefix 그대로 — 대소문자 변환 없음

### 4-4. 추정 시나리오 — 대소문자 쌍 발생

1. **t=과거 1**: 시트 시스템이 `vendorId = 6uZOAi...` 로 Cloud Function 호출 → `rooms_biz/6uZOAi...` (대문자) doc 생성
2. **t=과거 2**: 사용자가 ChatBiz 진입 (`?storeId=6uZOAi...`) → `looksLikeAutoId=false` → sanitize → `rooms_biz/6uzoai...` (소문자) doc 생성
3. **결과**: 같은 store 에 대해 두 doc 존재. 각자 별개 write 흐름.

→ **버그/혼란 — 의도 아님**. ChatBiz 의 `looksLikeAutoId` 정규식 누락이 직접 원인.

### 4-5. 사용자 확인 (수동)
- Firestore Console → `rooms_biz` 컬렉션 → `6uZOAi...` 와 `6uzoai...` (소문자) 둘 다 존재하는가?
- 둘 의 데이터 비교 — 어느 쪽이 최근 `updatedAt` 인가?
- 최근 쪽이 active → 다른 쪽은 잔존 데이터

  - 또는 Firestore Console 에서 직접 `needRooms`, `needPeople` 만 양수로 수정 (다른 필드 안 건드림)

### 5-3. ✅ 안전한 정정 절차 (사용자 수동)

1. **Firestore Console** 에서 13개 doc 중 하나 (예: youandme) 열기
2. `manualSaved` 필드 존재 여부 확인:
   - `true` 면 시나리오 A 확정 (admin 빈 시드 일괄 저장)
   - `manualSavedAt` 의 시각이 다른 12개와 같은지 확인 — 같으면 100%
3. 정정 방법 선택:
   - **권장 A**: 업체에게 `/biz/metrics` 에서 본인 가게 양수 입력 요청 → 사용자 화면에 즉시 반영

   - **비권장**: Firestore Console 에서 직접 수정 — 일관성 깨질 위험

### 5-4. 대소문자 중복 정리 (사용자 수동, 신중)

1. **양쪽 doc 의 updatedAt 비교**
2. **최근 doc** (active) 의 ID 를 stores 의 `storeId` 필드와 비교 → 어느 쪽이 정상인지
3. **비-active doc** 의 데이터를 active doc 으로 merge 후 비-active 삭제
4. 또는 시트 시스템 vendorId 를 소문자로 통일 후 단일 doc 으로 정리

### 5-5. 코드 수정 필요? (별도 PR 검토)

- ChatBiz `looksLikeAutoId` 정규식을 `/^[a-zA-Z0-9_-]{20,}$/i` 로 변경 → 대문자 auto-id 도 인식 → resolveStoreKey 시도 → vendorKey 추출
