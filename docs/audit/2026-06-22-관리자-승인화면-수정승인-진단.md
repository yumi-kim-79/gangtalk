## 0. TL;DR

- **현재 승인대기 카드는 클릭 액션 없음** (`StoresManagePage.vue:159-178`). 액션 버튼 3개(승인/거절/삭제) 만 노출. 입력 내용 검토/수정 UI 부재
- `approveStore` (`:807-820`) = `updateDoc(stores, { approved:true, applyStatus:'approved', 'exposure.gangtalk':true, approvedAt, updatedAt })` 단순 update
- `rejectStore` (`:821-832`) = `applyStatus:'rejected'` 만 set. stores/users/Auth 모두 보존 (재검토 가능)
- 별도 신청 삭제 = `deleteStore` → `deleteStoreFull` Cloud Function (Storage / rooms_biz / ratings / favorites / marketingRefs / stores 정리. users/Auth 보존)
- 업체 계정까지 완전 삭제 = `deleteBizAccount` (`BizAccountsPage` 만 — 승인 화면에 없음)
- `/biz-signup` 가 저장하는 사용자 입력 필드 = 11개 (`name/phone/category/region/desc/detailDesc/address/hours/closed/wage/wageType`). thumb=''
- users(type=company) 추가 정보: profile.email (=ownerEmail), profile.phone (휴대폰 — SMS 인증값), profile.nickname (=storeName)
- **이미지 정책**: storage.rules `isStoreOwner` 가 `isAdmin() OR ownerId==auth.uid` → 관리자도 업로드 가능. 단 현재 정책은 "업체가 승인 후 BizMyStore 에서 업로드" → 승인 모달에서 관리자가 강제 업로드 필요 없음 (옵션으로만 제공 가능)
- **권장 설계**:
  - 카드에 "검토" 버튼 또는 카드 전체 클릭 → **검토 모달** 오픈
  - 모달: 신청자 정보(읽기) + 업소 필드 폼(미리 채움, 수정 가능) + 거절 사유 textarea (선택)
  - 푸터 3 버튼: **저장만** (pending 유지) / **저장+승인** (한 트랜잭션 update) / **거절** (사유 함께)
  - 폼은 BizSignupPage 의 11 필드와 같은 구성 — 인라인 복붙 패턴 (PR #111 와 정합, 회귀 위험 차단)
  - 이미지는 모달에서 제외 (URL 입력만 옵션). 파일 업로드는 BizMyStore 그대로

## 1. 현재 승인 흐름 정확한 매핑

### 1-1. pendingStores computed (`StoresManagePage.vue:434-445`)
```js
const isPending = (s) => {
  const a = String(s?.applyStatus || '').toLowerCase()
  return ['pending','대기','waiting','신청','검토중'].includes(a)
}
const pendingStores = computed(() => stores.value.filter(isPending))
```
- `applyStatus` 한 글자 매칭. `approved:false` 단독은 pending 아님 (rejected 도 approved:false 라 분리 필요)
- `/biz-signup` 가입 → `applyStatus:'pending'` 명시 → 정확히 통과

### 1-2. Tab 3 마크업 (`StoresManagePage.vue:153-180`)
```html
<ul class="adm-store-list" v-if="pendingStores.length">
  <li v-for="s in pendingStores" :key="s.id" class="adm-store-row">
```

### 1-3. approveStore (`:807-820`)
```js
async function approveStore(s){
  if (!confirm(`'${s.name || s.id}' 을(를) 승인하시겠습니까?`)) return
  await updateDoc(doc(fbDb, 'stores', s.id), {
    approved: true,
    applyStatus: 'approved',
    [`exposure.gangtalk`]: true,
    approvedAt: serverTimestamp(),
    updatedAt: serverTimestamp(),
  })
}
```
- 단순 confirm 후 update. 입력 검증/수정 단계 없음 → **승인 시점에 잘못된 데이터도 그대로 노출됨**
- 5 필드 update. 사용자 입력은 건드리지 않음 (의도)

### 1-4. rejectStore (`:821-832`)
```js
async function rejectStore(s){
  if (!confirm(`'${s.name || s.id}' 신청을 거절하시겠습니까?`)) return
  await updateDoc(doc(fbDb, 'stores', s.id), {
    approved: false,
    applyStatus: 'rejected',
    rejectedAt: serverTimestamp(),
    updatedAt: serverTimestamp(),
  })
}
```
- **stores/users/Auth 보존** — 재검토 가능. 거절 사유 필드 없음 (현재)
- 사용자 화면 효과: `MainPage.isApproved` 가 false 반환 → 미노출
- 단 `applyStatus` 가 'rejected' 라 `isPending` 도 false → **Tab 3 에서도 사라짐** → 거절된 신청을 다시 보려면 별도 탭 필요 (현재 없음)

### 1-5. deleteStore (`:845-`)
- Cloud Function `deleteStoreFull` 호출 (`functions/index.js:2631`)
- 정리 6 단계: Storage / rooms_biz / ratings / favorites / `config/marketing` 인덱스 / stores doc
- **users / Auth 보존** — 업체가 다른 stores 가질 수 있음
- 2중 confirm + 중복 클릭 방지

### 1-6. 업체 계정 완전 삭제 = `deleteBizAccount` (별도 페이지)
- `BizAccountsPage.vue:174, 384` — `fnDeleteBiz({ uid })` 호출
- Cloud Function (`functions/index.js:2791`) 가 ① `_deleteStoreFullCore` 로 ownerId 매칭 stores 전부 삭제 → ② `users/{uid}` 삭제 → ③ `auth.deleteUser(uid)`

- 승인 화면에서 호출 안 함 (의도 — 검토 단계에서 계정까지 날리는 건 과함)

## 4. 거절 처리 — 현재 + 확장

### 4-1. 현재 (`rejectStore`)

- stores doc / users / Auth 보존 → 업체는 본인 정보 그대로, 재신청 (수정 후 다시 pending) 가능

### 4-2. 권장 확장
- **거절 사유 필드** `rejectedReason` 추가 (string, 선택 — admin 입력)
  - users 측 표시 인프라는 별도 PR (BizMyStorePage 에 "거절됨 + 사유" 안내 추가)
- **거절 탭** 신설 (옵션, PR e 또는 별도):
  - `tabs` 에 `{ key:'rejected', label:'거절', count: ... }` 추가
  - `applyStatus === 'rejected'` filter
  - 거절된 신청 재검토 / 사유 수정 / 재승인 가능
- **자동 알림** (이메일/SMS/in-app):
  - Cloud Function 신규 (`onStoreApproved` trigger) — 본 PR 범위 밖
  - 우선은 admin 이 별도 채널 (전화/카톡) 로 안내

### 4-3. 완전 삭제 (스팸/허위 신청)

## 5. 이미지 정책

### 5-1. storage.rules 측 (`storage.rules:49-52`)
```
match /stores/{storeId}/{allPaths=**} {
  allow read: if true;
  allow write: if (isAdmin() || isStoreOwner(storeId)) && isImage() && sizeOk();
}
```
- **`isAdmin()` 분기로 관리자도 업로드 가능** (10MB, 이미지 타입 제한)
- isStoreOwner 는 stores doc 존재 + ownerId 매칭 — BizSignupPage 가 stores doc 먼저 만든 후라 admin 우회 없이도 통과 가능 (가입자 본인 시점)

### 5-2. 현재 정책 — 업체가 BizMyStore 에서 업로드
- BizSignupPage 는 `thumb:''` 로 저장 (이미지 제외) — PR #93 결정 (의도)
- 업체가 승인 후 로그인 → BizMyStorePage → `fileToJpegBlob + uploadBytes + getDownloadURL` (`:438-460`)
- 업로드 경로: `stores/{storeId}/thumb-{ts}.jpg` (자기 storeId 만 사용)
- 결과 URL 을 versioned (`?v=ts`) 로 form.thumb 에 set → 저장 시 stores.thumb 갱신

### 5-3. 승인 모달에서 이미지 처리 — 권장: 제외 또는 URL 만
- **권장: 폼에서 이미지 항목 제외**
  - 신청 시점에 이미지가 없는 게 기본 (BizSignupPage `thumb:''`)
  - 승인 후 업체가 직접 업로드 → 자기 가게라 책임 명확
  - 관리자가 임의 이미지 강제하는 건 부적절
- **옵션: "대표 이미지 URL" 텍스트 입력만 허용** (createStore 모달 패턴, PR #111)
  - 관리자가 외부 URL 알고 있으면 입력 가능 (CDN 등)
  - 파일 업로드 UI 는 제공 안 함 (관리자가 실수로 부적절 이미지 올릴 위험 차단)
- **파일 업로드 추가 가능성 (옵션 분리)**:
  - storage.rules 통과 가능 (관리자 권한)
  - BizMyStorePage 의 `onPickImage` 코드 재사용 가능
  - 단 검토 단계의 admin 책임 범위 확장 → 본 PR 권장 안 함, 별도 PR

## 7. 주의점 / 회귀 위험

### 7-1. 동시 수정 race
- admin 이 검토 모달 열고 수정 중인데 업체가 BizMyStorePage 에서 같은 stores 수정 → 마지막 쓰기가 이김 (last-wins)
- 일반적 패턴, 별도 lock 불필요 — 단 검토 모달에 진입 시점의 데이터 보존 (`editForm = { ...s }`) 시 onSnapshot 이 도중에 stores 갱신해도 폼은 그대로
- 저장 충돌 발생 시 `serverTimestamp()` 만으로 충분

### 7-2. SMS 인증 비검증
- BizSignupPage 는 SMS 인증 통과한 휴대폰만 가입 허용
- admin 이 검토 모달에서 stores.phone (매장 전화) 또는 users.profile.phone (휴대폰) 수정 시 SMS 재인증 안 함 — admin 권한이므로 의도된 동작
- 단 users.profile.phone 수정은 본 PR 범위 밖 (stores 만 수정)

### 7-3. ownerId 변경 차단 일관성
- 폼에서 ownerId 노출 안 하므로 변경 0 (안전)
- payload 구성 시 명시적 omit 권장 (이중 안전): `const { ownerId, ownerEmail, applyStatus, approved, ...rest } = form; updateDoc(..., rest)`

### 7-4. 거절 사유 신규 필드 영향
- `rejectedReason` 필드 추가 → MainPage / BizMyStorePage 등 사용자 화면에서 표시 가능
- 현재는 어디서도 표시 안 함 → 추가 후에도 무해 (Firestore 가 새 필드 자동 처리)
- 단 BizMyStorePage 에 "거절됨 + 사유" 안내 추가는 별도 PR (UX 정합)

### 7-5. 모달 진입 시 카드 전체 클릭 vs 별도 버튼
- **별도 "검토" 버튼 권장** — 카드 전체 클릭은 실수로 모달 띄울 위험. PC 마우스 호버에 어색
- 또는 카드의 `<strong>{{ s.name }}</strong>` 부분만 클릭 가능하게 (보조 트리거)

### 7-6. Tab 3 분류 충돌
- 검토 모달에서 "거절" → `applyStatus:'rejected'` → 즉시 Tab 3 에서 사라짐
- "저장+승인" → `applyStatus:'approved'` → Tab 3 에서 사라지고 Tab 1 (노출 관리) 에 자동 등장
- "저장만" → `applyStatus:'pending'` 유지 → Tab 3 에 그대로 (수정사항만 반영)
- 사용자 입장 자연스러움. 단 거절된 신청 재검토 동선 부재 (4-2 의 거절 탭 신설 권장)

### 7-7. createStore 모달과의 시각 구분
- 둘 다 같은 모달 클래스 (`adm-modal-mask`, `adm-modal-wide`) 사용 → 혼동 가능
- 헤더 타이틀로 구분: "+ 새 출근업소 등록" vs "업소 등록 신청 검토"
- 헤더 색상/아이콘으로 추가 구분 가능 (선택)

### 7-8. partners 영향 없음
- 본 PR 범위는 stores(출근업소) 만 — partners(제휴처) 영향 0
- CLAUDE.md 의 일관된 정책 (deleteStoreFull / deleteBizAccount 도 partners 안 건드림)
