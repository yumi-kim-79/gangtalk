**날짜**: 2026-07-02
**대상 브랜치**: main (진단 전용)
**증상**: 관리자 `/admin/top5` (가게찾기 Top5 관리) 에서 하퍼 탭 → "+ 업소 추가" → "쎄미" 검색 → **검색 결과 없음**

**결론(요약)**: 검색 코드 자체는 **정상**이고 매우 관대함. "쎄미"/"퍼블릭" 이 안 잡히는 원인은 **stores 컬렉션에 그 업소가 아예 없거나** (미등록), **500개 limit 를 초과해 잘렸을** 가능성이 유력. **코드 수정 필요 없음** — 데이터 확인이 먼저.

## 1. Top5 관리 페이지 검색 로직 (파일:라인)

**파일**: `src/pages/admin/Top5ManagePage.vue`

### 1-1. 검색 후보를 어디서 가져오는가

**stores 컬렉션 전체를 onSnapshot 구독 (line 128–133)**:
```js
unsubStores = onSnapshot(
  query(collection(fbDb, 'stores'), limit(500)),
  (snap) => {
    stores.value = snap.docs.map(d => ({ id: d.id, ...d.data() }))
  },
)
```

- **컬렉션**: `stores` (제휴처 `partners` 가 아님 — 출근업소 전용)
- **한도**: `limit(500)` — **첫 500 문서만 로드**
- **필터**: 없음 — 승인 상태/노출 상태/카테고리 무관하게 **전부** 로드
- **정렬**: 지정 없음 → Firestore 기본 doc ID 순 (auto-id 는 시간 순서 아님, ID 문자열 정렬)

### 1-2. 검색 매칭 방식 (line 221–231)

```js
const searchResults = computed(() => {
  const q = searchQ.value.trim().toLowerCase()
  if (!q) return []
  return stores.value.filter(s => {
    return (
      String(s.name || '').toLowerCase().includes(q) ||
      String(s.region || '').toLowerCase().includes(q) ||
      String(s.category || '').toLowerCase().includes(q)
    )
  }).slice(0, 30)
})
```

- **대상 필드 3개**: `name` / `region` / `category`
- **매칭**: `String.includes(q)` — **부분 일치** (앞뒤 어디든 포함되면 hit)
- **대소문자**: 양쪽 `.toLowerCase()` — **무관**
- **공백/특수문자**: `trim()` 만 (양끝 공백 제거). 중간 공백은 원문 그대로 → "쎄 미" 로 저장돼 있으면 "쎄미" 검색으로 안 잡힘 (부분 일치는 되지만 중간 공백 자체가 다르므로)
- **결과 상한**: `slice(0, 30)` — 최대 30건 표시

### 1-3. 현재 카테고리(하퍼)의 업소만 후보로 거르는가

**❌ 아니다**. `searchResults` 는 `catKey.value` 를 사용하지 않음.
- **하퍼 탭에 있어도 "쩜오" / "바" 카테고리 업소가 검색에 잡힘.**
- 필터가 카테고리로 좁혀지지 않음 → 다른 카테고리 업소 미노출 이슈는 배제.
- 확인 방법: 하퍼 탭에서 다른 카테고리에 확실히 존재하는 업소명(예: 텐카페 계열)을 검색 → 잡히면 카테고리 무관 검색이 사실로 확인됨.

### 1-4. 승인/노출 상태로 후보를 거르는가

**❌ 아니다**. `searchResults` 에 `approved` / `applyStatus` / `exposure.gangtalk` / `exposure.dashboard` 참조 0.
- **미승인(applyStatus:'pending') / 노출 OFF / 만료된 업소도 검색에 잡힘.**
- rooms_biz 미매핑, 이미지 없음 여부도 무관.
- Firestore 룰 (`firestore.rules:108-109`) `allow read: if true` — 관리자든 아니든 stores read 공개. 룰로 차단 안 됨.

### 1-5. 참고 — 제휴관 Top5 (`PartnerTop5ManagePage.vue`) 는 다름

`src/pages/admin/PartnerTop5ManagePage.vue` 는 **현재 카테고리의 partner 만 후보로 제한** (설계 의도). 본 진단 대상은 가게찾기 Top5 (`Top5ManagePage.vue`) 이며, **stores 는 카테고리 미제한** — 위 로직 그대로.

## 2. "쎄미" 안 잡히는 원인 후보 (구분)

**결정**: 검색 코드는 위와 같이 매우 관대함 (`name.includes('쎄미') || region.includes('쎄미') || category.includes('쎄미')`). "쎄미" 가 안 잡히려면 다음 중 하나가 사실.

### 원인 (A) — **stores 컬렉션에 name="쎄미…" 문서가 아예 없음 (미등록)** — 🟢 **가장 유력**

- 사용자의 자기 진단 ("미등록 업소라") 과 일치.
- 확인 방법: §3 참고.
- 조치: **먼저 등록**. 관리자 흐름 3 가지 중 택 1
  1. 업체가 `https://www.gangtox.com/biz-signup` 자가가입 (SMS 인증 + 업소 정보 입력) → 관리자 `/admin/stores` Tab 3 승인
  2. 관리자가 `/admin/biz-accounts` 에서 업체 계정 생성 → 그 업체가 `gangtalk815.com/biz/my-store` 에서 스스로 등록
  3. (레거시 A/B 경로는 PR #116 로 제거됨. 관리자 직접 CRUD 는 `BizAccountsPage` "업소 연결" 기능만 잔존 — 이미 만든 stores 에 ownerEmail 부여용)

### 원인 (B) — **stores 컬렉션 문서 수 > 500 이라 "쎄미" 가 limit 뒤로 잘림** — 🟡 가능

- `limit(500)` 은 Firestore 서버 정렬 (doc ID 오름차순) 기준 앞 500 만 스냅샷에 실림.
- doc ID 는 auto-id (base62 랜덤). 시간 순서가 아니라서 최근 등록이 앞/뒤 어디든 갈 수 있음.
- 확인 방법: Firebase Console → Firestore → `stores` 컬렉션 문서 수 확인.
  - 500 미만 → 이 원인 배제.
  - 500 이상 → limit 조정 필요 (예: 1000, 또는 서버 쿼리 필터 도입).
- **조치 방향** (본 PR 아님, 별도 실행 PR 필요 시):
  - 옵션 1: `limit(500)` → `limit(2000)` 상향 (초기 500KB 정도 페이로드 → 2MB, 관리자 UX 안 아프면 OK)
  - 옵션 2: 검색어가 있을 때만 즉시 서버 쿼리로 재조회 (Firestore 는 부분 일치 검색 미지원 → prefix 매치만 가능. 실무는 클라 필터 유지가 자연스러움)
  - 옵션 3: 관리자 페이지에 "이 카테고리(하퍼) 만 로드" 옵션 추가 → 필요 문서 대폭 감소

### 원인 (C) — **name 필드가 아닌 다른 필드에 저장됨** — 🔴 매우 낮음

- 코드 사실:
  - 자가가입 (`src/pages/BizSignupPage.vue:520`): `stores/{id}.name = form.storeName`
  - MainPage 등 사용자 화면 표시도 `s.name`
- name 필드 존재 확신. 다른 필드명 (예: `storeName`, `displayName`) 에 저장될 경로 없음.

### 원인 (D) — **name 값에 중간 공백/특수문자 삽입 ("쎄 미" / "쎄·미" 등)** — 🟡 가능

- `.includes(q)` 는 문자열 부분 일치라 중간 공백을 넘지 못함:
  - "쎄미" 검색 → 저장값 "쎄미강남" ✅ 잡힘 / "쎄 미" ❌ 안 잡힘 / "쎄미(강남)" ✅ 잡힘 / "SEMI" ❌ (한→영 표기 다름)
- 확인 방법: §3 의 Firestore Console 조회에서 이름 원문 확인.
- 조치: 등록 시 공백 정규화 or 검색 로직에 `q.replace(/\s+/g, '')` 대칭 정규화 추가 — 별도 PR.

### 원인 (E) — **Firestore 캐시 stale + onSnapshot 이 아직 서버 fresh 수신 못 함** — 🔴 매우 낮음

- 최근 (배포 직후) 등록된 업소를 즉시 검색하려는 경우 로컬 캐시 우선 반환 후 서버 fresh 병합 지연 가능.
- 확인 방법: 하드 새로고침 (Ctrl+Shift+R) 후 재검색.
- 조치: 자연스레 해소됨. 코드 수정 불필요.

## 4. stores 에 쎄미 있는 경우 — 시나리오별 해석

Firestore Console 에서 "쎄미" 문서를 찾았다면:

| 필드 상태 | 의미 | 조치 |
|---|---|---|
| `approved: true` + `exposure.gangtalk: true` | 이미 완전 승인+노출 | 검색은 잡혀야 정상 → 실제로 다시 검색해 볼 것. 여전히 안 잡히면 원인 (B) 500개 잘림 확실 |
| `approved: true` + `exposure.gangtalk: false` | 승인됐지만 가게찾기 노출 OFF | 검색은 여전히 잡혀야 정상 (필터에 exposure 조건 없음). 안 잡히면 (B) |
| `approved: false` + `applyStatus: 'pending'` | 승인 대기 중 | 검색은 여전히 잡혀야 정상. 안 잡히면 (B) |
| `applyStatus: 'rejected'` | 거절됨 | 검색은 여전히 잡혀야 정상 (룰/필터 무관). 안 잡히면 (B) |
| 문서 자체 없음 | 미등록 | **원인 (A) 확정** — 등록 필요 |

즉 검색 로직에 상태 필터가 아예 없어서, 문서만 존재하면 상태 무관 잡히는 게 정상. 안 잡히는 유일한 이유는 **문서 부재 or limit(500) 잘림**.

## 5. 검색이 너무 좁게 걸러 정상 업소를 누락하는가

**❌ 아니다**. 오히려 반대로 검색 필터가 **너무 관대** 함:

- 승인 상태 무관 (거절된 것도 잡힘)
- 노출 상태 무관 (OFF 인 것도 잡힘)
- 카테고리 무관 (하퍼 탭에서 다른 카테고리도 잡힘)
- 대소문자 무관
- 부분 일치 (앞뒤 어디든)

**개선 방향 (관대함이 부담이면 별도 PR)**:
- 승인+노출된 업소만 검색 (실제로 Top5 는 노출용이므로 미승인 추가는 무의미)
- 현재 카테고리 업소만 검색 (하퍼 탭에서는 하퍼 업소만 — PartnerTop5 패턴 참고)

단 **이 개선을 지금 하면 "쎄미" 안 잡힘 이슈 재발** — 등록 직후 승인 전에는 검색 안 됨. 등록 이슈부터 해결 후 별도로 판단.
