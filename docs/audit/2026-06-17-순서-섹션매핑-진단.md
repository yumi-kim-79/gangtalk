## 0. 핵심 결론

**"강남 인기 업소" 섹션은 homeOrder 와 정확히 연결된 섹션이 맞다.** 코드 흐름 자체는 정상이므로, 순서가 안 맞는다면 원인은 **데이터 또는 배포 상태** 측 4개 중 하나다 (가능성 순):

1. 🔴 **PR #68 (캐시 수정) 가 아직 사용자 도메인에 배포 안 됨** — 가장 가능성 높음. 머지는 됐지만 `firebase deploy --only hosting:prod` 실행 안 했거나, CDN/브라우저 캐시에 옛 JS 가 남음
2. 🟠 **homeOrder 의 ID 일부가 filter (`exposure.gangtalk` false / `applyStatus` pending 등) 에 걸려 빠짐** — admin 이 reorder 한 19개 중 일부만 사용자에게 노출되고, 나머지 자리를 homeOrder 에 없는 다른 stores 가 차지
3. 🟡 **homeOrder 누적 stale ID** — `reorderApproved` 가 비-approved ID 를 뒤에 보존. Top 20 안에 stale 이 끼면 어색한 위치
4. 🟢 **ID 자체는 매칭됨** (코드상 양쪽 모두 `String(s.id)` 정규화) — 형식 mismatch 는 아님

## 2. `filtered` computed 의 정확한 동작 (`MainPage.vue:1739-1760`)

```js
const filtered = computed(()=>{
  const base = baseFiltered()
  if (near.value.enabled){           // ← 항상 false (코드 어디서도 true 설정 안 함)
    return base.slice().sort((a,b)=> distance(a) - distance(b))
  }
  if (!homeOrder.value.length) return base   // ← homeOrder 비어 있으면 무정렬
  const pos = new Map(homeOrder.value.map((id,idx)=>[String(id), idx]))
  return base.slice().sort((a,b)=>{
    const ai = pos.has(String(a.id)) ? pos.get(String(a.id)) : Infinity
    const bi = pos.has(String(b.id)) ? pos.get(String(b.id)) : Infinity
    if (ai !== bi) return ai - bi
    return 0
  })
})
```

- `homeOrder.value` 가 빈 배열 ([]) 이면 `base` 그대로 반환 (Firestore `updatedAt desc` 순서)
- `homeOrder.value` 가 차 있으면 그 순서대로 정렬
- homeOrder 에 없는 ID 는 `Infinity` 위치 → 정렬 결과 뒤로 밀림 + 그들끼리는 원래 (updatedAt desc) 순서 유지

→ 코드 로직 자체는 **정상**. homeOrder 가 제대로 들어오기만 하면 admin 저장 순서 그대로 표시.

## 4. `baseFiltered` 의 사전 필터 (`MainPage.vue:1716-1736`)

`filtered` 가 sort 하기 전에 `baseFiltered` 가 먼저 stores 를 걸러냄:

| 필터 | 코드 | 통과 조건 |
|------|------|---------|
| `okExpose` | `exposedHere(s)` (`:1708`) | `s.exposure.gangtalk` 가 `false` 가 아닐 때 (없거나 true) |
| `okApproved` | `isApproved(s)` (`:1664` 부근) | `applyStatus = 'approved'` 또는 `approved = true`, 또는 둘 다 미설정 (레거시) |
| `okPeriod` | `isActiveAd(s)` (`:1698`) | `adStart`/`adEnd` 둘 다 비어 있거나, 현재 시각이 기간 안 |
| `okT` | `type.value` 카테고리 매칭 | `'all'` 또는 같은 카테고리 |
| `okM` | `macro.value` 지역 매칭 | `'all'` 또는 같은 지역 |
| `okQ` | 검색어 | 없거나 이름 부분 일치 |
| `okNear` | `near.value.enabled` | dead — 항상 true |

→ **homeOrder 의 19개 중 위 필터 어느 하나라도 못 통과한 ID 는 사용자 화면에 안 나옴.** 그 빈 자리를 homeOrder 에 없는 다른 stores 가 채움 → 사용자 입장에선 "어, 왜 내가 앞에 둔 게 안 보이지?" → "순서가 다르다" 로 인식.

특히 의심:
- **`exposure.gangtalk`**: admin Tab 1 에서 토글로 노출 on/off. 저장은 `stores/{id}.exposure.gangtalk`. **admin 이 순서만 바꾸고 노출을 켜지 않은 항목** 은 `false` → 사용자 화면에서 빠짐
- **`adStart/adEnd`**: admin Tab 1 의 15/30/60/90일 버튼으로 설정. **만료된 항목** 은 `isActiveAd` 가 false → 빠짐
- **`applyStatus`**: admin 이 승인 안 한 항목 (pending) 은 빠짐

## 5. `homeOrder` 의 stale ID 누적 (의심 #3)

`StoresManagePage:reorderApproved` (`:255-266`):
```js
const displayIds = orderedApproved.value.map(s => String(s.id))
const approvedIdSet = new Set(approvedStores.value.map(s => String(s.id)))
const others = homeOrder.value.filter(id => !approvedIdSet.has(String(id)))
homeOrder.value = [...displayIds, ...others]
```

- `displayIds`: 현재 admin 이 보는 승인 업소들의 새 순서
- `others`: **현재 승인 안 된 stale ID** — 이전 homeOrder 에서 남은 잔재

저장된 homeOrder = `[새 승인 순서] + [stale ID 들]`. 사용자 측에서:
- 새 승인 순서 안의 ID 가 filter 통과하면 → 정상 위치
- stale ID 가 사용자 측 filter 를 통과해버리면 → top 20 안에 들어옴 (의외의 위치)

확률은 낮지만 시간 지나면 누적되는 디버그 가치 있음.

### 단계 2 — homeOrder 데이터 확인
1. DevTools 콘솔에서 직접:

### 단계 3 — filter 통과 확인 (admin 페이지에서)
1. `/admin/stores` Tab 1 진입
