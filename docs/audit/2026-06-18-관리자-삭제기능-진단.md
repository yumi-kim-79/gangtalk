# 관리자 페이지 업체 계정 / 가게 삭제 기능 추가 — 사전 진단

**날짜**: 2026-06-18
**범위**: gangtalk815 관리자 빌드. 가게(stores) + 업체 계정(users.type='company') 삭제 기능 추가 전 준비
**전제**: 진단 전용. 코드/룰/함수 수정·PR·배포 없음.
**핵심 결론**:
1. 관리 페이지 2개 (`StoresManagePage` 가게 / `BizAccountsPage` 업체 계정) — 분리 명확. 각 페이지에 삭제 버튼 추가
2. stores 삭제 시 **5개 연관 데이터 정리 필요** (rooms_biz 본 doc + 서브컬렉션, ratings, favorites, Storage `stores/{id}/*`, config/marketing 참조)
3. firestore.rules 의 stores/users/favorites/rooms_biz delete 룰은 **isAdmin 허용** — 단 **`stores/{id}/ratings/{uid}` 룰에 isAdmin 분기 없음** (관리자가 ratings 삭제 못 함)
4. **Auth 계정 삭제는 Admin SDK 필요** — 신규 Cloud Function `deleteBizAccount` 작성 필요 (createBizAccount 와 같은 패턴)
5. 2중 확인: 공용 모달 컴포넌트 **없음** — 옵션 A (`confirm()` 2회) 또는 옵션 B (가게명/이메일 typing 확인 커스텀 모달)

## 2. stores 삭제 시 연관 데이터 — 정리해야 할 것 5종

### 2-1. **`rooms_biz/{storeId}` 본 doc + 서브컬렉션**

`firestore.rules:151-162`:
- `rooms_biz/{storeId}`: 현황판 지표 미러
- `rooms_biz/{storeId}/{sub=**}`: 채팅 메시지/참여자 등

안 지우면: **유령 데이터 — 사용자 현황판이 `subscribeRoomsBiz` 로 모든 rooms_biz 구독 시 이미 삭제된 store 의 지표가 매칭 시도** (`MainPage.vue:1349-1377` 의 storeId 매핑 로직). 단 stores 의 doc 가 없으면 `_hasStoreId` false → 매핑 안 됨. **무해하지만 잔존**.

### 2-2. **`stores/{storeId}/ratings/{uid}` 서브컬렉션**

별점 데이터. 사용자가 별점 매긴 모든 uid 의 doc.

안 지우면: store 삭제 후에도 ratings 잔존. 새로 같은 storeId 발급 시 옛 별점이 보일 위험 (현실적으론 storeId 가 auto-id 라 충돌 거의 없음). **무해하지만 잔존**.

### 2-3. **`favorites where targetId == storeId && type == 'store'`**

루트 favorites 컬렉션. 사용자들의 즐겨찾기.

안 지우면: 사용자 마이페이지 즐겨찾기 목록에 **`stores/{deletedId}` 가 없는 doc** 가 hydrate 실패 → `FavoritesPage.vue:251 hydrateRefs` 의 `s.exists()===false` 분기 → 원본 필드만 표시 (이름 없음 등) → **사용자 경험 저하**.

쿼리: `query(collection(db, 'favorites'), where('targetId', '==', storeId), where('type', '==', 'store'))` 후 일괄 삭제.

### 2-4. **Storage `stores/{storeId}/*` 이미지**

`storage.rules:49-52` write 권한 = isAdmin 또는 isStoreOwner → **관리자 삭제 가능**.

방법:
- (a) 클라이언트: `listAll()` → 각 파일 `delete()` (수십 개 파일 시 느림)
- (b) Cloud Function: `admin.storage().bucket().deleteFiles({ prefix: 'stores/{id}/' })` (더 빠름 + 안전)

안 지우면: **Storage 비용 누수**. 보안: write 차단되지만 read 는 public.

### 2-5. **`config/marketing.homeOrder` / `topRanks` / `listOrders` 참조**

관리자가 가게 노출 순서 설정한 ID 배열.

안 지우면: 사용자 화면에서 `homeOrder` 에 있는 deleted storeId 가 `stores` 목록에 없음 → `filtered computed` (`MainPage.vue:1798-1818`) 가 자동으로 제외 (자연 무시).

→ **자동 무시되어 무해. 단 array 정리 권장** (불필요한 string 잔존).

### 2-6. 정리 순서 권장 (의존성 역순)

```
1. Storage stores/{id}/* 전체 삭제
2. rooms_biz/{id} 서브컬렉션 → rooms_biz/{id} 본 doc
3. stores/{id}/ratings/{uid} 서브컬렉션 (모든 uid)
4. favorites where targetId==storeId 일괄 삭제
5. config/marketing.homeOrder/topRanks/listOrders 에서 storeId 제거
6. stores/{id} 본 doc 삭제
```

**원자성 보장 불가** (Firestore 트랜잭션은 단일 컬렉션 < 10 doc 제약, Storage 는 별개 시스템). → **Cloud Function 으로 처리 권장** — 일관된 순서 + 에러 핸들링 + 부분 실패 로깅

## 3. 업체 계정 삭제 — Cloud Function 필수

### 3-1. Firebase Auth 사용자 삭제

**클라이언트 SDK 의 `deleteUser()` 는 본인만 삭제 가능**. 다른 사용자 삭제 → `permission-denied`.

→ **Admin SDK 필요** = Cloud Function `deleteBizAccount` 신규 작성.

### 3-2. `createBizAccount` 의 역연산

`functions/index.js:2447 createBizAccount` 가 하는 일:
1. `admin.auth().createUser({ email, password, ... })`
2. `users/{uid}` doc 생성 (type='company', accountKind='storeOwner')
3. storeId 있으면 `stores/{storeId}.{ownerId, ownerEmail}` 매핑

→ `deleteBizAccount` 의 역연산:
```js
exports.deleteBizAccount = onCall({ cors: ADMIN_CORS }, async (req) => {
  assertCallerIsAdmin(req)
  const uid = safeStr(req.data?.uid)
  if (!uid) throw new HttpsError('invalid-argument', 'uid required')

  // 1) 연결된 stores 처리 (ownerId 제거 또는 삭제)
  const storesSnap = await db.collection('stores').where('ownerId', '==', uid).get()
  for (const doc of storesSnap.docs) {
    // 옵션 A: ownerId 만 null 로 (가게는 보존)
    await doc.ref.update({ ownerId: null, ownerEmail: null })
    // 옵션 B: 가게도 함께 삭제 (deleteStore 함수 호출 — §2 의 흐름)
  }

  // 2) users doc 삭제
  await db.collection('users').doc(uid).delete()

  // 3) Auth 사용자 삭제
  await admin.auth().deleteUser(uid)

  return { ok: true }
})
```

### 3-3. 연결된 store 처리 옵션

| 옵션 | 동작 | 권장 시점 |
|---|---|---|
| A: ownerId 만 null | 가게는 살리되 소유자 끊음. 다른 업체 계정에 재연결 가능 (`linkStoreToBiz`) | 가게는 계속 운영, 업체만 교체 |
| B: 가게도 함께 삭제 | 가게 + 연관 데이터 (§2) 전부 정리 | 가게 자체 폐업 |

→ 관리자 UI 에 옵션 선택 라디오 추가 권장.

## 4. 권한 룰 현황 + 필요 변경

### 4-1. 현재 룰 (firestore.rules)

| 컬렉션 | delete 권한 | 관리자 OK? |
|---|---|---|
| `stores/{id}` (`:114-118`) | `signedIn() && (ownerId==auth.uid \|\| isAdmin())` | ✓ |
| `users/{uid}` (`:69`) | `isOwner(uid) \|\| isAdmin()` | ✓ |
| `favorites/{favId}` (`:87-88`) | `signedIn() && (ownerId==auth.uid \|\| isAdmin())` | ✓ |
| `rooms_biz/{storeId}` (`:151-157`) | `isAdmin() \|\| (signedIn && owner)` | ✓ |
| `rooms_biz/{storeId}/{sub=**}` (`:159-162`) | `isAdmin()` | ✓ |
| **`stores/{storeId}/ratings/{uid}`** (`:141-144`) | **`isOwner(uid)`** (← admin 분기 없음!) | **✗** |

### 4-2. 필요한 룰 변경 — 1건

```diff
  match /stores/{storeId}/ratings/{uid} {
    allow read: if true;
-   allow create, update, delete: if isOwner(uid);
+   allow create, update, delete: if isOwner(uid) || isAdmin();
  }
```

이유: stores 삭제 시 ratings 서브컬렉션 전체 삭제하려면 관리자 권한 필요. 현재는 본인만 삭제 가능 → 관리자가 deleteStore 호출 시 ratings 정리 실패.

### 4-3. Storage 룰 — 변경 불필요

`storage.rules:51`: `allow write: if (isAdmin() || isStoreOwner(storeId)) && isImage() && sizeOk()`
- delete 도 write 룰로 평가됨 → isAdmin 통과
- 단 `isStoreOwner(storeId)` 가 stores doc 의 ownerId 검사 → **stores doc 삭제 *전* 에 이미지 먼저 삭제 필요** (§2-6 순서)
- 또는 isAdmin 분기로 통과 — 정상

### 5-3. 2중 확인 옵션

| 옵션 | 구현 | 안전성 | 코드량 |

| **A**: `confirm()` 2회 (단순) | `confirm('정말 삭제?') && confirm('마지막 확인. 진행?')` | 낮음 (둘 다 OK 클릭 쉬움) | 0줄 추가 |
