## 1. 보안 (Security)

### 1-1. `functions/.env` 시크릿 노출
- **위치**: `git ls-files` 결과 `.env`, `functions/.env` 양쪽 모두 추적됨. `.gitignore` 에 `.env` 라인 **없음**. `functions/.env` 파일에 `BASE_URL` 외 CoolSMS 환경변수 키 헤더 확인. 값은 본 문서에 출력하지 않음.
- **판정**: ✅ **확인됨**. 보고서대로 평문 commit + 공개 GitHub 저장소 노출.
- **심각도 재평가**: 🔴 **즉시** (실제 과금/괴롭힘 가능 — 경량 앱이라도 SMS 는 실비용)
- **수정방안**:
  1. (사용자 수동 액션) CoolSMS 콘솔에서 키 즉시 폐기 → 재발급
  2. `git rm --cached .env functions/.env` + `.gitignore` 에 `.env` / `functions/.env` 추가
  3. Firebase Secret Manager 로 전환 (`functions:secrets:set COOLSMS_API_KEY` 등) — `index.js` 가 이미 `defineSecret` import 만 있고 사용은 안 함, 코드 수정 동시 필요
- **영향범위**: `functions/index.js` `sendSmsCode` 가 `process.env.COOLSMS_*` 에서 `secrets.value()` 로 변경 → 콜러블 옵션에 `{ secrets: [...] }` 추가. 회귀 위험: 배포 후 환경변수 누락 시 mock 모드(`hasSmsEnv=false`) 로 빠져 인증번호 전송 안 됨 (이미 폴백 분기 있음)

### 1-2. `sendSmsCode` 인증/속도 제한 부재
- **위치**: `functions/index.js:140` `exports.sendSmsCode = onCall(async (req) => { ... })` — 옵션 객체 자체가 없음. 본문(`:140-200`) 어디에도 IP/UID/전화번호 기반 쿨다운, App Check 강제, 인증 요구 없음. 코드 생성 후 즉시 `db.collection("smsAuth").doc(phone).set(...)` → CoolSMS 전송.
- **판정**: ✅ **확인됨**. 옵션 인자 부재 = `enforceAppCheck: false` 기본값
- **심각도 재평가**: 🔴 **즉시** (1-1 키 폐기 전까지는 잠재 폭탄, 폐기 후에도 잔액 충전 시 동일 위험)
- **수정방안**: `onCall({ enforceAppCheck: true }, ...)` + `smsAuth/{phone}` 에 `lastSentAt` 기록 → 60초 쿨다운 / 24시간 5회 캡. 검증 5회 실패 시 잠금. (verifySmsCode 도 함께 보강)
- **영향범위**: 회원가입(`AuthPage.vue:318-351`). App Check 강제 시 admin 빌드(IS_ADMIN_BUILD=true 에서 AppCheck 미초기화)는 sendSmsCode 호출 안 함 — 회원 빌드만 영향. 회귀 위험: 운영 reCAPTCHA Enterprise 키에 등록 안 된 도메인에서 호출 시 fail (gangtox.com 만 등록되어 있는 한 안전)

### 1-3. stores 빈 ownerId 점유
- **위치**: `firestore.rules:83-84`
  ```
  || (!('ownerId' in resource.data) && request.resource.data.ownerId == request.auth.uid)
  || (resource.data.ownerId == null && request.resource.data.ownerId == request.auth.uid)
  ```
- **판정**: ✅ **확인됨**. 일반 로그인 사용자가 ownerId 없는 가게 문서를 자기 uid 로 점유 가능
- **심각도 재평가**: 🟠 **높음** (관리자가 임시 생성한 가게가 표적). 관리자 전용 `linkStoreToBiz` Cloud Function 이 존재(`functions/index.js:2499`)하므로 룰 제거 후에도 정상 운영 가능
- **수정방안**: `firestore.rules:83-84` 두 절 삭제. 소유권 부여는 `linkStoreToBiz` (Admin SDK 우회) 또는 `isAdmin()` 분기로만 허용
- **영향범위**: 회원 사이트 `MyStoresPage.vue`(자기 가게 편집), `StoreEditPage.vue`, BizDashboard. 회귀 위험: 마이그레이션 도중 `ownerId` 미설정 가게가 있으면 그 가게 점주가 본인 가게 수정 불가 → 배포 전 `stores where ownerId == null` 일괄 admin 점유 정리 권장

### 1-4. 채팅 메시지 전체 열람
- **위치**: `firestore.rules:247-251, 258-262, 269-273` — `chats/`, `chat_rooms/`, `rooms/` 모두 `messages/{msgId}` 의 read 가 `if signedIn()`. 참여자 검증 없음.
- **판정**: ✅ **확인됨**. 모든 로그인 사용자가 모든 방 메시지 read 가능
- **심각도 재평가**: 🟠 **높음** (1:1 라이크 — `ChatBiz.vue` 의 점주-회원 대화 / `ChatOpen.vue` 의 오픈채팅이 동시에 존재. 점주 대화가 외부로 노출되는 게 의도가 아니라면 즉시 수정)
- **수정방안**: 룸 doc 에 `participants: [uid…]` 배열 두고 `allow read: if request.auth.uid in get(/databases/$(db)/documents/<root>/$(roomId)).data.participants || isAdmin()`. 전부 공개라면 룰 주석으로 명시 (감사 흔적)
- **영향범위**: `ChatBiz.vue`, `ChatOpen.vue`, `GangTalkPage.vue` 채팅 시트. 회귀 위험: 기존 메시지 doc 에 participants 미설정 시 모든 read 차단 → 마이그레이션 스크립트 필요

### 1-5. Maps + Firebase 공용 API 키
- **위치**: `src/firebase.js:82` `apiKey: 'AIzaSyCp...'` 하드코딩 + `.env` 의 `VITE_GMAPS_API_KEY=AIzaSyCp...` (둘 다 `AIzaSyCp` 시작 — 동일 키 확인)
- **판정**: ✅ **확인됨** (Firebase 웹 apiKey 노출 자체는 비취약이지만, Maps 겸용이라 GCP 리퍼러 제한 없으면 결제 위험)
- **심각도 재평가**: 🟡 **보통** (콘솔 작업으로 즉시 차단 가능, 코드 변경 불필요)
- **수정방안**: (사용자 수동 액션) GCP 콘솔 → API 키에 HTTP 리퍼러 제한 (`gangtox.com/*`, `gangtalk815.com/*`, `*.web.app/*`) + API 제한 (필요한 Maps/Places/Geocoding 만). 가능하면 Maps 전용 키 분리 후 `.env` 갱신
- **영향범위**: `src/views/MapView.vue`, 가게 지도 표시. 회귀 위험: 리퍼러 제한 누락 도메인에서 Maps 미동작

### 1-6. 관리자 판별 모델 이원화
- **위치**: `functions/index.js:2355-2363` `assertCallerIsAdmin` 이 `req.auth.token.email === ADMIN_EMAIL` 체크. `firestore.rules:9-13` `isAdmin()` 은 `admins/{uid}` 존재 체크. 두 시스템 병존.
- **판정**: ✅ **확인됨**. 관리자 추가/이관 시 두 곳 모두 갱신 필요
- **심각도 재평가**: 🟡 **보통** (현재 1인 운영, 즉시 사고 가능성 낮음). 단 1-2 와 합쳐 관리자 추가 시 일관성 깨질 위험
- **수정방안**: Firebase Auth Custom Claims (`{ admin: true }`) 로 통일하고 Rules 의 `isAdmin()` 을 `request.auth.token.admin == true` 로 교체. Functions 의 `assertCallerIsAdmin` 도 동일 claim 체크. `admins/{uid}` 컬렉션은 metadata 용도로만 남기거나 폐기
- **영향범위**: `functions/index.js` 3 콜러블 (`createBizAccount/resetBizPassword/linkStoreToBiz`), `firestore.rules` 전체. 회귀 위험: claim 설정 누락 시 모든 admin 작업 잠금 → 배포 전 `gangtalk815@gmail.com` 에 claim 부여 스크립트 1회 실행 필요

### 1-7. 열린 `/api` Express
- **위치**: `functions/index.js:1431` `app.use(cors({ origin: true }))` — 모든 origin 반사. `:1501` `app.get("/pass/mock", ...)`, `:1521` `app.post("/sheets/vendors/update", ...)`, `:2062` `app.post("/sheets/vendors/bootstrap", ...)`. 본문 추가 read 필요 (이번 검토 범위 아님)
- **판정**: 🟡 **부분맞음** (라우트 존재 확인, 인증 유무는 본문 추가 검증 필요)
- **심각도 재평가**: 🟡 **보통** (실제 인증 검사 여부에 따라 변동)
- **수정방안**: `/pass/mock` 운영 빌드 제거 (`NODE_ENV !== 'production'` 가드) · `/sheets/vendors/update|bootstrap` 에 Firebase ID 토큰 검증 미들웨어 또는 Admin claim 체크. `cors({ origin: true })` → 명시 origin 화이트리스트

## 2. 버그 / 정합성 (Correctness)

### 2-1. 좋아요/조회/투표 카운터 어뷰징
- **위치**: `firestore.rules:204` `changesAreOnly(['views','likes','votesA','votesB','updatedAt'])` — 모든 signed user 에게 허용. 같은 룰이 `:219` (comments), `:234` (replies) 에도 반복
- **판정**: ✅ **확인됨**. 단일 사용자가 likes/views 무한 증가 가능
- **심각도 재평가**: 🟢 **낮음** (경량 커뮤니티, 인기순위가 비즈니스 임팩트 적음). 단 `MainPage.vue` 의 인기글 카드 노출 정렬에 직결되므로 어뷰징 시 노출 왜곡 가능
- **수정방안**: 좋아요는 `board_posts/{id}/likes/{uid}` 서브문서 (생성 1회 제한) + Cloud Function `onDocumentCreated` 집계. 조회수는 세션 기반 디바운스 (`sessionStorage['view_'+id]`) — 클라이언트 신뢰이긴 함
- **영향범위**: `GangTalkPage.vue:likeDetail` (이미 increment), MainPage 의 인기순위 computed. 회귀 위험: 기존 likes 값은 마이그레이션 없이 새 카운트 0 부터 시작하면 인기순위 갑작스러운 변화

### 2-2. 전역 카운터 레이스 컨디션
- **위치**: `meta/counters` (userSeq) 룰 `firestore.rules:277-285` — 클라이언트가 +1 하는 패턴. `reserveReferralCode` 본 검토에서 **functions/index.js 에 미배포** 확인 (2-3 참고). functions/index.js 내 `runTransaction` 은 `:373` 의 `addPointsOnce` 1곳만 존재
- **판정**: ✅ **확인됨** (트랜잭션 미사용). 동시 가입 시 같은 userSeq 발급 또는 룰 거부로 일부 실패 가능
- **심각도 재평가**: 🟡 **보통** (트래픽 적은 동안엔 거의 안 터지지만 마케팅 트래픽 폭증 시 가입 실패)
- **수정방안**: userSeq 증가 자체를 Cloud Function 으로 이전 (`runTransaction` 으로 read→+1→write). 클라이언트 직접 쓰기 차단 — 룰 `:277-296` 을 admin 만 허용 + 함수 호출 통해 발급
- **영향범위**: `me.signupUser/signupBiz/signupAdmin` 흐름. 회귀 위험: 함수 콜드 스타트 지연 → 가입 UX 1초 정도 느려짐

### 2-3. 죽은 코드 / 중복 정의
- **위치**: `functions/authFunctions.js` 존재 (6KB) — `index.js` 에 import 없음 (grep 0건 확인). 컬렉션도 다름: `authFunctions.js:160` `sms_codes` vs `index.js:151` `smsAuth`. 함수명도 다름: `checkNickDuplicate` (`authFunctions.js:67`) vs `checkNicknameDuplicate` (`index.js:315`)
- **판정**: ✅ **확인됨** + **추가 발견** — `reserveReferralCode` 가 **오직 `authFunctions.js:83` 에만 정의**되어 있고 `index.js` 에 import 안 됨. 즉 **이 함수는 배포된 적 없음**. 그런데 `src/pages/AuthPage.vue:509` 가 `httpsCallable(fns, 'reserveReferralCode')` 로 호출. 실패 시 폴백 (`prefix + '00001'`) 으로 빠짐 → **모든 사용자가 같은 추천코드 suffix** 가입 중일 가능성
- **심각도 재평가**: 🟠 **높음** (보고서 🟢 → 🟠 상향) — 추천코드 정상 동작 안 함이 거의 확실. 무중복 보장 깨짐
- **수정방안**: `authFunctions.js` 의 `reserveReferralCode` 를 `index.js` 로 옮기고 `runTransaction` 으로 안전 카운터화. 나머지 잔재 함수는 삭제. AuthPage 에서 폴백 발생 빈도 로그 확인 필요
- **영향범위**: 회원가입 추천코드 발급 전체. 회귀 위험: 기존 사용자 DB 에 `prefix + '00001'` 같은 중복 코드가 다수 있을 수 있음 — 배포 전 `users where referral.myCode like '%00001'` 카운트 확인 권장
