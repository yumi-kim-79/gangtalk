# 로그인 세션 복원 실패 — PR #76 후에도 잔존 진단

**날짜**: 2026-06-18
**범위**: gangtox.com 회원 사이트. PR #76 (ensureSignedIn / me.init grace) 배포 후에도 실계정 로그인 → 새로고침 → 로그인 화면 복귀 재발
**전제**: 진단 전용. 코드/룰 수정·PR·배포 없음.
**결론**: PR #76 의 grace 는 **SDK 가 복원 중인 케이스** 만 보호. SDK 가 **복원 자체에 실패**하는 케이스 (persistence 충돌 / 토큰 미저장) 는 grace 가 만료된 뒤 익명 로그인으로 빠짐 → me.init 가 익명 user 를 정상 user 로 처리 → users doc 새로 생성하면서 email='' → 가드의 `rawLogged = loggedIn && !!email` 가 false → /auth 로 redirect.

---

## 1. 결정적 단서 — 진짜 원인 (파일:라인)

### 1-1. **`setPersistence` 호출이 2곳에서 충돌** (가장 유력)

| 파일:라인 | 호출 | 시점 |
|---|---|---|
| `src/firebase.js:151-159` | `setPersistence(auth, indexedDBLocalPersistence)` (폴백: browserLocal → inMemory) | 모듈 로드 시 즉시 (await 안 함) |
| `src/pages/AuthPage.vue:672` | `setPersistence(auth, browserLocalPersistence)` | AuthPage onMounted 안 (await) |

- 두 호출이 **서로 다른 persistence 타입** 지정 — 마지막 호출이 SDK 의 active persistence 가 됨
- Firebase Auth Web SDK 의 \[docs\](https://firebase.google.com/docs/reference/js/auth.md#setpersistence): "Changes the type of persistence on the Auth instance for the currently saved Auth session and applies this type of persistence for future sign-in requests"
- 즉 setPersistence 호출 시점에 **현재 세션 토큰도 새 persistence 로 옮김**
- AuthPage 가 `/auth` 로 진입할 때마다 onMounted 가 `browserLocalPersistence` 로 덮어씀 → 새 로그인 시 localStorage 에 저장
- 그 후 새로고침 → `firebase.js` 의 setPersistence(indexedDB) 가 다시 실행 → indexedDB 로 옮기려 함 → race
- 어느 storage 에 토큰이 있는지 시점마다 다름 → 복원 신뢰성 ↓

### 1-2. **익명 로그인이 grace 만료 후 호출 → me.init 가 정상 user 로 처리**

`src/store/user.js:282-294, 320-351` — `me.init` 의 onAuthStateChanged 콜백:

```js
if (snap.exists()) {
  data = snap.data() || {}
  ...
} else {
  // 문서가 없을 때 최소 생성 — V2 포맷
  const seq = 1
  const myCode = makeMyCodeV2(u.email || '', seq)   // ← u.email === null (익명)
  data = {
    type: 'user',
    profile: {
      email: u.email || '',                          // ← '' 빈 문자열
      nickname,
      ...
    },
    ...
  }
  await setDoc(userRef, { ...data, createdAt, updatedAt })
}
```

- 익명 user 가 들어오면 users/{익명uid} 문서가 **새로 생성**됨 (`type: 'user'`, `profile.email: ''`)
- `me.auth.value = { loggedIn: true, ...data, type: 'user' }`
- LS_AUTH 도 `me.save()` 로 덮어쓰임 → email='' 인 상태로 캐시 갱신

### 1-3. **라우터 가드의 `rawLogged` 가 email 빈문자열에 false**

`src/router/index.js:408-419`:
```js
const email = String(
  a.email || a.user?.email || a.profile?.email || ...
).trim()
const rawLogged = !!a.loggedIn && !!email   // ← email 빈문자열 → false
const logged = rawLogged && myType !== 'guest'
...
if (!logged && !publicForGuests.has(toName) && !isTabRoot) {
  return { path: '/auth', query: { next: to.fullPath, mode: 'signup' } }
}
```

- `me.auth.value.loggedIn === true` 이지만 `profile.email === ''` → `rawLogged === false`
- /mypage, /favorites 등 보호 페이지 진입 시 → `/auth` 로 redirect

## 2. 새로고침 시점별 흐름 재구성

| t (ms) | 이벤트 | currentUser / me.auth / 화면 |
|---|---|---|
| 0 | 새로고침 시작 | — |
| 0 | `firebase.js` 모듈 로드: `getAuth()`, `persistenceReady` 시작 (`setPersistence(indexedDB)`) | currentUser=null |
| ~10 | `store/user.js` 모듈 로드: `me.auth = ref(loadJSON(LS_AUTH))` | me.auth = LS_AUTH 캐시 (정상 시 loggedIn:true, email 정상) |
| ~20 | `main.js` app.mount → 라우터 첫 navigation 시작 | — |
| ~30 | 라우터 가드 진입: `await user.ensureAuthReady()` | _ready=false → pending |
| ~50 | `me.init` 의 `onAuthStateChanged` 등록 → SDK 가 첫 콜백 발화 | u=null (복원 진행 중 또는 실패) |
| ~50 | me.init 콜백: `_nullPending` setTimeout (2500ms) + **`_ready=true` 즉시 set** | LS_AUTH 캐시 유지 |
| ~50 | 가드의 ensureAuthReady resolve → me.auth 확인 → 캐시값 → logged=true → 통과 | **여기까지는 정상** |
| ~100 | firebase.js ensureSignedIn 도 grace 시작 (2500ms) | — |
| **~2500** | grace 만료: SDK 가 실계정 복원 못 함 (1-1 persistence 충돌) → ensureSignedIn 가 `signInAnonymously` 호출 | — |
| ~2550 | 익명 user 발화 → me.init 콜백 (`if (_nullPending) clearTimeout`) | u=익명, uid 새값 |
| ~2600 | `users/{익명uid}` doc 조회 → 없음 → else 분기 → **새 doc 생성** | profile.email='' |
| ~2700 | `me.auth.value = { loggedIn:true, ...익명data }` + `me.save()` → LS_AUTH 캐시도 email='' 로 덮임 | — |
| 사용자가 페이지 이동 시도 | 가드 재실행 → email='' → rawLogged=false → **redirect /auth** | 로그인 화면으로 |

핵심: **t=2500ms 의 grace 만료 직후가 화면을 망치는 시점**. 사용자가 그 후 클릭 / 다른 페이지 이동 시 가드가 즉시 작동.

## 3. PR #76 이 왜 이 케이스를 못 잡았는지

PR #76 의 변경 두 가지:
1. `firebase.js ensureSignedIn` — 첫 null 발화 즉시 익명 호출하지 않고 `RESTORE_GRACE_MS=2500ms` 대기
2. `store/user.js me.init` — 첫 null 발화 즉시 LS_AUTH reset 하지 않고 `NULL_GRACE_MS=2500ms` 대기

**가정**: SDK 가 grace 동안 실계정을 복원해서 두 번째 콜백으로 user 발화.

**현실**: grace 가 지나도 SDK 가 실계정 복원 **못 함** — 이유는:
- (a) **persistence race**: AuthPage.onMounted 의 `setPersistence(browserLocal)` 호출 후 로그인하면 localStorage 에 저장. 새로고침 후 `firebase.js` 가 indexedDB 로 다시 옮기려는데, 그 사이 SDK 의 복원 메커니즘이 어디서 토큰을 읽을지 결정됨. 호출 순서/타이밍에 따라 못 읽음
- (b) **토큰 자체가 어디에도 없는 경우**: 첫 로그인 시점에 두 persistence 가 race 라 token 이 in-memory 만 저장되고 새로고침 시 사라짐
- (c) **AuthPage 가 `await persistenceReady` 안 함**: signIn 호출 시점이 persistence 설정 완료 전이면 default 로 저장됨

PR #76 의 grace 는 (b)/(c) 의 **결과** (SDK 가 끝까지 null) 를 늦추기만 함. 끝내 user 발화 안 하면 익명으로 빠짐.

## 4. 가설별 검증 액션 (사용자가 콘솔에서 직접)

### 4-1. SDK 가 복원 시도하는지 확인

```js
// 새로고침 직후 콘솔에서 즉시 실행
const auth = firebase.auth()
console.log('currentUser at t=0:', auth.currentUser)

auth.onAuthStateChanged(u => {
  console.log('[onAuthStateChanged]', Date.now(), 'user=', u ? { uid: u.uid, email: u.email, isAnon: u.isAnonymous } : null)
})

// 또한 indexedDB / localStorage 검사
console.log('localStorage firebase keys:',
  Object.keys(localStorage).filter(k => k.includes('firebase'))
)

const req = indexedDB.open('firebaseLocalStorageDb')
req.onsuccess = (e) => {
  const db = e.target.result
  const tx = db.transaction('firebaseLocalStorage', 'readonly')
  tx.objectStore('firebaseLocalStorage').getAll().onsuccess = (ev) => {
    console.log('indexedDB firebase rows:', ev.target.result)
  }
}
```

**해석**:
- 둘 다 비어 있음 → 토큰 자체가 어디에도 저장 안 됨 (가설 b)
- localStorage 에만 있음 → AuthPage 의 setPersistence(browserLocal) 가 마지막 적용됨. firebase.js 의 setPersistence(indexedDB) 가 영향 안 줌
- indexedDB 에만 있음 → firebase.js 가 마지막. 그러면 SDK 가 복원해야 함. 그래도 onAuthStateChanged 가 null 이면 SDK 버그 / 다른 race

### 4-2. 익명 로그인이 실제로 호출됐는지

```js
// 새로고침 후 ~3초 기다린 다음
const u = firebase.auth().currentUser
console.log('after 3s:', u ? { uid: u.uid, email: u.email, isAnon: u.isAnonymous } : null)
```

**해석**:
- `isAnon: true` → ensureSignedIn 가 익명 호출 (이 진단의 가설 맞음)
- `isAnon: false, email: '...'` → 복원 정상. 다른 곳에서 redirect 일어남

### 4-3. me.auth 캐시 상태

```js
console.log('LS_AUTH:', JSON.parse(localStorage.getItem('app:user:auth') || '{}'))
```

**해석**:
- `{loggedIn:true, profile:{email:'...정상값'}, ...}` → 캐시 정상. 가드가 캐시 사용하면 통과해야 함
- `{loggedIn:true, profile:{email:''}}` → **이 진단의 핵심 가설 확정**. 익명 user 가 LS_AUTH 를 덮음

## 5. "한 번 로그인하면 유지" 만들 변경점 (별도 PR — 본 진단 외)

### 5-1. AuthPage 의 setPersistence 호출 제거 또는 통일
- **현재**: `AuthPage.vue:672 setPersistence(auth, browserLocalPersistence)` — firebase.js 와 충돌
- **고침**: AuthPage 의 호출 자체 삭제. firebase.js 의 `persistenceReady` 만 신뢰
- 또는: AuthPage 가 firebase.js 의 `persistenceReady` 를 `await` 한 뒤 signIn

### 5-2. me.init 가 익명 user 를 정상 user 로 처리하지 않게
- **현재**: 익명 user → users doc 자동 생성 → me.auth.value 가 정상 user 로 보임
- **고침**: `u.isAnonymous === true` 이면 `me.auth.value = { loggedIn: false, type: 'guest' }` 로 처리
- 또는: 익명 user 일 때 LS_AUTH 덮어쓰지 않음 (캐시 보존)

### 5-3. 익명 로그인 자체 폐지 검토
- 회원 사이트가 실제로 익명 user 가 필요한 곳은 `ChatOpen.vue:185` 정도
- `firebase.js ensureSignedIn` 의 익명 호출 제거 → ChatOpen 진입 시에만 호출
- 그러면 새로고침 시 실계정 복원 실패해도 익명으로 덮이지 않음
- 단 firestore.rules 의 `signedIn()` 요구 룰이 비로그인 사용자에게 거부 — public read 만 가능
  - 현황판 / 가게찾기 / 강톡 목록은 public read 라 무관
  - 게시판 / 채팅 등은 ChatOpen 패턴 따라 진입 시 익명 호출

### 5-4. 라우터 가드의 email 의존성 완화
- **현재**: `rawLogged = !!a.loggedIn && !!email` — email 없으면 비로그인
- **고침**: 익명 user 처리는 `myType === 'guest'` 로 구분되도록 me.init 수정 후, 가드는 `logged = a.loggedIn && myType !== 'guest'` 만 보면 됨

## 6. 결론

### 6-1. PR #76 후 잔존 원인 — 단일하지 않음, **3개 결합**
1. **persistence 호출 race** (`firebase.js:151` vs `AuthPage.vue:672`) → 토큰 저장처 불확실 → SDK 가 실계정 복원 못 함
2. **PR #76 grace 만료 → 익명 로그인 호출** (`firebase.js:194 signInAnonymously`) — grace 자체는 정상이지만 SDK 복원 실패한 케이스를 못 살림
3. **me.init 가 익명 user 를 정상 user 로 처리** (`store/user.js:320-351`) → users doc 새로 생성, profile.email='', LS_AUTH 덮어씀 → 가드 redirect

### 6-2. 본 진단의 단일 결정적 사실
- **PR #76 은 SDK 가 복원 *중*인 케이스만 보호**. 복원 *실패* 케이스는 grace 만료 후 익명 로그인이 정상 user 자리를 차지함
- 사용자가 보고한 "새로고침 → 로그인 화면" 의 정확한 메커니즘은 §2 의 시점별 표 참조

### 6-3. 검증 우선순위 (사용자가 콘솔에서)
1. §4-1 — indexedDB/localStorage 에 firebase 토큰이 있는가?
2. §4-2 — 새로고침 3초 후 `isAnonymous === true` 인가?
3. §4-3 — LS_AUTH 의 `profile.email` 이 빈 문자열인가?

세 가지 모두 yes 면 본 진단의 가설 확정.
