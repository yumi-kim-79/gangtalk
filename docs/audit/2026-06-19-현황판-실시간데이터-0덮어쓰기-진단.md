```js
function applyRoomsBiz(){
  const bases = baseStores.value     // ← stores onSnapshot 결과 (원본)
  const rbMap = roomsBiz.value        // ← rooms_biz 가공 결과
  const agg   = labelsAgg.value       // ← vendors 가공 결과 (현재 항상 {})

  const out = bases.map((s) => {
    const byRb = rbMap[id] || null
    const byAg = agg[s.name] || null

    const legacyMatch   = Number(s?.match ?? s?.needRooms ?? 0)
    const rbActive      = !!byRb?._hasInput          // ← 결정적

    // totalRooms — byAg?.totalRooms ?? s.totalRooms ?? 0
    // 혼잡도 — rbCg || agCg || computeStatus(...)

```

→ **`_hasInput`** 이 진실/거짓을 결정. true 면 rooms_biz 값 사용, false 면 stores 본 doc 의 legacy 사용.

## 2. 0 덮어쓰기의 결정적 지점 — `_hasInput` 계산

### 2-1. `subscribeRoomsBiz` 의 `_hasInput` 계산 (`MainPage.vue:1517-1521`)

```js

  || inputPeople > 0
```

여기서 `rooms / people` 계산은 그 위 (`:1477-1512`) 의 흐름:

→ 관리자가 빈 칸으로 저장하면 `rooms=0, people=0, _hasInput=true` → **legacy 덮어쓰기**

#### 케이스 B — pastedText 있음 (`:1484-1512`)

→ **시나리오**: ChatBiz 에 "응" / "ㅇㅇ" / "확인" 같은 짧은 메시지 1줄이 마지막 메시지로 있으면:

- `parseNeedFromLastPastedText` 가 0/0 반환
- `isOneLine = true` 이지만 `inputRooms=0` 이라 0 유지
- **`hasInput = !!pastedText = true`** (라인 1518)
- 결과: `{rooms:0, people:0, _hasInput:true}`

#### `applyRoomsBiz` 에서 적용 (`:1237-1245`)
```js

  ? Number(byRb.rooms)                                    // → 0 ✗ (덮어씀)
```

→ **stores 본 doc 의 `s.match=3` (진짜 값) 무시되고 0 표시**

## 3. race 메커니즘 (시간순)

```
t=0    ms   페이지 진입
            ├─ subscribe() → stores onSnapshot 시작
            ├─ subscribeVendorsSummary() → vendors onSnapshot 시작 (권한 실패 임박)
            └─ subscribeVendorStatusPerVendor() → vendors/{id}/status 시작 (권한 실패 임박)

t~100  ms   stores 첫 콜백 (캐시 + 서버)
            ├─ baseStores.value = rows
            ├─ subscribeRoomsBiz() 호출 → rooms_biz onSnapshot 시작
            └─ applyRoomsBiz() (1차)
               ├─ rbMap={}, agg={}
               ├─ byRb=null → rbActive=false → match = legacyMatch (s.match=3) ✓
               └─ stores.value = out  ← 진짜 값 (3) 화면에 표시 ✓

t~150  ms   vendors 권한 거부 (콘솔 에러, agg 유지 = {})

t~200  ms   rooms_biz 첫 콜백 시작 (async)
            └─ Promise.all 시작 — fetchLatestMessageText × N 병렬 호출

t~1~3  s    Promise.all 완료
            ├─ 각 entry: _hasInput 계산 (위 §2-1 의 케이스 B 발동 시 true)
            ├─ roomsBiz.value = map (정상 store: rooms=3 / 위험 store: rooms=0)
            └─ applyRoomsBiz() (2차)
               ├─ rbMap 채워짐
               ├─ 위험 store: byRb._hasInput=true, byRb.rooms=0 → match=0 ✗
               │  └─ stores 본 doc 의 s.match=3 무시 → 화면에 0 ✗
               └─ stores.value = out  ← 화면 갱신, 0 덮어씀
```

**사용자가 본 "잠깐 진짜 값 → 0"** 의 정확한 양상:
- t~100ms 시점에 legacy 값 (3) 보임
- t~수 초 후 (Promise.all 완료) rooms_biz 값 (0) 으로 덮어씀

### 3-1. 페이지 왔다갔다 시 "가끔 진짜 값"
- 캐시된 rooms_biz 콜백이 먼저 와도 같은 0 덮어쓰기
- 단 사용자가 빠르게 페이지 전환 → Promise.all 미완료 → 1차 콜백 (legacy) 만 표시 → "진짜 값 보임"
- 다시 페이지 머무름 → 2차 콜백 도착 → 0 덮어쓰기

### 3-2. 다른 store 들이 race 에 영향 받음
- `computeStatus` 의 `rangeByCategory(cat)` (`:1979-1992`) 가 `stores.value` 의 같은 카테고리 store 들의 match/persons 범위 계산
- **위험 store 가 같은 카테고리에 있으면** mMin/mMax 가 0 영향 받음 → 정상 store 의 normalize 결과도 영향
- 즉 카테고리 안 store 들이 서로 혼잡도 계산에 영향

## 4. 혼잡도 "나쁨" 근본 원인

### 4-1. `computeStatus` 의 분기 (`MainPage.vue:1994-2033`)

```js
const cat = String(s?.category || 'etc')
const { mMin, mMax, pMin, pMax } = rangeByCategory(cat)
const match   = num(s?.match)        // 위험 store 면 0
const persons = num(s?.persons)      // 0
const mN = normalize01(match,   mMin, mMax)    // 0/0/0 → 0
const pN = normalize01(persons, pMin, pMax)    // 0/0/0 → 0

// ① 카테고리 기준 정규화
if (mN != null && pN != null){
  const availability = (mN + pN) / 2   // = 0
  if (availability >= 0.60) return '좋음'
  if (availability >= 0.30) return '보통'
  return '나쁨'                         // ← 여기로 떨어짐
}

// ② totalRooms 기반 비율
const totalRooms = num(s?.totalRooms ?? s?.total ?? s?.rooms)   // 0
const maxPersons = num(s?.maxPersons ?? s?.capacity ?? s?.max)  // 0
const rRooms  = (totalRooms > 0 && Number.isFinite(match)) ? (match / totalRooms) : null    // null
const rPeople = (maxPersons > 0 && Number.isFinite(persons)) ? (persons / maxPersons) : null  // null

let availability
if (rPeople != null && rRooms != null)      availability = (rPeople + rRooms) / 2
else if (rPeople != null)                  availability = rPeople
else if (rRooms  != null)                  availability = rRooms
else                                       availability = 1     // ← totalRooms=maxPersons=0 이면 좋음

if (availability >= 0.60) return '좋음'
if (availability >= 0.30) return '보통'
return '나쁨'
```

### 4-2. `normalize01` 의 분기 (`:1972-1978`)

```js
function normalize01(v, min, max){
  if (!Number.isFinite(v)) return null
  if (!Number.isFinite(min) || !Number.isFinite(max)) return null
  if (max <= min) return v > 0 ? 1 : 0       // ⚠️ max=min=0 이면 v=0 → 0
  const r = (v - min) / (max - min)
  return Math.max(0, Math.min(1, r))
}
```

→ 카테고리 내 다른 store 들의 match 도 모두 0 이면 mMin=0, mMax=0 → `max <= min` → match=0 → **0 반환**

### 4-3. 결과 시나리오

| store 자체 match | 같은 카테고리 다른 store match 분포 | mN | 결과 |
|---|---|---|---|
| 0 (덮어쓴) | 모두 0 (race 영향) | 0 | availability=0 → **'나쁨'** |
| 0 (덮어쓴) | 일부 양수 (mMax>0) | 0 | availability=0/2 → **'나쁨'** |
| 3 (정상) | 모두 0 | mMax=3 → normalize=1 | availability=1 → **'좋음'** |

→ **`s.match=0` 인 store 가 거의 무조건 '나쁨'**. 사용자 증상과 일치.

### 4-4. vendors 와의 관련성 (간접)

vendors 권한 실패 → `agg = {}` → `byAg=null` → `agCg=null` → `applyRoomsBiz` 의 혼잡도 폴백:
```js
const status = ... (rbCg || agCg || computeStatus(...))
```
→ `agCg` 가 null 이라 `computeStatus` 자동계산으로 떨어짐 → 위 시나리오 결과 적용

**만약 vendors 가 작동했다면**: `agCg` 가 시트에서 가져온 혼잡도 라벨 ("여유"/"보통"/"혼잡") 직접 표시 → 0 덮어쓰기와 무관하게 정상 표시 가능

→ **vendors 권한 실패는 0 덮어쓰기 자체 원인은 아니지만, 혼잡도 표시를 자동계산에 의존하게 만들어 증상을 더 두드러지게 함**

## 5. 보호 우회 시나리오 상세

결과:

- `rooms=0, people=0`
- → `applyRoomsBiz` 에서 stores legacy 덮어쓰기

### 시나리오 B — 관리자가 0/0 으로 manualSaved

- 관리자가 `StoresManagePage` Tab 2 또는 업체가 `BizMetricsPage` 에서 `match=0, persons=0` 입력 후 저장

## 6. 고칠 방향

### 권장 1 — `_hasInput` 정의 강화 (가장 단순)

`MainPage.vue:1517-1521` 변경:
```js
// 이전 (현재):
const hasInput = manualSaved
  || !!pastedText           // ⚠️ 의미 없는 1줄도 통과
  || inputRooms  > 0
  || inputPeople > 0

// 권장:
const hasInput = manualSaved
  || (rooms > 0 || people > 0)              // ← 파싱 결과 또는 입력값이 실제로 양수일 때만
```

**효과**:
- pastedText 가 있어도 parse 결과가 0/0 이면 `_hasInput=false` → legacy 폴백
- 시나리오 A 해결 ✓
- 시나리오 B (manualSaved 빈 저장) — 그대로 통과 (관리자 의도 존중)

**위험**: 관리자가 의도적으로 "0 으로 표시" 하고 싶어도 manualSaved 가 아니면 legacy 폴백 — 단 manualSaved 패턴이 명시적이라 큰 문제 없음

### 권장 2 — `_hasPastedText` 가 양수일 때만 신호

```js
const hasInput = manualSaved
  || (pastedText && (rooms > 0 || people > 0))
  || inputRooms > 0
  || inputPeople > 0
```

→ pastedText 와 입력값을 둘 다 고려. 권장 1 과 유사 효과

### 권장 3 — `applyRoomsBiz` 의 rbActive 강화

`MainPage.vue:1237` 변경:
```js
// 이전:
const rbActive = !!byRb?._hasInput

// 권장:
const rbActive = !!byRb?._hasInput
  && (Number(byRb?.rooms || 0) > 0 || Number(byRb?.people || 0) > 0 || byRb?._manualSaved)
```

→ `_hasInput=true` 라도 rooms/people 둘 다 0 이면 (manualSaved 제외) legacy 사용

**위험**: PR #71 의 의도와 약간 충돌 — `_hasInput` 정의를 바꾸지 않고 적용 단에서 보호

### 가장 안전한 조치 (조합)

권장 1 (소스 보호) + 권장 3 (적용 보호) 양쪽 적용 — defense in depth.

**단** 관리자가 "지금 0/0 이다" 라고 명시 저장한 의도를 살리려면 `_manualSaved=true` 분기는 예외로 두기 (그대로 0 표시).

### 권장 4 — vendors 권한 정리 (혼잡도 자동계산 의존도 완화)

별도 진단 (`docs/audit/2026-06-19-콘솔-노이즈-vendors-진단.md`) 의 방안 A (vendors 구독 제거) 또는 방안 B (savedToken 분리) 적용. 단 이건 **0 덮어쓰기 직접 원인 아님** — 부수효과 (혼잡도 폴백) 만 영향

## 10. 보고서 한계 (추정 사항)

- **시나리오 A / B / C 중 어느 것이 사용자 환경의 실제 데이터인지 확정 불가** — 정적 분석 한계. Firestore Console 에서 `rooms_biz` doc 의 `_hasInput=true, rooms=0, people=0` 인 entry 직접 확인 필요
- **`fetchLatestMessageText` 가 어떤 메시지를 반환하는지** 환경 의존 — 짧은 일상 대화가 있으면 시나리오 A 트리거
- **`manualSaved=true + 0/0`** 케이스는 관리자 의도일 가능성 — 사용자가 "0 인데 표시되어서 이상하다" 라면 의도 아님, "지금 마침 0 이다" 라면 의도
- **race timing (수 ms~수 초)** 은 네트워크/캐시 상태 의존 — 환경마다 변동
