## 1. 리셋 로직 — 정확한 위치 + 코드

### 1-1. Cloud Function `dailyReset0700` (`functions/index.js:2383-2405`)

```js
/* =========================================================
   ★ 매일 07:00 리셋(옵션)
========================================================= */
exports.dailyReset0700 = onSchedule(
  { schedule: "0 7 * * *", timeZone: "Asia/Seoul", region: "asia-northeast3" },
  async () => {
    const col = db.collection("rooms_biz")
    const qs = await col.get()
    const bw = db.bulkWriter()
    const today = new Date().toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" })
    for (const doc of qs.docs) {
      bw.set(doc.ref, {
        needRooms: 0,                 // ← 리셋
        needPeople: 0,                // ← 리셋
        matched: 0,                   // ← 리셋
        lastResetDate: today,         // ← 오늘 날짜 기록
        updatedAt: admin.firestore.FieldValue.serverTimestamp()
      }, { merge: true })            // ← 다른 필드는 보존
    }
    await bw.close()
    return null
  }
)
```

### 1-2. 리셋 사양 확정

| 항목 | 값 |
|---|---|
| **트리거** | onSchedule (Cloud Scheduler) |
| **스케줄** | `0 7 * * *` — 매일 분=0, 시=7 |
| **시간대** | `Asia/Seoul` |
| **리전** | asia-northeast3 (서울) |
| **대상 컬렉션** | `rooms_biz` 전체 (모든 doc) |
| **write 방식** | `bulkWriter()` + `merge: true` |
| **리셋 필드** | `needRooms=0`, `needPeople=0`, `matched=0`, `lastResetDate=today` |
| **today 형식** | `toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" })` — 결과 예: `"2026. 6. 21."` 또는 `"2026.6.21"` |

→ youandme 의 `lastResetDate: "2026.6.21"` 와 정확히 일치. **이 함수가 youandme 의 0/0 박은 주체** 가 거의 확실 (관리자 일괄 저장과 별개 또는 추가 원인).

### 1-3. 다른 곳에서의 `lastResetDate` 사용

`grep` 결과:
- `src/pages/ChatBiz.vue:224`: `lastResetDate: ''` (ensureRoom 초기값)
- `src/lib/firestoreSafe.js:64, 87`: 화이트리스트 정의만
- 그 외 비교/체크 로직 0건

→ **`lastResetDate` 는 리셋 기록 용도일 뿐, 클라이언트 측 비교/조건 분기에 사용 안 함**. 즉 클라이언트가 "오늘 이미 리셋됨" 으로 판단하는 분기 없음.

## 2. 리셋 주체와 시점

### 2-1. 주체 = Cloud Function (서버, 사용자 무관)

- Cloud Scheduler 가 매일 07:00 KST 에 `dailyReset0700` 트리거
- **사용자가 현황판 열든 안 열든 무관** — 서버 자동 실행
- **업체가 ChatBiz 열든 안 열든 무관** — 서버 자동 실행

### 2-2. 시점 = 매일 오전 7시 정각 (한국시각)

- 사용자가 본 "하루~주말 지나면 0/0" — 거의 확실히 이 함수
- 마지막 입력 시각이 오전 7시 이전이든 이후든 무관 — 다음 오전 7시에 리셋됨
- 예시:
  - 월요일 22:00 admin 입력 5/8 → 화요일 07:00 자동 리셋 → 0/0
  - 화요일 22:00 admin 입력 5/8 → 수요일 07:00 자동 리셋 → 0/0
  - 금요일 22:00 admin 입력 5/8 → 토요일 07:00 자동 리셋 → 토~월 07:00 모두 리셋 → 사용자 인상 "주말 지나면 0/0"

### 2-3. 클라이언트는 리셋 안 함

- 진단 §1-3 확인 결과 클라이언트 측 `lastResetDate` 비교/리셋 분기 0건
- ChatBiz `ensureRoom` 의 `lastResetDate: ''` 는 **신규 doc 생성 시 초기 빈값**일 뿐 (덮어쓰기 아님)
- → 사용자 진입과 무관하게 매일 07:00 만 영향

### 4-3. **manualSaved 잔존 + 0/0 의 부작용 ⚠️**

이전 진단 (`docs/audit/2026-06-19-현황판-실시간데이터-0덮어쓰기-진단.md` 시나리오 B) 와 같은 결과:

- 어제 admin/업체가 `manualSaved: true` 로 저장 (예: 5/8)
- 오늘 07:00 리셋 → `needRooms=0, needPeople=0, manualSaved=true 잔존`
- MainPage `applyRoomsBiz` (PR #107):
  ```js
  const rbHasPositive = (rooms > 0) || (people > 0)   // false
  const rbActive = !!_hasInput && (rbHasPositive || !!_manualSaved)
  //              = true && (false || true) = true
  ```
- → `byRb.rooms=0` 채택 → **현황판 0/0 표시**

즉 **manualSaved 가 잔존하면 PR #107 의 의도 존중 분기가 0/0 을 그대로 통과시킴**. 이게 운영상 불편의 근본.

### 4-4. ChatBiz 시스템과의 차이 (manualSaved 없는 케이스)

ChatBiz `updateCounts` 는 **manualSaved 안 박음** (PR #107 의도). 따라서:
- 리셋 후: `needRooms=0, needPeople=0, manualSaved=undefined, lastPastedText 잔존`
- MainPage `subscribeRoomsBiz` 의 manualSaved 분기 (`:1484`):
  - `manualSaved=false` → `pastedText` 분기 진입 → `parseNeedFromLastPastedText(lastPastedText)` 호출
  - 양수 파싱 가능 시 `rooms/people` 양수 → `_hasInput=true` (PR #107 `rooms > 0`) → 양수 표시 ✓
- 즉 **ChatBiz 시스템 (manualSaved 없음) 으로만 채워진 store 는 리셋 후에도 lastPastedText 파싱으로 자동 복원** 가능

→ **manualSaved 잔존 store 가 가장 영향 받음** (현재 admin 일괄 저장한 13개)

## 5. 리셋 주기 적절성 평가

### 5-1. 매일 07:00 의 적정성

| 평가 항목 | 결과 |
|---|---|
| 주기 (매일) | 적정 — 야간 영업 업체 특성상 다음날 출근 정보는 새로 입력 합리적 |
| 시각 (07:00) | 적정 — 야간 영업 종료 후 + 다음 출근 시작 전 |
| 시간대 (Asia/Seoul) | 적정 — 한국 운영 |
| 너무 자주? | ❌ 적정 (매시간/매분 아님) |
| 입력 직후 리셋? | ❌ 그런 케이스 없음 (스케줄 기반, immediate 트리거 없음) |
| 주말/공휴일 처리 | ❌ **없음** — 매일 무차별 리셋 |

### 5-2. 주말/공휴일 미고려의 영향

- 일요일 영업 안 하는 업체도 일요일 07:00 리셋됨
- 토요일 입력 → 일요일 07:00 리셋 → 일요일 영업 안 함 → 입력 안 함 → 0/0 유지
- 월요일 07:00 추가 리셋 → 월요일 영업 전이라 입력 안 함 → 0/0 유지
- → 월요일 영업 시작 시까지 사용자 화면에 0/0

**이게 "주말 지나면 0/0" 사용자 인상의 정체** — 토~월 영업 안 하는 업체가 많고, 토요일 입력 → 일/월 07:00 두 번 리셋 → 화/수까지 0/0

### 6-2. UX 개선 후보 (별도 PR)

**문제**: 리셋 후 "0/0/나쁨" 표시가 "오늘 영업 안 함" 인지 "정보 없음" 인지 사용자 구분 불가

**옵션 A — "정보 없음" 표시 (권장)**:
- `MainPage applyRoomsBiz` 에 분기 추가:
  - `manualSaved=true && rooms===0 && people===0 && lastResetDate === todayKR`
  - → 화면에 `—` 또는 "정보 없음" 표시
- 혼잡도도 자동 계산 안 함 (별도 표시)
- 업체가 그날 입력 안 한 store 와 입력했지만 0/0 인 store 구분 가능

**옵션 B — admin 의 manualSaved 자동 해제**:
- `dailyReset0700` 에 `manualSaved: false` 도 함께 set
- → 리셋 후 ChatBiz lastPastedText 파싱으로 자동 복원 가능
- 단 의도된 0 저장 (마감/휴업) 도 복원되어 부작용 가능

**옵션 C — 클라이언트 리셋 감지**:
- MainPage 가 `lastResetDate === todayKR` 일 때 "오늘 갱신 필요" 표시
- 변경 코드 작음

**옵션 D — 주말/공휴일 리셋 스킵**:
- `dailyReset0700` 에 요일 체크 추가 (단 한국 휴일 캘린더 의존)
- 또는 store 별 휴무일 (`stores.closed`) 참조 — 데이터 의존

**권장**: 옵션 A 가 가장 명확. 옵션 B 는 부작용 위험. 출시 직전 비권장. 별도 PR 검토.

### 6-3. 즉시 액션 (운영자, 코드 변경 0)

1. **업체에게 매일 입력 안내 공지** — 카톡/이메일/admin 공지 등
2. **출시 전 13개 store 의 manualSaved 데이터 확인**:
   - Firestore Console → rooms_biz → manualSaved 필드 존재 여부 확인
