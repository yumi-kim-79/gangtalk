# 업체(stores) vs 가게(partners) 개념 구분 — 코드 검증 진단

**날짜**: 2026-06-18
**범위**: 사용자의 "업체 = 출근업소, 가게 = 제휴처" 개념이 코드와 일치하는지 검증
**전제**: 진단 전용. 코드/룰/함수 수정·PR·배포 없음.
**중대 결론**:
1. **사용자 정의 "업체"** = 코드의 **`stores` 컬렉션** = 출근하는 구인업소 ✓ (사용자 설명과 일치)
2. **사용자 정의 "가게"** = 코드의 **`partners` 컬렉션** = 서비스 받는 제휴처 (미용실/성형외과 등) ✓
3. **두 컬렉션은 완전히 별개**. functions/index.js 에 `partners` 참조 0건. createBizAccount 는 **stores 컬렉션만** 건드림
4. **업체 계정 ↔ stores 연결은 실재** (createBizAccount 가 `stores/{id}.ownerId = uid` 매핑). **업체 계정 ↔ partners 연결은 존재하지 않음**
5. **이전 진단(`2026-06-18-관리자-삭제기능-진단.md`) 의 "업체 계정에 연결된 stores 삭제" 전제는 코드 사실과 일치**. 단 **용어 표기 혼동** — 코드의 "store" 는 사용자가 "가게" 라고 부르는 제휴처가 아니라 사용자가 "업체" 라고 부르는 출근업소
6. **삭제 로직 자체는 안전** — 다만 UI/주석/메시지에서 "가게 삭제" 라는 표현은 사용자에게 혼동 → "업소 삭제" 또는 "업체 정보 삭제" 로 표기 권장

## 2. 업체 계정 ↔ 어느 컬렉션과 연결되는가

### 2-1. `createBizAccount` (`functions/index.js:2447-2535`) 단계별

1. `admin.auth().createUser({ email, password, displayName: storeName })` — Auth 계정 생성
2. `db.collection('users').doc(uid).set({ type:'company', accountKind:'storeOwner', company.name, ... })` — users doc
3. **storeId 주어지면 `db.collection('stores').doc(storeId).set({ ownerId: uid, ownerEmail: email }, { merge: true })`** — `stores` 매핑 (`:2517-2532`)

### 2-2. `partners` 컬렉션 참조 — 0건

```bash
$ grep -n "collection(.*partners" functions/index.js
# (no matches)
```

→ **Cloud Functions 어디서도 partners 컬렉션 안 건드림**. 업체 계정 시스템은 stores 만 알고 partners 는 모름.

### 2-3. 매핑 관계 정리

| 사용자 정의 용어 | 코드 컬렉션 | 업체 계정 연결 | 관리 페이지 |
|---|---|---|---|
| **업체** (출근 구인업소) | `stores` | ✓ `ownerId/ownerEmail` | `/admin/stores` (관리자), `/biz/my-store` (업체 본인) |
| **가게** (서비스 받는 제휴처) | `partners` | ✗ 연결 없음 | 별도 관리 페이지 없음 (config/marketing 으로 운영) |

## 3. 사용자 화면별 어느 컬렉션에서 오는가

### 3-1. 회원 사이트 (gangtox.com)

| 화면 | 컬렉션 | 표시 데이터 의미 |
|---|---|---|
| **현황판** (MainPage) | `stores` | **출근업소** (강남 인기 업소) |
| **가게찾기** (StoreFinder) | `stores` | 명칭은 "가게찾기" 지만 실제로는 **출근업소** |
| **제휴관** (PartnersPage) | `partners` + `config/marketing/partnerCards` | **제휴처** (사용자가 서비스 받는 곳) |
| **강톡** (GangTalkPage) | `stores` + `board_posts` | 출근업소 + 게시판 |
| **마이페이지 즐겨찾기** | `favorites` (type='store' or 'partner') | 둘 다 |
| **마이페이지 내 업소** (MyStoresPage) | `stores where ownerId==me` | 출근업소 |

### 3-2. 명명상의 혼란

- **사용자 정의**: "가게" = 제휴처 (partners)
- **코드/UI 표기**: "store/Store" = stores 컬렉션 = 출근업소
- 예시:
  - "StoreFinder" 페이지 = **출근업소 찾기** (이름이 헷갈림)
  - "BizMyStorePage" = **업체가 자기 출근업소 정보 입력** (이름이 헷갈림)
  - "StoresManagePage" = **관리자가 출근업소 승인/관리**

UI 의 "가게" 표기는 사용자가 "출근업소" 로 이해해야 함. **이전 진단(`docs/audit/2026-06-18-관리자-삭제기능-진단.md`) 의 표기 "가게 삭제" 는 코드 사실과 일치하지만 사용자 직관과 어긋남**.

## 4. 이전 진단의 전제 재평가

### 4-1. 이전 진단(`2026-06-18-관리자-삭제기능-진단.md`)의 주장
- "stores 삭제 시 5개 연관 데이터 (rooms_biz, ratings, favorites, Storage, config/marketing) 정리"
- "createBizAccount 의 역연산 → 연결된 stores 처리 옵션 A/B"
- "업체 계정 삭제 시 연결 가게 처리"

### 4-2. 코드 사실과의 비교
| 이전 진단 표현 | 코드 사실 | 일치? |
|---|---|---|
| "stores 삭제 = 가게 삭제" | stores = **출근업소** (사용자의 "업체") | **표기 혼동** — 실제로는 "업소 삭제" |
| "업체 계정에 연결된 stores" | createBizAccount 가 `stores.ownerId` 매핑 | ✓ 정확 |
| "stores 의 연관 데이터 5종 정리 필요" | rooms_biz/ratings/favorites/Storage/config 가 stores 와 연관 | ✓ 정확 |
| "partners(제휴처) 연관 처리는 별도" | functions 가 partners 안 건드림 | ✓ 일관 |

### 4-3. **삭제 로직 자체는 안전**
- `deleteBizAccount` 가 건드릴 대상 = Auth + users + 연결된 `stores` (출근업소)
- **`partners` 컬렉션은 절대 건드리지 않음** (코드에 참조 자체 없음)
- 제휴처(partners) 가 잘못 삭제될 위험 = **0** (코드 구조상 불가능)

### 4-4. 다만 표기 / 안내 메시지 권장
| 이전 진단 표현 | 권장 변경 |
|---|---|
| "가게 삭제" | "업소 삭제" 또는 "출근업소 삭제" 또는 "stores 삭제" |
| "연결된 가게" | "연결된 출근업소" |
| "deleteStoreFull" 함수명 | 그대로 유지 가능 (코드는 store, UI 만 표기 변경) |
| 2중 확인 모달 텍스트 | "이 출근업소를 삭제하시겠습니까?" |

## 5. 결론

### 5-1. 사용자 의문에 대한 답
- **"업체"와 "가게"는 서로 다른 개념** — 사용자 설명 정확
- **두 컬렉션 (stores / partners) 완전 별개** — 코드 사실 일치
- **업체 계정 ↔ 출근업소(stores) 연결은 실재** — createBizAccount 가 `stores.ownerId` 매핑
- **업체 계정 ↔ 제휴처(partners) 연결은 존재하지 않음** — functions 에 partners 참조 0건
- **이전 진단의 "stores 삭제" 는 출근업소 삭제로 정확**. 단 **UI/문서 표기 "가게"** 는 사용자에게 혼동 → "업소" 로 통일 권장

### 5-2. 삭제 로직 안전성
| 우려 | 코드 검증 결과 |
|---|---|
| 잘못된 컬렉션 삭제? | ✗ 위험 없음 — partners 는 참조 자체 0 |
| 제휴처 데이터 손실? | ✗ 위험 없음 — 별개 컬렉션 |
| 업체 계정 ↔ 가게 잘못된 연결? | ✗ 위험 없음 — 연결은 stores 만 |

### 5-3. 후속 작업 (이전 진단 보강)
- **PR (a) 백엔드** (이전 §6-1) — 코드 그대로 진행 가능. `deleteStoreFull` / `deleteBizAccount` 함수명도 그대로
- **PR (b) UI** — 모든 사용자용 표기 검토 + "가게 삭제" → "업소 삭제" 로 일관 변경
- **장기**: StoreFinder / BizMyStorePage 등의 페이지 이름도 명칭 명확화 검토 가능 (단 큰 리팩토링이라 별도 작업)
