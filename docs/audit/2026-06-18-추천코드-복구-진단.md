# 추천코드 폴백(y00001) 회귀 + 복구 방향 진단

**날짜**: 2026-06-18
**범위**: 회원 가입 시 추천코드(myRefCode) 발급 흐름. 보고서 Sprint 1 #6
**전제**: 진단 전용. 코드/룰/함수 수정·PR·배포 없음.
**결론**: **예상보다 복잡한 다중 경로 시스템**. `reserveReferralCode` Cloud Function 은 **분명히 미배포** (catch 폴백 발동) — 그러나 그 폴백 변수 `myReferralCode` 는 **실제로 어디서도 사용되지 않음** (코드상 dead variable). 실제 users 에 저장되는 추천코드는 다른 두 경로 — (a) `store/user.js _fbSignupUser` 의 `makeMyCodeV2(email, seq)` 클라이언트 생성 + (b) 서버측 `functions/index.js ensureMyReferralCode` 의 랜덤 코드. **"모든 가입자 y00001"** 이라는 보고가 사실이라면 (a) 의 `seq` 가 항상 1 로 고정되는 race / 트랜잭션 실패가 진짜 원인일 가능성 더 큼. **결정적 확인은 콘솔에서 users 의 myRefCode 분포 확인 (§5-1 스니펫)**.

`makeMyCodeV2(email, seq)` (`store/user.js:54-61`):
```js
function makeMyCodeV2(email = '', seq = 1) {
  const local = emailLocalPart(email)
  const prefix = (local[0] || 'x').toLowerCase()
  const n = Math.max(1, Number(seq) || 1)
  const numStr = String(n)
  const padded = numStr.length >= 5 ? numStr : numStr.padStart(5, '0')
  return `${prefix}${padded}`
}
```

- `email='yusung090909@naver.com'`, `seq=1` → `'y00001'`
- `seq=23` → `'y00023'`
- **즉 사용자가 본 `y00001` 은 폴백이 아니라 _fbSignupUser 가 `seq=1` 로 정상 발급한 값일 가능성**

## 3. 진짜 원인 가능성 시나리오

### 시나리오 A: **이 사용자가 첫 번째 가입자라 seq=1 → y00001** (정상)
- _fbSignupUser 의 makeMyCodeV2('yusung...', 1) = 'y00001'
- 두 번째 가입자가 yusung 이메일이 아니라면 다른 prefix → 'a00001', 'b00002' 같이 각자 다름
- **확인 방법**: §5-1 스니펫으로 users 의 myRefCode 분포 확인. 만약 사용자별로 다양한 코드 → 정상 동작 중

### 시나리오 B: **`meta.counters.userSeq` 트랜잭션 race / 룰 거부 → 항상 base=0, seq=1**
- 모든 가입자에게 `prefix + '00001'` 발급 (사용자가 본 보고와 일치)
- 가능한 원인:
  - firestore.rules `meta/counters` 트랜잭션 실패 (CLAUDE.md Sprint 2 #11 "userSeq 트랜잭션화 — 클라이언트 직접 +1 차단" 참고)
  - 또는 counters 문서가 매번 reset 됨
- **확인 방법**: §5-2 스니펫으로 `meta/counters.userSeq` 현재 값 확인

### 시나리오 C: **`functions/index.js generateUniqueReferralCode` 가 랜덤 → makeMyCodeV2 결과를 덮어씀**
- _fbSignupUser 가 'y00001' 저장 → applyReferralNow 등 호출 시 `existing` 발견하고 유지 → 변화 없음
- ensureMyReferralCode 의 `existing` 체크 → 이미 'y00001' 있으면 그대로 → 덮어쓰지 않음
- **결과**: 'y00001' 그대로 유지. 시나리오 B 와 같은 양상

### 시나리오 D: **클라이언트 트랜잭션이 권한 거부로 실패** → 카운터 업데이트 안 됨
- 모든 가입자가 base=0, seq=1 → 'y00001'
- firestore.rules:
  ```
  match /meta/counters {
    allow read: if signedIn();
    allow create: if signedIn() && !exists(...) && (userSeq == 0 || userSeq == 1) && keys hasOnly ['userSeq', 'updatedAt']
    allow update: if signedIn() && request.resource.data.userSeq == resource.data.userSeq + 1 && diff.hasOnly(['userSeq', 'updatedAt'])
  }
  ```
- create 시 userSeq=1 강제, update 시 정확히 +1 강제. 정상 동작이면 문제 없음
- 만약 가입자 동시 가입 race → 트랜잭션 retry → 정상 동작 보장 (Firestore 트랜잭션 동작)
- **확인 방법**: §5-2 스니펫으로 `userSeq` 값과 users 컬렉션 count 비교. userSeq < users.count 면 카운터가 갱신 안 됨

## 5. 결정적 확인 — 사용자 콘솔 스니펫

### 5-1. users 컬렉션의 myRefCode 분포 확인 (관리자 권한 필요)

Firebase 콘솔 → Firestore → users 컬렉션 전체 export 또는 콘솔에서:

```js

```

**해석**:
- 모든 doc 의 `myRefCode` 가 `prefix + '00001'` 패턴 (`a00001`, `b00001`, `y00001`...) → **시나리오 B/D 확정**. 카운터가 갱신 안 됨
- `myJoinSeq` 가 사용자별로 1, 2, 3 ... 순증 → **시나리오 A** (정상). 단 일부만 `00001` 일 수 있음
- 만약 일부 사용자만 `00001` → 그 사용자들이 첫 번째 가입자거나 트랜잭션 race 일 가능성

## 6. 복구 방향 (별도 PR — 본 진단 외)

### 6-1. 단기 — `reserveReferralCode` 복구 또는 AuthPage 의 dead variable 제거

**옵션 A — 복구**: `functions/index.js` 에 `reserveReferralCode` 를 `runTransaction` 으로 재작성하여 배포. CLAUDE.md Sprint 1 #6 의 요구.

```js
exports.reserveReferralCode = onCall(async (req) => {
  const prefix = String(req.data?.prefix || "").trim().toUpperCase();
  if (!/^[A-Z]$/.test(prefix)) throw new HttpsError("invalid-argument", ...)

  return db.runTransaction(async (tx) => {
    const ref = db.doc("meta/referral_counters")
    const snap = await tx.get(ref)
    const cur = snap.exists ? (snap.data()[prefix] || 0) : 0
    const next = cur + 1
    const code = `${prefix}${String(next).padStart(5, "0")}`

    // 중복 사전 체크 — 같은 prefix 의 카운터로만 확보된 코드라 OK
    tx.set(ref, { [prefix]: next }, { merge: true })
    tx.set(db.doc(`referral_codes/${code}`), { reserved: true, createdAt: FieldValue.serverTimestamp() })

    return { code }
  })
})
```

**옵션 B — Dead variable 제거**: AuthPage 의 `getOrCreateMyReferralCode` 호출 자체 제거 (`myReferralCode` 안 쓰니까). _fbSignupUser 의 자체 생성에 일임.

**추천: 옵션 B** — 클라이언트 자체 생성 (makeMyCodeV2 + counters) 가 이미 작동 중. reserveReferralCode 는 다른 컬렉션 (`meta/referral_counters` vs `meta/counters`) 을 쓰는 *별도 시스템*. 중복 시스템 운영보다 단일화가 안전. AuthPage 의 호출은 단순 dead code 정리.

### 6-2. 단기 — `meta/counters.userSeq` 트랜잭션 race 검증

§5-2 스니펫으로 `userSeq` 와 `users.count` 비교. 어긋나면 트랜잭션 실패 케이스 있는 것 — CLAUDE.md Sprint 2 #11 "userSeq 트랜잭션화 — Cloud Function 으로 이전, 클라이언트 직접 +1 차단" 작업으로 처리.

### 6-3. 중기 — 기존 폴백 코드 받은 계정 재발급

만약 §5-1 으로 다수 사용자가 `prefix + '00001'` 가진 게 확인되면 마이그레이션 Cloud Function 작성:

```js
exports.migrateReferralCodes = onCall(async (req) => {
  assertCallerIsAdmin(req)
  const all = await db.collection('users').get()
  const batch = db.batch()
  let counter = 0
  for (const doc of all.docs) {
    const d = doc.data()
    if (!d.myRefCode || d.myRefCode.match(/^\w00001$/)) {
      counter++
      const seq = d.myJoinSeq || counter
      const newCode = makeMyCodeV2(d.profile?.email || '', seq)
      batch.update(doc.ref, { myRefCode: newCode, 'referral.myCode': newCode })
    }
  }
  await batch.commit()
  return { count: counter }
})
```

(관리자만 호출 가능. 1회 실행)

## 7. 결론

### 7-1. 정리
- **`reserveReferralCode` 미배포는 확실**. 단 그 폴백값 `prefix+'00001'` 은 **AuthPage 의 dead variable** 라 실제 users 에 저장 안 됨
- **사용자 보고 "모든 가입자 y00001" 의 진짜 원인은 다른 곳** — 가장 유력한 후보:
  - 시나리오 B/D: `meta/counters.userSeq` 트랜잭션 race / 갱신 실패 → 모든 가입자 seq=1
  - 시나리오 A: 사용자가 본 사례가 첫 번째 가입자뿐이라 우연히 모두 'y00001' 처럼 보임
- **결정적 확인 필요**: §5-1 스니펫으로 users 의 myRefCode 분포 확인 → 시나리오 확정

### 7-2. 복구 우선순위
1. **§5-1, §5-2 콘솔 확인** (사용자 액션) — 시나리오 확정
2. **AuthPage 의 dead variable 정리** (옵션 B, 안전)
3. **userSeq 트랜잭션 신뢰성 확보** (시나리오 B/D 확정 시)
4. **기존 폴백 코드 받은 계정 재발급 마이그레이션** (확정 시)
