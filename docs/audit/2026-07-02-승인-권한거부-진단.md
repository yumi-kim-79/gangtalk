## 0. TL;DR

- **PR #126 은 원인이 아님** — `exposure.dashboard:false` 추가 자체는 rules 통과 (관리자 분기는 필드 화이트리스트 없음)

- **왜 지금 발견됐나**: `ensureAdminProvision()` 은 **앱 부트스트랩 시 1회만** 실행 (`main-admin.js:86`). `auth.currentUser === null` 이면 조기 return. **로그인 이벤트에 연결 안 됨** → 어떤 이유로 admins 문서가 미생성 또는 유실된 후로 승인 실패

- **해결 (근본)**: `ensureAdminProvision` 을 `onAuthStateChanged` 콜백에 등록 → 로그인 시 자동 생성 (별도 PR 권장)

## 2. firestore.rules stores update 조건 (`:120-132`)

```
allow update: if signedIn()
           && (
                isAdmin()                                              ← ①
                || (
                     resource.data.ownerId == request.auth.uid
                     && request.resource.data.ownerId == resource.data.ownerId
                     && (
                          !('ownerEmail' in resource.data)
                          || request.resource.data.ownerEmail == resource.data.ownerEmail
                        )
                   )                                                    ← ②
                || changesAreOnly(['rating', 'ratingSum', 'ratingCount', 'updatedAt'])
                                                                        ← ③
              );
```

### 2-1. 3 분기 분석
| 분기 | 조건 | 관리자가 승인 시 |
|---|---|---|
| ① `isAdmin()` | `signedIn() && exists(admins/{uid})` | **여기서 통과되어야 함** |
| ② owner 본인 | `resource.data.ownerId == auth.uid` + ownerId/Email 변경 금지 | 관리자 uid ≠ 업체 owner uid → **false** |
| ③ 별점 화이트리스트 | `changesAreOnly(['rating', 'ratingSum', 'ratingCount', 'updatedAt'])` | 승인은 17 필드 → **false** |

→ **`isAdmin()` 이 통과 안 되면 나머지 두 분기 모두 실패 → 권한 거부**

### 2-2. ① 분기 통과 시 필드 화이트리스트 없음
- rules 는 `isAdmin()` 만 확인하고 어떤 필드든 허용
- **PR #126 의 `exposure.dashboard:false` 추가는 rules 위배 아님**
- 필드 수(17개) 도 무관 — `isAdmin()` 이면 자유

## 3. `isAdmin()` 판정 = `admins/{uid}` 문서 존재 (`firestore.rules:9-13`)

```
function isAdmin() {
  return signedIn()
    && exists(/databases/$(database)/documents/admins/$(request.auth.uid));
}
```

→ **관리자 자격은 `admins/{uid}` 문서 존재 여부로 판정**. 이메일 검사 아님.

## 4. `ensureAdminProvision` — admins 자동 등록 로직 (`main-admin.js:36-53`)

```js
async function ensureAdminProvision() {
  const auth = getAuth()
  const db = getFirestore()
  const u = auth.currentUser
  if (!u) return                             // ← ★ 조기 return
  const email = String(u.email || '').toLowerCase()
  if (!ALLOWED_ADMIN_EMAILS.has(email)) return
  const ref = doc(db, 'admins', u.uid)
  const snap = await getDoc(ref)
  if (!snap.exists()) {
    await setDoc(ref, { role: 'admin', createdAt: serverTimestamp() }, { merge: true })
    console.info('[ADMIN] admins/{uid} 문서 자동 생성:', u.uid)
  }
}
```

### 4-1. 호출 위치 (`main-admin.js:73-87`)
```js
router.isReady().then(async () => {
  await firebaseReady
  ...
  app.mount('#app')
  await ensureAdminProvision()               // ← ★ 부트스트랩 시 1회만
})
```

→ **`ensureAdminProvision` 은 앱 로드 시 정확히 1번 실행**.

### 4-2. 위험 시나리오
1. **비로그인 상태로 admin 도메인 첫 진입**:
   - `router.isReady` → `firebaseReady` → `app.mount` → `ensureAdminProvision()` 실행
   - 이 시점 `auth.currentUser === null` (아직 로그인 안 함) → **조기 return**
   - admins/{uid} 문서 **미생성**
2. **`/biz/login` 에서 `gangtalk815@gmail.com` 로그인**:
   - Firebase Auth 상태 변경 → 로그인 완료
   - **`ensureAdminProvision` 재호출 안 됨** — auth 리스너에 연결 안 됨
   - admins/{uid} 여전히 **없음**
3. **`/admin/stores` 승인 시도**:
   - `updateDoc(stores/{id}, {...})`
   - Firestore rules → `isAdmin()` = `exists(admins/{uid})` = **false**
   - stores update 3 분기 모두 실패 → **Missing or insufficient permissions**

### 4-3. auth 이벤트에 admins 자동 생성 훅 없음
- `grep "setDoc.*admins|ensureAdminProvision"` 결과: `main.js` / `main-admin.js` 두 곳뿐
- `watchAdminDoc / watchAdmin` (`useMyPageCore.js:26`, `AppHeader.vue:156` 등) 은 admins 를 **읽기만** — setDoc 없음
- → **로그인 후 admins 자동 생성 경로 부재**

## 5. 권한 거부 정확한 원인 구분

### 후보 A: `admins/{uid}` 문서 없음 → `isAdmin() = false` [★ 가장 유력]
**근거**:
- rules 는 `admins/{uid}` 존재 여부만 확인
- `ensureAdminProvision` 은 부트스트랩 1회만, `currentUser` 없으면 조기 return
- 로그인 이벤트에 연결 안 됨 → 재실행 경로 없음
- 로그아웃/재로그인 후 부트스트랩 시점에 로그인 상태가 아니면 admins 미생성 상태 지속

**증거 검증 방법** (사용자 수동):
1. Firebase Console → Authentication → gangtalk815@gmail.com 의 uid 복사
2. Firestore Database → `admins` 컬렉션 → `{uid}` 문서 존재 확인
3. **없으면 → 후보 A 확정**

### 후보 B: admins 있으나 rules 가 승인 필드 (dashboard 등) 를 허용 안 함 [× 배제]
**배제 근거**:
- rules `:120-132` 의 ① `isAdmin()` 분기는 **필드 화이트리스트 없음**
- `isAdmin()` 통과 시 어떤 필드든 update 가능
- `exposure.dashboard` 를 명시 금지하는 룰도 없음
- 필드 수 (17개) 도 무관

**만약 후보 B 라면 이전 승인 (PR #125 이전) 도 실패했어야 함** — 이전에는 성공했으니 B 아님.

### 후보 C: PR #126 코드가 rules 와 안 맞는 방식 [× 배제]
**배제 근거**:
- PR #126 diff:
  ```diff
  + [`exposure.dashboard`]: false,
  ```
- 필드 1 개 추가만 함. 타입 (`false` boolean), 경로 (dot notation) 모두 정상
- Firestore SDK 가 dot notation 을 정상 필드로 처리 (기존 `exposure.gangtalk` 와 동일 패턴)
- rules 는 새 필드 추가를 별도 금지 안 함 (`isAdmin` 이면 자유)

### 후보 D: PR #126 배포와 우연히 겹친 로그아웃/uid 변경 [보조 가능성]
- 사용자가 최근 로그아웃했다가 재로그인 하면서 (또는 다른 계정으로 로그인) uid 바뀜?
- gangtalk815@gmail.com 은 같은 이메일 — 하지만 Firebase Auth 계정이 삭제되고 재생성됐다면 uid 완전 다름
- 이 경우도 결과적으로 후보 A (admins/{새 uid} 없음) 로 귀결

## 7. 해결 방향

### 7-1. 즉시 해결 (사용자 액션, 코드 변경 0)

**옵션 1 — 부트스트랩 재실행 (가장 간단)**:
1. admin 도메인 (`gangtalk815.com`) 에서 `gangtalk815@gmail.com` 로그인 확인
2. 로그인 상태로 **강제 새로고침** (`Ctrl+Shift+R`)
3. → `ensureAdminProvision()` 재실행 → `auth.currentUser` 있으면 admins/{uid} 자동 생성
4. Firebase Console `admins` 컬렉션에서 문서 생성 확인
5. 승인 재시도

**옵션 2 — Firebase Console 수동 생성**:
1. Firebase Console → Authentication → Users → `gangtalk815@gmail.com` 의 UID 복사
2. Firestore Database → `admins` 컬렉션 → "문서 추가"
3. 문서 ID = 위에서 복사한 uid
4. 필드: `role: 'admin'`, `createdAt: (timestamp)` 등 자유 (rules 는 문서 존재만 확인)
5. 저장 → 즉시 승인 재시도

### 7-2. 근본 해결 (별도 PR 권장)

**PR: `feat/ensure-admin-on-auth-state`**
- `main-admin.js` 의 `ensureAdminProvision()` 을 `onAuthStateChanged` 콜백에 등록
- 로그인 이벤트마다 실행 → 로그인 즉시 admins/{uid} 자동 생성

**변경 예시 (진단 참고용, 본 문서에서 실행 안 함)**:
```js
import { onAuthStateChanged } from 'firebase/auth'

router.isReady().then(async () => {
  await firebaseReady
  ...
  app.mount('#app')
  await ensureAdminProvision()           // 부트스트랩 시점 1회 (기존)

  // NEW: 로그인 이벤트마다 재확인
  onAuthStateChanged(getAuth(), (u) => {
    if (u) ensureAdminProvision()
  })
})
```

**장점**:
- 어떤 순서 (비로그인 진입 → 로그인 / 로그아웃 → 재로그인) 에서도 admins 자동 생성 보장
- 사용자 수동 개입 불필요

**위험**:
- 낮음. `ensureAdminProvision` 자체가 `snap.exists()` 체크 있어 중복 create 안 함
- `ALLOWED_ADMIN_EMAILS` 화이트리스트로 무단 생성 차단
- 단일 파일 (`main-admin.js`) 변경, admin 빌드만 영향

### 7-3. rules 변경 (권장 안 함)
- `isAdmin()` 을 이메일 기반으로 바꾸는 방안 (`request.auth.token.email == 'gangtalk815@gmail.com'`)
- 단점: 이메일 검증 안전성 낮음, custom claim 없이 client-side email 신뢰 → 우회 위험
- **권장 안 함** — 현재 `exists(admins/{uid})` 구조가 안전. 해결은 admins 문서 관리 쪽

## 8. 참고 — 이전에는 왜 성공했나

**가설 (검증 필요)**:
- 이전에 관리자가 admin 도메인에 **로그인된 상태로 부트스트랩** 을 한 적이 있음
- → `ensureAdminProvision()` 실행 시점 `auth.currentUser` 있어서 admins/{uid} 생성됨
- 그 후 승인은 계속 성공
- 최근 어떤 이유로 admins 문서가:
  - (a) Firebase Console 에서 삭제됐거나
  - (b) 계정 재생성으로 uid 바뀌었거나
  - (c) 실제로는 원래 없었지만 다른 경로로 rules 우회 (있을 리 없음)

→ 정확한 원인은 Firebase Console 에서 admins 컬렉션 확인으로 즉시 판별 가능.
